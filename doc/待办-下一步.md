## 1. 自主活动 2.1：每轮两次行动 + 反馈闭环

> **完整规格见 [`doc/自主活动-2.1方案.md`](自主活动-2.1方案.md)**（机主 10-31 定稿，11 节）。
> 这里只留摘要和差异提醒。

### 要改成

1. 每轮**最多两次**行动，类型必须不同；第二次必须**依据第一次的真实结果**重新选。
2. 每次行动产出统一反馈：`result`（success / failed / skipped / **no_output**）+
   `resultSummary` + `reflection` + `next` + `nextStatus`。
   **`no_output` ≠ `failed`**：没产出可能是不想分享、没灵感，不是工具坏了。
3. `pendingNextStep` 从字符串改成对象（topic / intent / sourceAction / status），
   下次可以继续、也可以主动放弃（`abandoned`），**不得把计划当成已完成**。
4. 行为冷却用 `actionId` + `actionType`（xhh_share / bili_comment / draw…），
   同轮不重复类型；冷却只防机械重复，不代表她不喜欢那类活动。
5. 两次都没成果也能正常结束，**不触发补做**；`finish` 永远可选、不计入行动次数。

### 不动的东西

唤醒间隔 3 小时、30 分钟窗口、每轮 6 次模型调用、每天评论 3 / 发帖 1、
每轮分享 2、安静时段、dryRun、`shareMode:"live"`。
**不加模型调用预算、不新增调度器、不重写已有工具、不开发 activityProfile。**

### 现状差距（10-31 核对）

| 项 | 现在 | 2.1 |
|---|---|---|
| 每轮行动 | 1 次 | 最多 2 次、类型不同 |
| 结果字段 | `stopReason`/`error`/各动作 `mode` | 加 `result`/`resultSummary`/`reflection` |
| `no_output` vs `failed` | 没区分 | 必须区分 |
| 冷却 | 只有去重 + 每日额度 | 加 `actionId`/`actionType` 冷却 |
| `pendingNextStep` | 字符串 | 对象 + 状态 |
| 日记 / proactiveNote / H 族 | 已有（10-31） | 保留 |

实施从 `runSession` 开刀：把「一次决策 + 执行」抽成可调用两遍的单元。

## 1.5 空闲时缺的两个能力（2026-10-31 记）

核对她能力清单时发现两处「聊天时能做、空闲时做不到」，都是**入口没接**，不是能力没有。

### A. 空闲时分享图片

- 现状：`share` 只发**文字**（链接由她决定带不带）。翻帖子时图会下到
  `data/social-images` 并把路径给她，但空闲活动没有动作能把图发出去。
- 唯一能发图的空闲动作是 `draw`（`maybeDraw` → `maybeShareImage`，走 `chat.send` 图片通道）。
- 修法：给 `share` 加分支——挑中的内容有图时，用 `maybeShareImage` 发「图 + 一句文字」，
  和画画共用同一套安静时段/额度规则。planner 的 prompt 要说明「有图可以发图」。
- 注意：发图前过一遍隐私（截图可能带别人的头像/私信）。

### B. 空闲时看收件箱、回楼中楼

- 现状：`qq_inbox` → `qq_comment` 是**聊天时**的工具（真机 UI），
  `plugins/autonomous` 里没有任何 inbox 入口（grep 无 `inbox`/楼中楼）。
  所以那 3 小时里有人回她/艾特她，她看不到、也回不了。
- 修法：加一个 `inbox` 动作（或每轮开头先扫一遍收件箱当候选源），
  发现有人回她就作为候选，交给 planner 决定回不回。
- 风险：真机 UI 写操作，比只读高一个量级；要先在 dryRun 下跑，确认不会重复回、
  不会回错人。每轮回复要有上限（建议 ≤1 条，每天 ≤3 条）。

### 顺手记一下现状边界（别踩）

- 小黑盒评论走 **web API**，但当前账号被服务端拒绝（`xhh-write.js` 注释），
  所以 `comments=0` 不是她不想评，是发不出去。要评论只能走真机（聊天时那条路）。
- 手机源（`sources.js` 的 phone）**只读**：只调 status/look，不点不赞不评论。
  `publish` 是另一条真机 UI 路径，不是这个源。

## 1.6 面板升级：小鲸鱼的日常（生活观察面板 v1.0）

> **完整规格见 [`doc/小鲸鱼的日常-面板方案.md`](小鲸鱼的日常-面板方案.md)**。
> 它包含并扩展了原 `doc/自主活动-面板可视化方案.md`（那份保留作背景，以新文件为准）。
> **依赖第 1 条**：活动卡片要展示的 `result` / `reflection` / `next` 得先由 2.1 写出来。

**硬约束：原有功能一律不动、不减、不降权。** 新页面只加不改——
经验管理、状态、画廊、表情、NapCat 操作、人设编辑全部原样保留，原有写入接口不扩权。

分四阶段，**不在同一次提交里混做**：

1. **拆前端**：把 572 行的 `PAGE` 模板拆成 `web-panel/{index.html,style.css,app.js}`，
   功能等价、URL/接口不变、不碰业务逻辑；
2. **生活首页**：今日概览（真实日志为准，不靠时间推断）+ 最近片段 + 今日画作 + 日记摘录；
3. **活动详情**：时间线 + 筛选 + `goal/why/result/reflection/next`，区分
   已完成/探索无成果/主动放弃/工具失败/跳过；
4. **视觉**：样式与适配，最后做。

三条硬约束（沿用原 1.6）：

- **纯读**：面板是独立进程，只能读 `data/autonomous.json`、`autonomous-log.md`、
  画廊 `index.json`、日记文件，不调模型、不写状态；
- **程序结果与模型评价分开存**，没看过作品不能评价画面，没看过正文不能声称读完；
- **不自动补写** `reflection`，空就显示「未留下评价」。

工程红线：改 PAGE 或页面生成逻辑必须跑 `node test/web-panel-page-test.mjs`，
且要**验证浏览器实际加载的脚本**（不能只看 HTTP 200）；改 `web-panel-server.mjs` 必须重启面板；
静态文件能否免重启刷新**先实测再说**，不许未验证就宣称热更新。
