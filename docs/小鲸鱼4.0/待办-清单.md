> 并发安全四条：单写者、原子提交、失败重试/明确报错、崩溃恢复。

  - 已实现：`src/companion/events.js` + `src/store.js` 的 appendIncoming/appendSelf 挂点；`test/companion-events-test.mjs` 7 项通过
  - 验收：事件不重复、不丢失（幂等 + 跨进程锁 + 失败降级）；**待重启后真实消息实测**
  - 未接：`chat.topic_answered` / `chat.plan_cancelled`（需主题判定，放阶段 2）、工具执行事件（可后续在工具层补 `recordToolEvent`）
- [x] **1.2 Token 账本归一**：所有模型调用（聊天 DSH、回落 API、自主活动、日记回顾、silence-ping）走统一费用统计
  - 已实现 `src/token-ledger.js`：`recordAutonomousCall`（串行队列 + 原子写）、`readAutonomous`、`readDay`（聊天+自主+合计）、`readMonth`
  - 自主活动 `noteUsage` / `budgetGate` 改走统一账本：**预算看合计**（聊天 + 自主），不再只看自己那一本
  - 聊天侧仍由 `usage-days/` 聚合（不重复造数据），本模块只做合并读取
  - 成本口径：聊天侧实时文件 `usage-today.json` 不含成本时会明确返回 `cost: null` + `costAccurate: false`，不假装精确
  - 测试：`node test/token-ledger-test.mjs`（13 项，含并发 50 笔不丢、坏文件降级、真实账本备份还原）
  - 验收：并发调用后账本准确 ✅（同进程串行）；跨进程由 autonomous 单实例约束保证
  - 未做：面板展示分列（等 5.1 伙伴状态页一起）
  - **复查（2026-11-01）见 [阶段1.2-复查报告](阶段1.2-复查报告.md)**：
    - 修掉一个破坏性错误：按「聊天+自主合计」卡 5 元预算 → 聊天侧已 ¥20.35，她会永久停摆。
      现在分三层：自主预算（主限制）/ 自主 token 兜底（800 万）/ 可选总预算（默认关）。
    - 补跨进程锁：第一版只锁写、读在锁外，等于各读旧值互相覆盖；现在读-改-写整体在锁内，
      两个子进程各记 50 笔实测总数 100 不丢。
    - 成本未知不再当零：`costAccurate:false` 时如实返回 null，靠 token 兜底。
    - 已修隐患：`usage-days` 曾只在打开面板用量页时才重算。现在补账有三处触发
      （启动后 30 秒、每天 00:05、面板手动），重算是覆盖写所以幂等；
      失败写 `data/usage-backfill-state.json`，下次启动重试；只碰聊天侧日文件，不碰自主账本。
    - 新增 `token-ledger.health()` + `GET /api/usage/health`：最后更新时间、缺失日期、
      重复（日文件 vs usage-daily 快照）、两边成本、成本准确性、未完成重算；
      面板「① 状态」里展示一行。**纯读，不修任何文件。**
    - 预算最终口径（机主 2026-10-31 定）：`monthlyBudgetYuan=5` / `monthlyTokenCap=8000000` /
      `totalBudgetYuan=0`，聊天与自主分别统计、默认不共享；成本未知不按零处理。
- [x] **1.3 事件可靠性 + 存储归档（D5）**
  - 已实现 `src/companion/archive.js`：`listUnprocessed` / `markProcessed`（幂等）/ `archiveProcessed` / `storage` / `health`
  - 归档：已处理且超过 90 天 → 按月 `archive/YYYY-MM.ndjson.gz`（gzip），**按 `processedAt` 判断**；
    归档前校验条数与 eventId 去重，校验不过不删 active
  - 磁盘保护：500 MB warn / 1 GB stop（stop 时暂停归档扩张，记日志）
  - 恢复：重启后 `listUnprocessed` 直接拿到未处理事件；坏行计数跳过不抛
  - 触发点：启动 45 秒后一次 + 每天 00:05（跟在补账之后）
  - 测试：`node test/companion-events-archive-test.mjs`（22 项：幂等消费、失败重试、归档完整性、重复归档不重复、磁盘分级、坏行不炸）
  - **1.2 复查顺带修的**：`token-ledger` 的锁等待从 3 秒加到 10 秒 —— 记账是整文件读改写（写放大），
    Windows 上 100 次连续写入会偶发 99/100（实测）。加长后连跑 10 次稳定。
- [x] **1.4 旧系统兼容（故障注入验收）**：事件系统故障时，QQ 聊天、自主活动、日记继续可用
  - 六个场景全部通过：appendEvent 抛错 / 事件文件不可写 / 目录被删 / 写入卡 1.2s / 故障后重启 / 重复发布
  - 隔离方式：每个场景独立子进程 + `QQ_AGENT_DATA_DIR` 临时目录，**没碰生产 data/**
  - 报告：[阶段1.4-故障隔离验收](阶段1.4-故障隔离验收.md)
  - 关键结论：事件写在业务写入**之后**（先 saveChat 再发事件），所以事件失败回滚不了已成功的消息；
    失败的事件从未落盘，恢复后不会重放成两条
  - 测试：`node test/companion-isolation-test.mjs`（14 项，约 8 秒）

## 阶段 1.5：写入口归一（P0 优先，3~4 天）

## 待定：沉默权（她可以选择不回）

> 记录时间：2026-11-01 20:55
> 来源：机主提问「她是一定要回复吗？可以不可以仅思考不回复」
> 状态：**已记录，未排期**（机主说"先加入，等后续"）

### 现象

2026-11-01 20:22 的真实对话：

```
20:22:36 [老大] 我先说，你先别回，等我说说完了你再回复
20:22:51 [她]   可以
20:22:51 [她]   你说，我不打岔
20:26:41 [老大] 我上了大学以后，本来是想保研的…
20:26:47 [她]   嗯，我在听
20:26:57 [她]   你接着说，说完我再讲
20:27:08 [她]   嗯，考研
20:27:09 [她]   接着说吧
```

**她完全理解了**（"可以，你说，我不打岔"），但**每条消息都回**。

### 架构原因

```
一条消息 → wake(chatKey) → 调 DSH/API → 拿到文本 → 发送
```

**没有"决定不发"的分支。**

`sent.length > 0` → `done`
`sent.length === 0` → `noreply`

`noreply` 状态**已经存在**（16 个历史会话），但它是「发了 0 条」的**结果**，
不是「她主动选择不发」的**决定**。

现在的路径：模型返回空 → 判定为 `DSH_EMPTY_REPLY` **失败** → **回落 API** → API 又给一段话 → 发送。

**所以「不回」在当前架构里等于「失败」。**

### 要解决的问题

| 场景 | 现在 | 应该是 |
|---|---|---|
| 老大说"先别回，我说完你再讲" | 每句都"嗯，我在听" | **安静听着** |
| 群里闲聊 | 每条都接话 | 偶尔接一句 |
| 连发多条补充 | 合并成一次 ✅ | 已经对了 |
| 发个"哈哈" | 她回一段 | 可能一个表情或不回 |

### 真正的难点：三种 `sent = []` 语义不同

- `noreply`：她想了想，决定不回
- `error`：DSH 超时 / 模型挂了
- `aborted`：被打断

**看起来一样，语义完全不同。** 不区分的话会出现"她今天怎么不理我——是在想，还是坏了？"

### 设计方向（初步，未定稿）

1. 给她一个**显式**的「不回」能力，而不是靠"返回空"来猜
2. 程序识别这个信号 → 不发送，但记成 **`noreply`（主动）**，不是 `error`
3. 面板能看到"她今天有 3 次看了没回"——**那是她的选择，不是故障**

### 归属

**不属于 2.6**（2.6 是 Goal 生命周期）。

候选：**2.7 沉默权**，或者在 2.6.7（聊天上下文集成）之后单独做。

### 一个提醒

这个能力如果做错，比"每条都回"更糟——**沉默无法被用户区分成"她不想说"和"她坏了"**。

所以做的时候必须：
- 有明确的"主动不回"记录（不是静默）
- 面板可见
- 和故障严格分开

## 待办：日记对"行动没发出去"的归因不准确

> 记录时间：2026-11-02 18:05
> 来源：机主问「今天日记为什么有很多次想给我发消息，说没发出去？就是因为她写的没找到外部内容？」

### 现象

2026-11-01 的日记里有 4 条「想找人说话｜没发出去」，其中两条写的是：

> 没发出去——**没外部内容**，按原本想做的搭话

### 真实原因（查 autonomous.json 得到）

| 时间 | result | mode | 真实原因 |
|---|---|---|---|
| 05:52 | skipped | **quiet** | **安静时段**（凌晨不发） |
| 15:29:27 | skipped | **dryRun** | **演练模式**（机主手动跑的测试） |
| 15:29:53 | skipped | **dryRun** | 同上 |

**都不是「没外部内容」。**

`没外部内容` 是 `explore` 类行动的说法（榜单没翻到东西），她把那个词套用到 `chat` 上了。

### 问题

`resultSummary` 传给日记的措辞不够准确，她照着写就写歪了：

- `没发出去（quiet）` → 她可能理解成"我在安静时段，所以不发"（这个还算对）
- `没发出去（dryRun）` → 她完全不知道 `dryRun` 是什么，只能瞎编个理由

**后果**：机主看日记会以为"她总是没找到东西所以没法说话"，实际大部分是系统行为。

### 要不要修 / 怎么修

**候选**：

1. 给 `dryRun` 一个**她能理解的说法**（比如"这次只是演练，没真发"）
2. `quiet` 明确说"现在是安静时段"
3. **日记里不让她自己解释原因**，只记事实（"想说话，没发出去"），原因由系统字段记录

**我倾向 3**：行动结果和日记是两层，日记不该替系统编原因。

### 归属

不属于 2.6。候选：2.7 或单独的小修。

## 待办（重要）：容量满时她的新目标会被静默丢掉

> 记录时间：2026-11-02 18:15
> 来源：2.6 代码已在真实环境跑起来后，检查生产数据时发现

### 现状（真实数据）

```
data/companion-state.json
  version: 2                          ← 2.6 代码已真实写入
  goals:
    [paused] 问耳机和今晚睡不睡          11-01 21:32
    [paused] 看看有没有人聊思考强度这件事  11-02 12:38:31
    [paused] 把这篇丢给老大，顺便问问他要我怎 11-02 12:38:33
    [active] 把白嫖资源告诉老大，顺便催他回话 11-02 12:38:35
```

**4 个 goal 在 2 秒内创建完**（同一轮自主活动的决策循环，每做一个动作就换一次方向）。

**现在 paused = 3，正好满了。**

### 后果（已用生产数据副本验证）

```js
setGoal('她这一轮想立的新方向')
// → { ok: false, error: '已经记了 3 件搁置的事，再记一件就 4 件了（上限 3）' }
```

**它不抛错，只是返回 `ok: false`。**

而 `plugins/autonomous/index.js` 的调用点是：

```js
try {
  if (decision.goal) setCompanionGoal(...);   // ← 返回值被忽略
} catch (e) {
  warn(...);                                   // ← 捕不到，因为没抛
}
```

**所以：容量满时，她这一轮决定的方向会被静默丢弃。**

- `companion-state.json` 的 goal 保持旧的
- `autonomous.json` 的 `currentGoal` 也是旧的（2.4 起不写了）
- **日志里什么都不会有**

### 为什么会这样

`setGoal` 是 2.5 的兼容封装，返回 `{ ok, state }`。
`createGoal` 加了容量检查后，失败路径多了 `CAPACITY_FULL`。
**但调用点从来没检查过返回值**——因为以前它不会失败。

### 修法候选

| 方案 | 做法 |
|---|---|
| A | 调用点检查返回值，失败时 `warn` 一行 |
| **B（我倾向）** | 调用点检查返回值；**失败时降级**：把旧 active 保留，不换方向（现在是"想换但换不了，什么都没发生"） |
| C | `setGoal` 失败时抛错（让 catch 接住） |

**B 的问题**：她会"卡在旧方向上"，但至少不是静默的。

**更根本的问题**：**她每做一个动作就换一次方向**（12:38:31/33/35 三个），这才是 paused 迅速填满的原因。

**这是产品层面的问题**：一个动作 = 一个 goal？还是整个活动 = 一个 goal？

### 归属

**不属于 2.6.4b**（那是替换提议）。

候选：**2.6.4c 或 2.6.6（自主活动集成）时一起解决**——需要在接入自主活动时重新想"goal 的粒度"。
