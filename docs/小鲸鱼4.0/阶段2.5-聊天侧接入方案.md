## 一、2.5 要解决什么问题

2.4 之前：

```
她在自主活动里决定「把视频花费的事说开」
  → 写进 companion-state.json

你在 QQ 里跟她说话
  → 她不知道自己在等什么（prompt 里没有这段）
  → 只有下次自主活动醒来才读得回来
```

2.4 之后读点切了，但**聊天路径还没注入** —— 所以这个断点还在。

2.5 就是把这段接上：**聊天时她能看到「现在的方向 / 刚才在聊 / 还没做完的」。**

## 二、两条聊天路径，都要注入

| 路径 | 装配点 | 形态 |
|---|---|---|
| **DSH**（主路径） | `dsh-gateway.js` 的 `personaPatchFile()` | 写一个 `--patch` 文件 |
| **API**（回落路径） | `prompt.js` 的 `buildSystemPrompt({ extraSections })` | 拼进 messages |

**两条都要加**，否则回落时就丢上下文。

### 2.1 API 路径

```js
// prompt.js 的 buildSystemPrompt
const skillSections = [...collectSkillSections(skillContext || {}), ...(Array.isArray(extraSections) ? extraSections : [])];
```

`extraSections` 本来就是"运行时算出来的片段"，**直接加一段**：

```js
// orchestrator 里拼 system prompt 的地方
const companion = promptSection();   // 空串时什么都不加
const extraSections = [
  ...(masterSection ? [masterSection] : []),
  ...(companion ? [{ id: 'companion-state', content: companion }] : [])
];
```

### 2.2 DSH 路径

```js
// dsh-gateway.js 的 personaPatchFile
const sections = [
  roleText,
  skillText,
  companionSection(),   // ← 新增
  ...
];
```

**注意 `personaPatchFile` 有缓存**（比对文件内容，相同就不重写）：

```js
if (fs.readFileSync(PERSONA_PATCH, 'utf8') === content) return { file: PERSONA_PATCH, ... };
```

**Companion State 变了 → content 变 → 会重写 patch 文件**。这是对的（她要看到新状态），代价是一次几十 KB 的写，可接受。

## 三、注入内容：短、诚实、不命令

`promptSection()` 的输出（2.2 已实现）：

```
【你现在】
现在的方向：把视频花费的事说开，别让老大觉得白提
刚才在聊：视频花费
还没做完的：等老大回应，看他怎么说（在等）
```

**三条纪律**：

1. **短**：最多三行，< 300 字。她本来就有记忆库和日记，这里只放"当前状态"。
2. **诚实**：过期项标「已过期，需重新确认」，不假装还有效。
3. **不命令**：这是**上下文**，不是行动清单。她可以知道有三件事没做完，但不代表这轮要逐条处理。
   → 提示词里**不写**"请逐条处理"，只陈述事实。

**我建议 2.5 先不做写**，理由：

1. **读已经能解决核心断点**（她知道在等什么）
2. 写需要新的交互设计，容易把简单的事做复杂
3. 2.4 的结算已经证明了"自主活动写的 pending 能在聊天后结算"，**闭环是通的**

**如果要做**，我推荐 **A（加工具）**：她明确知道自己记了什么，比程序猜准确。但那是 2.6 的事，要单独评估成本。

## 五、结算：2.5 要补一条通用规则

现在只有"迁移来的那条"能结算（`migrationTag === 'chat-wait-reply'`）。

2.4 之后，自主活动新加的 pending（比如「等老大回一句，再翻翻评论」）**永远结算不了** —— 它没有 tag。

**2.5 要补的规则**（保守版）：

```
老大回话后：
  · 只结算 status === 'waiting' 的
  · 且 at 早于"最后一条用户消息"
  · 且 文本里含"等/回/再说"这类信号
  · 结算成 done，不删
```

**为什么不结算 `pending`**：

- `pending` = "还没开始做的事"（明天查资料），老大回话不代表它做完了
- `waiting` = "在等某件事"（等他回话），他回话就是这件事完成了

**这个区分就是 2.2 定 `waiting` 状态的意义。**

**但自主活动现在写的都是 `pending`**（`addCompanionPending({ status: 'pending' })`）。

**所以 2.5 要改**：如果 `decision.next` 是"等回话"类，就写 `waiting`。

```js
// plugins/autonomous/index.js 的决策后写入
const isWait = /等(老大|回话|回复|回应)/.test(next);
addCompanionPending({ text: next, source: 'autonomous', status: isWait ? 'waiting' : 'pending' });
```

**这样**：

- 「等老大回一句，再翻翻评论」→ `waiting` → 老大回话就结算
- 「明天查查资料」→ `pending` → 不结算，等它自己过期
