## 二、发现的问题

### 问题 1（低）：`statusSince` 相同时的选择依赖排序稳定性

**代码**（`state.js` `createGoal` 第 ② 段）：

```js
const samePaused = same
  .filter((g) => g.status === 'paused')
  .sort((a, b) => Date.parse(b.statusSince || 0) - Date.parse(a.statusSince || 0));
if (samePaused.length) {
  const target = samePaused[0];
```

**实测**（三条 `statusSince` 完全相同的 paused）：

```
第一次恢复: g-aaa
第二次恢复: g-aaa (created=false)
第三次恢复: g-aaa (created=false)
```

**结论**：结果**确定**（V8 的 sort 是稳定的），但**这是实现细节，不是显式规则**。

**如果**：
- 数组顺序变了（比如手工编辑文件、或将来有别的写入路径）
- 或 Node 换了排序算法

**结果就会变**。

**影响**：低。当前的写入路径总是 push 到数组末尾，顺序稳定。

**最小修复建议**（不实施）：加一个 tie-breaker，比如 `statusSince` 相同时按 `id` 升序。

### 问题 2（低）：`updateGoal` 不写 history

**代码**：

```js
if (g.text === t) { out = g; changed = false; return; }
g.text = t;
g.updatedAt = nowIso();
```

**只改 `text` 和 `updatedAt`，不写 history。**

**判断**：**这是合理的**——history 记录的是**状态变化**（`from` / `to`），而 `updateGoal` 不改状态。

**但**：如果将来要追溯"描述什么时候被改过"，就没有记录。

**结论**：**符合设计，不是缺陷**。但如果需要审计描述变更，要另加机制。

## 四、`mutator` 执行次数（关键并发细节）

`created` 和 `out` 是**闭包变量**，在 `updateCompanion(fn)` 的 `fn` 里赋值。

**如果 `fn` 执行多次**（比如 `withState` 的 3 次重试），`created` 可能被覆盖。

**验证**：

```js
// state-store.js
for (let attempt = 0; attempt < 3; attempt += 1) {
  const got = withStateOnce(file, mutator, ...);
  if (got.ok || got.code !== 'ELOCKTIMEOUT') return got;
}
```

`ELOCKTIMEOUT` 是**锁循环耗尽、`mutator` 从未执行**的情况：

```js
// file-lock.js
for (let i = 0; i < retries; i += 1) {
  try { fs.writeFileSync(lock, ...); } catch (e) { ... continue; }
  try { return fn(); } finally { fs.unlinkSync(lock); }   // ← 只有拿到锁才执行
}
throw ELOCKTIMEOUT;   // ← 没执行过 fn
```

**结论**：**`mutator` 只会执行一次**，`created` / `out` 不会被污染。✅

**但**：`fn` 里**不能有外部副作用**（比如日志、网络请求），否则重试会重复。**当前四个接口的 `fn` 全是内存操作** ✅

## 六、2.6.3 的准备

你列的三种确认语义，`canOperate` 现在只返回一个 boolean，**无法区分**：

| 操作 | autonomous | user_directed | 需要什么确认 |
|---|---|---|---|
| complete | 自主判断 | 用户确认**已完成** | 不同的确认语义 |
| cancel | 自主判断 | 用户**明确放弃** | 不同的确认语义 |
| supersede | 自主判断 | 用户确认**旧目标已失去意义** | 不同的确认语义 |

**2.6.3 要设计的重点**：**三种操作各自的确认状态机和记录格式**，不能共用一个 `confirmed: true`。

**特别要防的**（你的原话）：

> 防止模型把用户暂时不提、暂时搁置，误判为取消或取代。

**我建议 2.6.3 引入一个显式的"提议"概念**：

```js
completion: {
  proposedAt,      // 什么时候提的
  proposalKind,    // 'complete' | 'cancel' | 'supersede'
  reason,          // 为什么觉得可以了
  askedAt,         // 什么时候问的老大
  answerAt,        // 老大什么时候答的
  answer,          // 'yes' | 'no' | 'later' | ''
  answerQuote      // 老大原话（可选，便于审计）
}
```

**关键**：**提议不等于执行**。`user_directed` 的三种操作，只有 `answer === 'yes'` 才真的改状态。
