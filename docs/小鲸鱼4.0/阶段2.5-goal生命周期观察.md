## 一、发现的事实

生产环境里出现了一个**真实的过时 goal**：

```json
// data/companion-state.json
"goal": {
  "text": "问出老大昨晚真实睡眠情况",
  "source": "autonomous",
  "since": "2026-11-01T07:29:56.671Z"    // 15:29:56
}
```

**实际进展**：

```
10:27:39  她问「昨晚你到底睡没睡着啊？」
10:49:39  老大答「睡着了呀，我现在刚醒」
          → 这个目标 10:49 就达成了
15:29:56  自主活动又把它写进 goal（作为「当前方向」）
15:48:25  老大问「你在干什么」
15:48:41  她答「刚在「睡」，你一喊我才睁眼」
          → **没有重复问睡眠**
```

**所以**：goal 过了 5 小时还是过时的，但她这次没有因此重复提问。

---

## 二、这是设计缺口，不是 bug

2.5 的结算规则只处理 `waiting`（等回话），**没有处理「goal 达成」**。

goal 的清除只有三条路径：

| 路径 | 条件 | 现在会不会发生 |
|---|---|---|
| `settleChatPending()` | 有**匹配文本的 pending** 被结算 | 这条 goal 没有对应 pending → 不会 |
| 下一轮 `setGoal()` | **直接覆盖** | 16:59 会 |
| `clearGoal()` | 手动调用 | 没人调 |

**结论**：一个达成的 goal 会一直留到下次自主活动。

---

## 三、为什么不选 A / B（机主判断）

### A. 用关键词/肯定回答检测达成

**误清风险比旧 goal 暂时残留更难处理**。

举例：

```
goal:「进一步了解昨晚睡眠质量」
老大:「睡着了呀」
```

这句话**确实回答了睡眠问题**，但**不代表「了解睡眠质量」这个目标达成了**。

系统很难仅靠关键词区分「回答了问题」和「目标达成的充分条件」。

### B. 用时间过期

**时间不是完成依据**。

24 小时没更新 ≠ 事情做完了。最多能标「过期，待确认」，不能直接清。

### C. 先观察（选中）

- 目前没有证据表明残留导致重复提问
- 下一轮自主活动会覆盖
- 避免为消除一个暂时性问题引入更复杂的误判机制

## 六、如果真要做，2.6 的方向（机主倾向）

**明确的 `completeGoal` 机制**：

- 由**自主活动**或**明确的上下文判断**提出「这件事完成了」
- 再由状态更新逻辑清除
- **不让底层状态模块去猜自然语言是否意味着完成**

这符合 agent 设计的一条通用原则：

> 目标完成应当有明确的完成条件和可验证依据，而不是仅凭模型对自然语言的猜测。
