# 1.4 故障隔离验收报告

> 时间：2026-11-01 05:15（Asia/Shanghai）
> 性质：**故障注入测试**，不是新功能
> 隔离方式：每个场景一个独立子进程，`QQ_AGENT_DATA_DIR` 指向临时目录 ——
> **全程没有碰生产 `data/`**（机主 2026-10-31 明确要求）
> 结论：六个场景全部通过，事件系统故障不影响聊天/消息写入

## 一、验收结果

| # | 故障场景 | 预期 | 实际 |
|---|---|---|---|
| 1 | `appendEvent` 抛错（模拟 EACCES） | QQ 聊天正常 | ✅ 返回 `{ok:false,error}` 而不是抛；同一条消息照常写进存档 |
| 2 | 事件文件不可写（只拒绝 companion-events 路径） | 不影响原有消息写入 | ✅ 两条消息（入站 + 出站）都写进 `messages/*.json` |
| 3 | 事件目录被删 | 旧系统继续运行 | ✅ 不抛；目录自愈重建；聊天照常 |
| 4 | 事件写入卡 1.2 秒 | 不阻塞聊天回复 | ✅ 聊天完成；**代价可观察**（耗时 +1.2s），不是静默 |
| 5 | 故障后重启 | 能重新发布 | ✅ 失败的那笔没进文件；恢复后新事件正常；**没有把失败的重放成两条** |
| 6 | 重复发布同一 eventId | 不产生重复业务效果 | ✅ 三次发布只落 1 条；聊天侧按自己的规则去重 |

## 二、为什么能扛住

三道隔离，缺一不可：

```
store.appendIncoming / appendSelf
   ├─ saveChat(st)          ← 先写聊天存档（旧的、必须成功的）
   └─ try { recordMessageEvent(...) } catch {}   ← 事件永远在最后，且包住
```

1. **位置**：事件写在 `saveChat()` **之后** —— 聊天存档先落盘，事件失败回滚不了已经成功的写入；
2. **包裹**：调用点有 `try/catch`，`appendEvent` 内部也有 `try/catch` 返回 `{ok:false}`；
3. **不重放**：失败的事件从未写进 `active.ndjson`，恢复后不会"补发"已经失败的那笔 ——
   避免"本来成功过的动作被执行两次"。

## 三、边界（这些没测，如实写）

- **超时**是用 busy-wait 模拟的，不是真实的 IO 超时（Node 的同步写没有超时概念）；
  真实磁盘卡顿的表现与此一致：拖慢、不失败。
- **跨进程锁超时**不在本测试范围（`appendEvent` 拿不到锁时会降级为"直接追加"，
  在并发下可能多写一条，由 eventId 幂等兜住 —— 见 `events.js` 注释）。
- **日记写入**目前还是三处旧入口（1.5.1 才统一），本测试用"聊天消息写入"代表"旧系统写入"。
  1.5.2 迁移完成后，需要把日记也纳入这组用例。

## 四、对 1.5 的启示

| 发现 | 对写入口归一的要求 |
|---|---|
| 事件写在业务写入**之后**才能保证不回滚 | Diary Writer 也必须：**先写日记，再发事件**；不许先发事件再写盘 |
| 失败的事件从不重放 | Diary Writer 的幂等键要落在**写入前**判断，不能靠"重放时去重" |
| 慢是可见的代价 | 1.5.3 的 `autonomous.json` 单写者要记录"等锁耗时"，别把卡顿藏起来 |
