## 二、`intent` 字段的核实结果（机主点名要查）

### 读点 4 确实用了 `intent`

```js
// index.js:1041-1046
const pns = st.pendingNextStep;
const pending = typeof pns === 'string'
  ? pns.trim()
  : (pns && typeof pns === 'object'
    ? [pns.topic, pns.intent].filter(Boolean).join('｜')   // ← 用了
    : '');
```

### 但两者内容 100% 相同

| 检查 | 结果 |
|---|---|
| history 里对象型 `pendingNextStep` | 0 条（该字段只存"当前"，不存历史） |
| 当前状态 `topic` vs `intent` | **完全相同** |
| 字符串形式（更老格式） | 0 条 |

**所以**：原代码在两者相同时，拼出来是 `"等老大回应，看他怎么说｜等老大回应，看他怎么说"` —— **重复了一遍**。

### 结论：不纳入新 schema

- `pending[].text` 已足够表达"这件事是什么"
- `intent` 和 `topic` 语义重叠（都是"要做什么"），历史数据里从没分开过
- **迁移只搬 `topic` 没有丢信息**

### 但要在读点 4 的注释里写清这个差异

新实现只取 `text`，planner 看到的文本会比以前**少一份重复**。这是有意的简化，不是丢失。

### 3.2 读点 3：`settleChatPending`

**现在**：读 `st.pendingNextStep`，条件满足就清空 `st.pendingNextStep` 和 `st.currentGoal`。

**改成**：

```js
export function settleChatPending(st) {
  // 从 Companion State 里找"等老大回话"的那条
  const list = activePending();          // companion 的未结算项
  const hit = list.find((p) =>
    p.source === 'autonomous'
    && p.status === 'pending'             // 只结算 pending，waiting 不动
    && 有 at
  );
  if (!hit) return false;
  if (!(last > at + 90_000)) return false;

  settlePending(hit.id, 'done', { source: 'autonomous' });   // 走 companion 的单写者
  if (goal 也是这一件事) clearGoal({ source: 'autonomous' });
  return true;
}
```

**关键决策**：

- **怎么判断"这条 pending 就是等回话的那条"**：旧数据靠 `sourceAction === 'chat'`。
  新 schema 没有 `sourceAction`，用 `source === 'autonomous'` + `status === 'pending'` + **有 `at`**。
  但这样会把所有自主活动加的待办都当"等回话"——**太宽**。
- **更稳**：新 schema 的 `pending` 加一个 `kind` 字段（`'wait-reply'` / `'todo'`），迁移时把 `sourceAction==='chat'` 的标成 `wait-reply`。
  **但这要改 schema**，超出 2.4 范围。

**折中（2.4 用）**：
- 结算条件：`source === 'autonomous'` 且 `status === 'pending'` 且 **`at` 早于最后一次聊天**
- 而 `goal` 只在"这条 pending 的 text 和 goal 说的是同一件事"时才清（用文本包含判断，保守）
- **如果判断不了，就只结算 pending，不清 goal** —— 宁可留一个多余 goal，也不要误清

**这条要问机主确认**（见第五节）。

### 3.3 读点 4：`decideIntent`

// 4.0 / 2.4：改从 Companion State 读。**不再拼 topic｜intent** ——

## 五、要你确认的两件事（影响 2.4 的实现）

### ① `settleChatPending` 怎么判断"这条 pending 就是等回话"

旧逻辑靠 `sourceAction === 'chat'`（自主活动自己写的标记）。

新 schema 没有这个字段。三个选项：

| 方案 | 做法 | 风险 |
|---|---|---|
| **A** | 所有 `source==='autonomous'` 且 `status==='pending'` 的都算 | **太宽**：她记的"明天查资料"也会被老大回话清掉 |
| **B** | 新 schema 加 `kind: 'wait-reply' | 'todo'`，迁移时标 | 要改 schema（2.2 已定稿） |
| **C**（我建议） | **2.4 先只结算"从旧数据迁来的那条"**（`migratedFrom` 标记 + `sourceAction` 信息），新加的 pending 不参与结算 | 保守，不会误清 |

**我倾向 C**：2.4 只保证"迁移过来的那条能正常结算"，新的 pending 结算留给 2.5（聊天侧接入时一起设计）。

### ② 读点 4 从"一条"变成"多条"

旧代码只给 planner 看一条 `pendingNextStep`。

新 schema 允许多条 → planner 会看到 `text1；text2；text3`。

**这算改变业务决策吗？**

我的判断：**不算**（她看到更多"没做完的事"，是 2.2 设计时就想要的效果）。但**这是行为变化**，要你点头。
