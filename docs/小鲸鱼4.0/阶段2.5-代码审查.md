## 一、`lastUserMessageAt()`

### 1.1 源码

```js
// plugins/autonomous/index.js
export function lastUserMessageAt() {
  try {
    const master = String(getConfig()?.persona?.masterId || settings().shareTarget || '');
    if (!master) return 0;
    const file = path.join(DATA_DIR, 'messages', `private_${master}.json`);
    const raw = JSON.parse(fs.readFileSync(file, 'utf8'));
    const list = Array.isArray(raw) ? raw : (raw.messages || []);
    for (let i = list.length - 1; i >= 0; i -= 1) {
      const m = list[i];
      if (!m || m.self) continue;
      const ts = Number(m.ts);
      if (Number.isFinite(ts) && ts > 0) return ts;
    }
    return 0;
  } catch {
    return 0;
  }
}
```

### 1.2 逐项核查

| 检查项 | 结果 | 依据 |
|---|---|---|
| 文件不存在 | ✅ 返回 0 | `readFileSync` 抛 → catch → 0 |
| 文件损坏 | ✅ 返回 0 | `JSON.parse` 抛 → catch → 0 |
| 空数组 | ✅ 返回 0 | 循环不执行 → 0 |
| `self === false` 过滤 | ✅ **实测全是 boolean** | 5519 条消息，`self` 类型统计 `{"boolean":5519}` |
| 时间戳无效 | ✅ 跳过 | `Number.isFinite(ts) && ts > 0` |
| **取真正时间最新** | ⚠ **不是** | 取的是"数组末尾往前第一个" |
| 只读当前机主私聊 | ✅ | 只读 `private_<masterId>.json`，群聊 `group_*.json` 不碰 |

### 1.3 问题：数组顺序 ≠ 时间顺序

**实测**：`private_1846383180.json` 有 5519 条，**5 处乱序**：

```
位置 145:  23:10:49 → 23:10:48（差 775ms）
位置 1650: 13:30:08 → 13:30:08（差 281ms）
位置 1652: 13:30:09 → 13:30:09（差 41ms）
位置 2801: 13:45:10 → 13:45:09（差 855ms）
位置 3754: 23:18:05 → 23:18:04（差 308ms）
```

**原因**：QQ 消息时间戳只有秒级精度，同一秒内的消息按到达顺序排，`ts` 可能倒挂几百毫秒。

**当前影响**：

```
按数组顺序取: 2026/11/1 15:27:46
按时间最大值取: 2026/11/1 15:27:46
两者相同? 是
```

**判断**：**理论存在，当前无实际影响**。乱序都在毫秒级，不影响"谁更晚"的判断。

**但**：如果将来消息批量导入或补插，可能放大。**建议改成取 max**（成本很低）。

## 二、waiting 结算

### 2.1 源码

```js
export function settleChatPending() {
  const list = activePending();
  if (!list.length) return false;

  const userAt = lastUserMessageAt();
  if (!userAt) return false;

  let settled = 0;
  for (const p of list) {
    const at = Date.parse(p.at || '');
    if (!Number.isFinite(at) || at <= 0) continue;
    if (!(userAt > at)) continue;                    // 严格晚于

    const isMigrated = p.migrationTag === 'chat-wait-reply';
    const isWaiting = p.status === 'waiting';
    if (!isMigrated && !isWaiting) continue;

    if (isMigrated && !(userAt > at + 90_000)) continue;   // 迁移的 90 秒保护

    settlePending(p.id, 'done', { source: 'autonomous' });
    settled += 1;
  }

  if (!settled) return false;

  // goal 只在"它说的就是同一件事"时清 —— 保守
  const cg = readCompanion().goal;
  const hitTexts = list.filter((p) => p.migrationTag === 'chat-wait-reply' || p.status === 'waiting').map((p) => p.text);
  if (cg && hitTexts.includes(cg.text)) clearGoal({ source: 'autonomous' });

  log(`老大已经回过话，结算了 ${settled} 条待办`);
  return true;
}
```

### 2.2 核查结果

| 检查项 | 结果 | 说明 |
|---|---|---|
| 只处理当前机主私聊 | ✅ | `lastUserMessageAt` 只读 `private_<masterId>.json` |
| 不把机器人回复当触发 | ✅ | `self === false` 过滤 |
| 不把群聊当触发 | ✅ | 不读 `group_*.json` |
| 不把其他用户当触发 | ✅ | 私聊文件里只有机主 |
| `userAt` 严格晚于 `pending.at` | ✅ | `if (!(userAt > at)) continue` |
| 多条 waiting 逐条处理 | ✅ | 循环 + 幂等 |
| `migrationTag` 兼容分支 | ✅ | 保留，且额外 90 秒保护 |
| 重复结算幂等 | ✅ | `settlePending` 内部检查状态 |

### 2.3 **问题：goal 可能被误清**

**源码第 3 段**：

```js
const hitTexts = list.filter((p) => p.migrationTag === 'chat-wait-reply' || p.status === 'waiting').map((p) => p.text);
if (cg && hitTexts.includes(cg.text)) clearGoal({ source: 'autonomous' });
```

`hitTexts` 收集的是 **`list` 里所有 waiting/migrated 的 text**，**不管它有没有真的被结算**。

**误清场景**：

1. 自主活动写：`goal = "等老大回话"`，同时 `pending = "等老大回话"`（`status: waiting`，`at = 现在`）
2. 老大消息的 `ts` **早于** `at`（比如消息先到、pending 后写）→ **不结算**
3. 但 `hitTexts` 里仍有 `"等老大回话"`
4. → `cg.text === "等老大回话"` → **`clearGoal()` 被调用**
5. **goal 被清掉了，但那条 pending 还在**

**后果**：goal 消失，但对应的事还没做完。下次自主活动看不到方向。

**概率**：低（要求 goal.text 和某条未结算 waiting 的 text 完全相同）。

**但它违反"只在说的就是同一件事时清"的原则。**

**修法（一行）**：只在**实际结算成功**的里面找：

```js
const settledTexts = [];   // 循环里 push
...
if (cg && settledTexts.includes(cg.text)) clearGoal(...);
```

## 四、并发与持久化

### 4.1 核查结果

| 检查项 | 结果 | 依据 |
|---|---|---|
| 所有修改走单写者 | ✅ | `settlePending` / `clearGoal` / `setGoal` / `addPending` → `updateCompanion` → `withState` → `withFileLock` |
| 原子写入 | ✅ | `writeFileAtomic`（临时文件 + rename，带 EPERM 退避） |
| 聊天结算 vs 自主写入 | ✅ 不会丢更新 | 每次 `updateCompanion` 都是**锁内读-改-写**：读最新文件 → 改 → 写 |
| N 条结算 = N 次加锁 | ⚠ 性能 | pending 通常 < 5 条，可接受 |

### 4.2 一个细节

`settleChatPending` 里的 `list` 是循环开始时的快照。

- 每次 `settlePending(p.id)` 内部会**重新读文件**找 id → 不会因为快照过时而改错
- 但 `settled` 计数是本地累加 → 反映"尝试结算的条数"，不是"实际改动的条数"

**影响**：无（返回值只用于日志和 `if (!settled) return false`）。
