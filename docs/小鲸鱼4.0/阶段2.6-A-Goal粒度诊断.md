## 一、根因：`decision.goal` 被当成了 Companion Goal

### 1.1 真实数据

11-02 12:38 那轮活动（`round-42574042`）：

```
intent: continue | 看看老大回没回话，顺便翻翻评论里有没有人吐槽那个架构
why:    上次留的事就是等老大回一句再翻架构评论，现在有空，想接着看看

actions:
  · comment → failed  | goal=看看有没有人聊思考强度这件事
  actions.next: 翻翻这条的评论，再瞄一眼老大回没回
  · share   → success | goal=把这篇丢给老大，顺便问问他要我怎么用
  next: 等老大回话，看他怎么选
  · chat    → success | goal=把白嫖资源告诉老大，顺便催他回话
  next: 等老大回话，看他对我找的资源感不感兴趣
```

### 1.2 对照 `companion-state.json`

```
[paused] 问耳机和今晚睡不睡               ← 11-01 21:32 的 chat 动作
[paused] 看看有没有人聊思考强度这件事       ← comment 动作（**它还 failed 了**）
[paused] 把这篇丢给老大，顺便问问他要我怎么用 ← share 动作
[active] 把白嫖资源告诉老大，顺便催他回话    ← chat 动作
```

**四条 Goal，逐字对应四个 action 的 `goal` 字段。**

### 1.3 代码位置

```js
// plugins/autonomous/index.js，决策后
if (decision.goal) setCompanionGoal(String(decision.goal), { source: 'autonomous' });
```

**`decision.goal` 的语义是"这个动作想干什么"**（planner 里叫 `goal`，和 `next`、`action` 并列）。

**Companion State 的 `goal` 语义是"长期方向"**。

**两者被直接划等号了。**

### 1.4 后果

| 后果 | 说明 |
|---|---|
| **paused 迅速填满** | 一轮活动 3 个动作 → 3 个 Goal → 4 秒内填满 3 个 paused |
| **失败的动作也建 Goal** | `comment` 失败了，Goal 照样进列表 |
| **Goal 语义被污染** | 现在这 4 条全是"这一轮想干什么"，没有一条是"长期方向" |
| **容量检查变成噪音** | 因为 Goal 本身就不该存在，容量满不是资源问题，是分类错误 |

## 二、四层概念（机主定稿）

| 层 | 是什么 | 例子 | 存哪 | 生命周期 |
|---|---|---|---|---|
| **Goal** | 跨越多个活动周期、有持续关注价值的方向 | 持续提升 C++ 和算法能力 | `companion-state.json` 的 `goals[]` | 月级 |
| **Pending** | 为了推进 Goal，需要记住并在以后继续处理的事 | 整理一份树形 DP 学习路线 | `companion-state.json` 的 `pending[]` | 天级 |
| **Round** | 某一次自主活动（一段执行周期） | 11-02 12:38 那轮 | `autonomous.json` 的 `history[]` | 一次性，归档 |
| **Action** | 这一轮决定做什么 | 搜索一篇文章、发一条消息 | `history[].actions[]` | 一次性 |

**外加**：

| 层 | 是什么 | 存哪 |
|---|---|---|
| **Topic** | 聊天话题 | `companion-state.json` 的 `topic` |

**Topic 不塞进这四层**（机主明确）。

---

## 三、设计原则（机主定稿）

> **只有跨越单次自主活动、具有持续关注价值的方向，才能成为 Goal。**
>
> **单次活动产生的具体行动默认不持久化为 Goal；需要以后继续处理时，才考虑记录为 Pending。**

### 判定示例

| 小鲸鱼的想法 | 应该归属 |
|---|---|
| 看看有没有人讨论思考强度 | **Action** |
| 把找到的文章发给老大 | **Action** |
| 老大还没回复，之后需要再问 | **Pending**（确实值得跟进时） |
| 长期关注 AI 领域的新进展 | **Goal** |
| 持续完善自己的 AI 伙伴系统 | **Goal** |
| 今天进行了一轮 B 站浏览 | **Round** |

## 五、这个发现改变了什么

### 5.1 2.6.4b（替换提议）的前提不成立

**原设计**：「容量满时，提议替换哪个旧 Goal」。

**问题**：如果 Goal 本身就是误创建的，那"替换哪个"就是在错误前提上做优化。

**先修分类，再谈替换。**

### 5.2 2.6.4c（autonomous 容量淘汰）同样

**本来要设计"淘汰哪个 autonomous Goal"**。

**但**：如果 autonomous Goal 根本不该那么多，淘汰算法就是过度设计。

### 5.3 2.6.5（完成建议）也只对真正的 Goal 有意义

**给一个"看看有没有人聊思考强度"提完成建议** ——没有意义。

### 5.4 容量上限不该改

**机主明确**：1 active + 3 paused 是安全约束，**不因为错误粒度导致满就放宽到 10 或 20**。

**先解决"不该建的 Goal"，再看真实需求。**

## 六、必须修的工程问题（独立于粒度）

### 6.1 `CAPACITY_FULL` 静默丢弃

```js
try {
  if (decision.goal) setCompanionGoal(...);   // ← 返回值忽略
} catch (e) {
  warn(...);                                   // ← 捕不到，因为不抛
}
```

**`setGoal` 返回 `{ ok: false }` 不抛异常** → **静默丢弃**。

**修（原则，非最终代码）**：

```js
const r = setCompanionGoal(...);
if (!r?.ok) {
  warn('Goal 创建失败', { code: r?.code, capacity: r?.capacity });
}
```

**机主强调**：**失败后不能把即时行动也丢掉**——行动本身可能仍然值得执行，只是不该作为长期 Goal 保存。

### 6.2 修复后的语义

```
动作的 goal（决策层）  →  只记 history[].actions[].goal（已经有了）
                       →  不再写 Companion Goal
```

**Companion Goal 只能由"她明确表达长期意图"创建**——那个入口 2.6.6 才接。

## 八、要机主确认的

### ① 四条真实 Goal 怎么处理

| 方案 | 做法 |
|---|---|
| A | **保留不动**（当历史遗留，不影响功能） |
| B | 手工转成 `cancelled`（记录"分类错误，不是真正的方向"） |
| C | 等 2.6.6 接入后，由她自己在某轮活动中判断 |

**我倾向 A**（保留不动）——它们是**真实的决策记录**，删了会丢失"她当时确实想做这件事"的证据。而且它们现在只占容量，不影响别的功能。

**但如果保留，容量一直是满的**，2.6.6 接入后她会立不了新 Goal。

**折中**：A + 2.6.6 接入时**给一次性的"清理误分类"操作**（不是自动，是明确的维护动作）。

### ② `setCompanionGoal` 的调用要不要**现在**就删

**机主说**："把这列为下一批修改的必修项"。

**"下一批"是 2.6.6**（接 autonomous）还是**现在**？

**我倾向现在删**：因为现在每跑一轮自主活动就多一条假 Goal，容量已经满了，**继续跑只会更糟**。

**但**：删了之后，`autonomous.json` 的 `currentGoal` 也不写（2.4 起），她就**没有"当前方向"了**。

**这正好是设计问题**：**自主活动该不该有"当前方向"？**

**如果该有**：它存在哪？Round 记录里（`intent`）已经有了。

**答案可能是**：**自主活动不需要跨轮的方向**，每轮自己判断。

**这个要一起决定。**
