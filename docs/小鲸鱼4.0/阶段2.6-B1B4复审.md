## 四、发现的问题

### P1-1：`createGoal` 和 `setGoal` 可以绕过 B3 证据校验

**代码位置**：

```js
// src/companion/state.js:472
export function createGoal({ text, source = 'autonomous' } = {}) {
  // ← 没有任何 evidence 校验
}

// src/companion/state.js:1200
export function setGoal(text, { source = 'unknown' } = {}) {
  const r = createGoal({ text, source });   // ← 也没校验
}
```

**影响**：

- 任何调用方 `createGoal({ text, source: 'autonomous' })` 都能建**无证据的自主 Goal**
- `setGoal` 同理
- **B3 的证据校验只保护 `createAutonomousGoal` 这一个入口**

**当前生产调用点**：

```
state.js:1184  createAutonomousGoal 内部（有校验）✅
state.js:1201  setGoal 内部（无校验）⚠
```

**但**：`plugins/autonomous/index.js` **已经不调 `setGoal` 了**（止血提交删掉），所以**现在是安全的**。

**风险**：B5 或未来代码如果调 `setGoal` / `createGoal` 就绕过。

**建议（不实施）**：

- 方案 A：`createGoal` 加参数 `{ evidence }`，`source === 'autonomous'` 时**强制**校验
- 方案 B：把 `createGoal` 改成内部函数，只导出 `createAutonomousGoal`（需证据）和 `createUserGoal`（不需要）

### P2-1：`validateGoalEvidence` 和 `createGoal` 不在同一个锁内

**代码**：

```js
export function createAutonomousGoal({ text, evidence, knownRounds }) {
  const v = validateGoalEvidence(...);    // ← 无锁，只读
  if (!v.ok) return ...;
  const r = createGoal({ text, source: 'autonomous' });   // ← 自己一次锁
}
```

**影响**：

- 证据校验和写入之间有一个时间窗
- 如果 `autonomous.json` 在这期间被改（比如归档删除了某个 Round），校验会通过但 Round 已经不在了

**实际风险**：低（`autonomous.json` 的 history 不会频繁删）。

**但**：**这不是"原子边界"**——机主问的这个点答案是"**不在同一锁**"。

### P2-2：并发 `createAutonomousGoal` 的理论风险

**场景**：两个进程同时用**同一份证据**创建**同一文本**的 Goal。

**结果**：`createGoal` 有同文本去重 → **只有一个会创建**（`created: true`），另一个 `created: false`。

**所以**：**不会重复创建** ✅

**但**：两个进程都会**通过证据校验**（校验无锁）→ **两个都"认为"自己合法**。

**影响**：只是返回值的 `created` 不同，**没有数据损坏**。

### P2-3：Action 写入失败可能留下孤立 Pending

**场景**：

```
AddCompanionPending 成功 → Pending 写入文件
但 rec.actions 最终没写进 autonomous.json（finish 时异常）
```

**结果**：有一个 Pending，但**没有 Action 指向它**（`pendingId` 悬空）。

**影响**：低（Pending 本身是有效的，只是追溯链断了）。

**现状**：`finish` 在 `finally` 里保证写，异常概率极低。

### P2-4：prompt 仍可能让模型每个 Action 都填 `next`

**现状**：`next` 的说明是"下次从哪继续，一句话"——**没有说"可以不填"**。

**结果**：模型可能每个 Action 都填 `next` → 每个 Action 都建 Pending。

**这是真实风险**：`pending` 已经有 10 条了（4 pending / 5 done / 1 waiting）。

**但**：`addPending` 有同文本去重，且上限 20 条。

**建议（不实施）**：prompt 里加"没有明确的后续就不填 next"——**但预算不允许**。

### P2-5：`fitToBudget` 可能截断候选内容

**现状**：900 tokens 时只给 3 个候选（每个的摘要可能也被截短）。

**影响**：**候选看得少** → 她可能漏掉有价值的内容。

**但**：这是**原有设计**（不是 B4 引入的），B4 只是让它更紧了一点。

### 5.1 必须遵守

1. **只能用 `createAutonomousGoal`**，不能用 `createGoal` / `setGoal`
2. **证据必须来自真实的 Round**（`history[].roundId`）
3. **至少 2 个不同 Round**

### 5.2 建议的实现位置

**在 `rec.actions` 循环之后**（一轮活动结束时）：
- 汇总本轮的所有 Action
- 判断是否形成"长期方向候选"
- 带证据调 `createAutonomousGoal`

**不要在单个 Action 之后** —— 那会重蹈"一个动作一个 Goal"的覆辙。

### 5.3 必须记录

- `created: true` 时 log 一行（哪个 Goal、什么证据）
- `code` 非空时 warn（但不阻断）
