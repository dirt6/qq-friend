## 三、四个新接口的建议签名和行为

### 3.1 `createGoal`

```js
export function createGoal({ text, source = 'autonomous', reason = '' } = {})
// → { ok: true, goal, created: boolean } | { ok: false, error }
```

**行为**：

| 情况 | 处理 |
|---|---|
| 已有**相同文本的 active** | **不新建**，返回已有那条（`created: false`） |
| 已有**相同文本的 paused** | **恢复它**（paused → active），不新建 |
| 已有**相同文本的终态**（completed / cancelled / superseded） | **新建**（那是一次旧的结束，现在重新开始） |
| 有别的 active | 旧的转 `paused`，带 history |
| 没有 active | 直接建 |

**校验**：
- `text` 非空、≤ 200 字
- `source` 必须是 `autonomous` / `user_directed`
- `reason` 可选

---

### 3.2 `updateGoal`

```js
export function updateGoal(id, { text, reason = '', by = 'unknown' } = {})
// → { ok: true, goal } | { ok: false, error }
```

**行为**：

| 情况 | 处理 |
|---|---|
| 找不到 id | 报错 `没有这条 Goal` |
| `text` 为空 | 报错 |
| 改成和**别的 goal 相同**的文本 | **拒绝**（避免重复方向） |
| 正常 | 只改 `text` + `updatedAt`，**不动状态** |

**关键**：`updateGoal` **不改变 status**。想改状态用 `pauseGoal` / `resumeGoal`（以及 2.6.3 的完成/取消）。

**为什么不做"文本相同就跳过"**：更新时如果传了相同的文本，直接返回成功（幂等），不写盘。

---

### 3.3 `pauseGoal`

```js
export function pauseGoal(id, { reason = '', by = 'unknown' } = {})
// → { ok: true, goal } | { ok: false, error }
```

**行为**：

| 情况 | 处理 |
|---|---|
| 找不到 id | 报错 |
| 已经是 paused | **幂等返回**（不重复写 history） |
| 是终态 | 报错 `终态不能再暂停` |
| active | → paused，写 history |

**校验**：`canTransition(current, 'paused')`

---

### 3.4 `resumeGoal`

```js
export function resumeGoal(id, { reason = '', by = 'unknown' } = {})
// → { ok: true, goal, pausedPrevious: string|null } | { ok: false, error }
```

**行为**：

| 情况 | 处理 |
|---|---|
| 找不到 id | 报错 |
| 已经是 active | **幂等返回** |
| 是终态 | 报错 |
| **有别的 active** | 那个转 paused（带 history），**这条**转 active |
| 没有 active | 直接转 active |

**关键**：**同一时间只能有一个 active**，恢复时自动处理冲突。

## 四、新旧接口兼容方案

### 4.1 `setGoal` 改为薄封装

```js
export function setGoal(text, { source = 'unknown' } = {}) {
  // 2.6.2：内部改用 createGoal / updateGoal，不再自己写一段逻辑
  const r = createGoal({ text, source, reason: '' });
  if (r.ok) return { ok: true, goal: r.goal };
  return r;
}
```

**行为等价性**：

| 场景 | 2.6.1 `setGoal` | 2.6.2 `setGoal`（走 createGoal） |
|---|---|---|
| 相同文本 active | 只更新 `updatedAt` | **一样**（`created: false`，只更新） |
| 新文本 | 旧转 paused + 新建 | **一样** |
| 相同文本 paused | 旧转 paused + **新建** | **恢复那条** ← **行为变了** |

**行为变化**：从"新建"变成"恢复"。

**判断**：这是**改进**（不重复建）。但要**在提交信息里明确写出**，并加测试。

### 4.2 `clearGoal` 不动

保持 2.6.1 的行为（转 completed），**已标 @deprecated**。2.6.3 用 `completeGoal` / `cancelGoal` 取代。

### 4.3 旧数据兼容

`normalizeGoals` 不变，旧文件读出来的 goal 仍然是 `status: 'active'`，可以直接被 `pauseGoal` / `updateGoal` 操作（id 是 `g-legacy-1`）。

## 五、当前并发写入机制，能否保护 read-modify-write

### 5.1 机制

```
updateCompanion(fn)
  └─ withState(file, mutator, { fallback })
       └─ withStateOnce: withFileLock(file, () => { 读 → fn → 写 })
            └─ withFileLock: 跨进程文件锁（*.lock + 退避重试 1500×20ms）
                 · 锁内：readFileSync → JSON.parse → fn(cur) → writeFileAtomic
                 · writeFileAtomic: 临时文件 + rename（带 EPERM 退避）
```

### 5.2 能保护 read-modify-write 吗

**能。**

- `fn(cur)` **在锁内**执行
- `cur` 是**锁内刚读出来的**最新内容
- 写完才释放锁

**所以**：两个进程同时 `createGoal`，第二个会等锁，拿到锁后读到第一个的写入 → 不会丢更新。

### 5.3 一个要注意的点

`updateCompanion` 里：

```js
if (!Array.isArray(cur.goals)) cur.goals = normalizeGoals(cur);
```

**这行在锁内**，所以旧格式归一化也是原子的 ✅

**但**：`normalizeGoals(cur)` 返回**新数组**，`cur.goal` 旧字段**仍在** → 下次读优先 `goals` ✅（不冲突）

### 5.4 结论

**并发机制够用，不需要新增锁**。

**测试要验证**：两个子进程各 `createGoal` 5 次（不同文本）→ 15 条 goal 一条不丢。
