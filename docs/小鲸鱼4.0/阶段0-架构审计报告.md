## 0. 结论摘要

1. **4.0 的方向成立，但原方案对现状有两处关键假设不成立**：
   - 自主活动**没有 DSH Session**，它直接调 `src/llm.js` 的 `chatCompletion`；
   - DSH 不是常驻会话，而是**每轮 spawn 一个 `dsh --profile headless` 子进程**，靠 `--session-id` 恢复。
2. **记忆不是"分散"，而是"分散 + 多写入口"**：日记有三处写入（diary 技能、autonomous 插件、qq-tools → orchestrator），经验/印象/活动/会话各有自己的文件与写者。
3. **最大的架构风险不是缺 Memory Hub，而是缺"单一写者 + 事件"**：`autonomous.json`、`learned.json`、日记、`data/sessions/` 都是"读-改-写整个文件"，没有跨进程锁。
4. **Token 账本已经分裂成三份**：QQ-agent 主账本（`data/usage-days/`、`data/token-usage.json`）、自主活动自己的账本（`plugins/autonomous/lib/usage.js`）、DSH 返回的 usage（经 orchestrator 并回主账本）。
5. **DSH 多 Session 能力静态上成立、并发上未验证**：同一 DSH_HOME 下已有 11 个历史会话；不同 chatKey 在 gateway 层串行队列，但跨进程并发打开不同会话、profile 加载、projcache 竞争都还没有实测证据。

因此：**阶段 0 的交付不是"确认方案"，而是把方案里几处要改的假设标出来**（见第 6 节差异表），并给出修订后的顺序（见第 9 节）。

关键事实：

- DSH 调用参数：`--profile headless --patch <persona> --patch <qq-tools> --json [--session-id <sid>] -`（`src/dsh-gateway.js:503-514`），正文走 **stdin**，因为 cmd 会丢 UTF-8 参数。
- 会话映射：`data/dsh-sessions.json`，当前只有 1 个 key（`private:1846383180`），717 turns，session 自 2026-10-24 起复用。
- DSH 数据隔离：`DSH_HOME=data/dsh-home`（29.5 MB、11 个会话），与桌面 DSH 的 `~/.dsh` 完全分开。
- 自主活动：`plugins/autonomous/index.js` 直接 `llm.chatCompletion`（`plugins/autonomous/index.js:641`），每轮 2~6 次模型调用（intent / decision / diary review / reflection）。

- 面板：`scripts/web-panel-server.mjs`（127.0.0.1:8899），13 个 GET API + 18 个 POST action，只读/写 data 文件，不参与决策。

## 2. 两条完整调用链

### 2.1 聊天（当前 DSH 路径）

```
QQ 消息
 → onebot.js（OneBot 事件）
 → orchestrator（触发判定 / 组批 / 会话状态）
 → #askDsh（orchestrator.js:893）
    · 只取用户本轮消息（图片转本地路径）
    · 时钟行 + 多连发系统注记
    · cold 时 preface = 人设 + 历史（buildDshPreface）
    · proactiveNote = 她主动说过的话 + autonomous 最近活动摘要
 → dsh-gateway.ask（withQueue 串行，按 chatKey）
 → spawn cmd /c dsh --profile headless ... --json [--session-id] -
 → stdout NDJSON：session / final / status(usage)
 → 进程退出码 0 且有 final 才算成功
 → drainOutbox(callId)：贴纸 / 图片 / 工具 / 日记
 → orchestrator 转成 tool_calls，交给 QQ-agent 的工具执行层
 → sender.js 真正发到 QQ
```

失败语义：`dsh-gateway` 返回 `{ok:false}`，orchestrator 返回 `null`，`#runAgent` 回落旧 API（`src/orchestrator.js:1482` 附近）。**日志里 892 次调用 769 OK / 30 FAIL，FAIL 集中在 2026-10-24 的 cordis 错误。**

### 2.2 自主活动（当前 API 路径）

```
定时器 / selfWake
 → plugins/autonomous/index.js runSession
 → decideIntent（lib/intent.js，1 次模型调用）
 → 抓取候选（B站/小黑盒，不耗 token）
 → decideOnce（lib/planner.js，1~N 次模型调用）
 → executeAction：
      share / chat / draw / comment / publish / search / think / diary
 → maybeShare → 经过 QQ-agent 的发送能力（live）或只记录（quiet/dryRun）
 → 写 autonomous.json（history/actions/currentGoal/pendingNextStep）
 → 写 autonomous-log.md
 → 写日记（appendDiaryLine）
```

**它完全不经过 DSH**，没有 Session，没有 DSH 工具，也看不到聊天上下文——这就是"两套脑子"的代码来源。

## 4. 模型调用入口与 Token 统计

| 调用方 | 入口 | 是否经过 DSH | 记账 |
|---|---|---|---|
| 聊天主路径 | `dsh-gateway.ask` → headless 子进程 | 是 | DSH `status.usage` → orchestrator 转 OpenAI 口径 → session.usage → `usage-days` |

## 5. DSH 多 Session 能力：静态结论与未验证项

**已验证（静态 + 现有日志）**：

- headless profile 存在且被实际使用：`data/dsh-home/profiles/headless/{cordis.yml,cordis.patch.yml,package.json}`；
- 会话可创建、可恢复：`data/dsh-home/sessions/` 下有 11 个 `session-*` 目录，当前映射 1 个；
- 同一 chatKey 串行：`dsh-gateway` 的 `withQueue`（`src/dsh-gateway.js:211-217`）；
- 不同 chatKey 可映射不同 session（结构上支持，当前只用了 1 个）；
- 失败可观测：`data/dsh-gateway.log` 892 行，769 OK / 30 FAIL，FAIL 有明确退出码与 stderr。

**未验证（阶段 3 必须实测，本阶段按约束不做）**：

1. 同一 DSH_HOME 下，两个不同 session 的**并发子进程**是否稳定（文件锁、projcache、attachments 竞争）；
2. 同一 session 被两个进程同时打开时的拒绝语义（现有证据：桌面端与 headless 共用 `~/.dsh` 时曾出现 `CreateSemaphoreW EACCES`、`owned by an active write handle`，见 `src/dsh-gateway.js:84-91` 注释）；
3. 长会话（当前 717 turns）在新进程里恢复的耗时与内存；
4. 多 session 并发时的 token 账本归属；
5. DSH 会话被外部删除/损坏后的恢复行为。

**结论**：可以按"每个逻辑会话一个 session"设计，但阶段 3 必须先做并发实测，再迁移自主活动。

## 6. 与原方案的差异（必须修订的地方）

| 原方案假设 | 实际情况 | 修订建议 |
|---|---|---|
| Chat Session 与 Autonomous Session 都是 DSH Session | 自主活动没有 Session，直连 `llm.chatCompletion` | 阶段 3 先建 autonomous session，再做迁移；不要在阶段 1/2 假装它已存在 |
| DSH 是常驻会话 | 每轮 spawn 一个 headless 子进程，冷启动 ~3-5 s | 统一调用后，自主活动每轮 2~6 次调用会放大延迟；需要批量/常驻方案或接受成本 |
| 两个 Session 独立但不是两个 AI | 现在就是两个 AI（两套 prompt、两套记忆读取、两套 token） | 阶段 1 先统一"状态与事件"，阶段 2 统一记忆读取，阶段 3 再统一模型入口 |
| 事件实时同步 | 没有事件总线和事件日志；靠每轮 hotNote 补丁 + 读日记 | 阶段 1 新增事件日志，**聊天侧发布事件**是前置条件 |
| Companion State 是新增 | `autonomous.json` 已有 currentGoal/pendingNextStep/selfWake | 不要新增第二套；把 companion-state 设计成 autonomous.json 的**受控投影**，或迁移字段并保留旧文件只读 |
| Memory Hub 统一读写 | 日记三处写、经验/印象/活动各写各的 | 阶段 2 先统一**写入口**（一个 writer），再谈检索 |
| 影子测试不影响生产 | DSH 工具会真实执行（qq_tool 可能发消息/评论/发帖） | 阶段 3 必须先加 dry-run/影子开关，否则"只记录不执行"做不到 |
| Token 统一统计 | 主账本 + 自主账本分裂 | 阶段 1 就把 autonomous usage 并入主账本（或建立统一账本接口） |
| 阶段 0 不调真实模型即可完成 | 多 Session 并发必须实测 | 阶段 0 输出"静态审计 + 待实测清单"；并发验证放到阶段 3.1 |

## 9. 修订后的迁移顺序

原方案顺序：状态中心 → Memory Hub → 自主活动迁 DSH → 工具权限 → 面板。
修订建议（把"事实修正"和"写入口归一"提前）：

```
阶段 0  审计（本报告）+ 机主确认第 10 节的问题
阶段 1  Companion State + 事件（先做"聊天侧发布事件"）
阶段 1.5 写入口归一：日记/经验/印象/活动都走一个 writer
阶段 2  Memory Hub（读接口 + 检索，写入口已在 1.5 统一）
阶段 3  自主活动迁 DSH（3.1 先做多 session 并发实测）
阶段 4  工具权限统一（模式白名单 + dry-run）
阶段 5  面板状态页 + 事件审计页 + 7 天长跑
```

理由：如果先做 Memory Hub，而不先统一写入口，Hub 只是给三个写者加了一层包装；事件是 Companion State 的输入，没有聊天事件，状态只能靠轮询。

## 10. 需要机主决定的问题

1. **自主活动走 DSH 后，每轮 2~6 次模型调用意味着 2~6 次进程启动（每次约 3~5 s）**：接受延迟，还是要求 DSH 侧提供常驻 session？
2. **Companion State 与 `autonomous.json` 的关系**：迁移字段（旧文件只读），还是双写过渡？
3. **日记写入口**：是否同意先统一到一个 writer（保留 Markdown 与现有目录，不改格式）？
4. **DSH 单会话已 717 turns**：是否需要会话轮换策略（按天数/大小/主题开新会话）？
5. **事件日志保留期**：保留多少天、何时归档、是否允许面板重放？
6. **面板写操作**：当前面板可改 learned/stickers/日记；4.0 是否把它降为只读，写操作只走 Memory Hub？
7. **旧 API 回落**：正式切换后是否允许人工开关回退？默认是否完全禁止静默回落？
