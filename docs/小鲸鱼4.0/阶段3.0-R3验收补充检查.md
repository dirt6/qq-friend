# 一、空文件 append 语义

## 1.1 对应文件和函数

`src/diary/meta.js`

- `appendDiaryEntry(dateKey, { paragraphIndex, contentType, epistemicType, origin, roundId })`
- `splitParagraphs(text)`

## 1.2 现有实现行为

```js
export function appendDiaryEntry(dateKey, { paragraphIndex, ... } = {}) {
  // ① 读原文
  raw = fs.readFileSync(sourceFile(key), 'utf8');
  // ② 切段
  const paras = splitParagraphs(raw);
  // ③ 检查索引
  const idx = Number(paragraphIndex);
  if (!Number.isInteger(idx) || idx < 0 || idx >= paras.length) {
    return { ok: false, error: 'paragraphIndex 越界' };
  }
  ...
}
```

**空文件时**：

| 步骤 | 结果 |
|---|---|
| `raw` | `''` |
| `splitParagraphs('')` | **`[]`（0 段）** |
| `idx = 0` | `0 >= 0` → **越界** |
| 返回 | `{ ok: false, error: 'paragraphIndex 越界' }` |

**所以失败原因是**：**空日记没有任何段落可引用**，不是"接口不支持追加"。

**接口本身的约束**：`paragraphIndex` **必须指向一个已存在的段落**。

# 二、Windows 并发与原子写入

## 2.1 `withFileLock`：是进程内锁还是跨进程锁

**对应**：`src/file-lock.js:42` 的 `withFileLock(file, fn, {...})`

**实现行为**：

```js
const lock = `${file}.lock`;
for (let i = 0; i < retries; i += 1) {
  try {
    fs.writeFileSync(lock, `${process.pid}`, { flag: 'wx' });   // ← 排他创建
  } catch (e) {
    if (e?.code !== 'EEXIST') throw e;
    // 陈旧锁：mtime > staleMs 就删
    if (Date.now() - fs.statSync(lock).mtimeMs > staleMs) { fs.unlinkSync(lock); continue; }
    sleepSync(waitMs);
    continue;
  }
  try { return fn(); } finally { try { fs.unlinkSync(lock); } catch {} }
}
throw ELOCKTIMEOUT;
```

**结论**：**跨进程锁** ✅

- 用**文件系统排他创建**（`flag: 'wx'`）做互斥
- **两个独立 Node.js 进程会争同一个 `.lock` 文件** → 串行
- **不是进程内 mutex**（进程内 mutex 只能防同进程重入）

**参数**：

| 参数 | 默认值 | 效果 |
|---|---|---|
| `retries` | 1500 | 最多试 1500 次 |
| `waitMs` | 20 | 每次等 20ms |
| `staleMs` | 15000 | 锁超过 15s 没释放 → 当陈旧锁删掉 |

**最长等待**：1500 × 20ms = **30 秒**。

## 2.2 两个独立进程同时写同一份元数据：会串行吗

**会** ✅

**链路**：

```
writeDiaryMeta(dateKey, meta)
  → withFileLock(metaFile, () => writeFileAtomic(...))
    → 文件锁（跨进程）
```

**但有一个**（见 2.5）**：锁只保护"写"，**读在锁外**。

```js
// appendDiaryEntry 里
const cur = readDiaryMeta(key);      // ← 读在锁外！
...
const w = writeDiaryMeta(key, meta); // ← 写才加锁
```

**这意味着**：两个进程同时 append 同一段 →
- 都读到旧 meta（entries 空）
- 都算出"不重复"
- 都写入（后写的覆盖前写的）
- **结果：只留下一条**（不是两条，也不是坏的）

**这是"丢失更新"，但不是"数据损坏"**。详见 2.6 的严重度判断。

## 2.3 `writeFileAtomic` 临时文件与目标文件是否同一目录

**对应**：`src/file-lock.js:79` 的 `writeFileAtomic(file, content)`

```js
const tmp = `${file}.${process.pid}.${Date.now()}.tmp`;
fs.writeFileSync(tmp, content, 'utf8');
fs.renameSync(tmp, file);
```

**结论**：**同一目录** ✅

- `tmp` = `${file}.PID.TS.tmp` → **和 `file` 同目录**
- **同目录 `rename` 在 Windows 上是原子的**（跨卷才不原子）

## 2.4 rename 在 Windows 遇到目标文件被占用时如何处理

**实现**：

```js
for (let i = 0; i < 12; i += 1) {
  try { fs.renameSync(tmp, file); return; }
  catch (e) {
    if (e?.code !== 'EPERM' && e?.code !== 'EBUSY' && e?.code !== 'EACCES') throw e;
    sleepSync(15 + i * 10);   // 15, 25, 35, … 125 ms
  }
}
fs.renameSync(tmp, file);   // 最后再试一次，失败就抛
```

**结论**：

- **只重试** `EPERM` / `EBUSY` / `EACCES`（Windows 上文件被占用的典型错误）
- **其他错误直接抛**（不掩盖真实问题）
- 重试退避：15→25→…→125ms（**总共约 840ms**）
- **最后还不行就抛** —— **不静默失败** ✅

**代码里的注释**（2026-11-01 实测经验）：

> Windows 上如果一个进程刚好在读目标文件（或杀毒软件在扫），rename 会抛 EPERM/EBUSY。

## 2.5 写入失败时是否清理临时文件，是否保留原文件

### 部分成功 ✅

| 项 | 行为 |
|---|---|
| **原文件** | **保留** ✅（`rename` 失败 = 原文件没被动） |
| **临时文件** | ❌ **不清理** |

**临时文件泄漏的具体路径**：

```js
for (let i = 0; i < 12; i += 1) {

  catch (e) { ... }

```

**没有 `try/finally` 清理 `tmp`。**

## 2.6 锁释放、异常退出和超时处理是否可靠

| 场景 | 行为 | 评价 |
|---|---|---|
| **正常完成** | `finally { fs.unlinkSync(lock) }` | ✅ |
| **`fn()` 抛异常** | `finally` 仍然执行 | ✅ |
| **进程崩溃** | 锁文件残留 → 下次 `mtime > 15s` 当陈旧锁清掉 | ⚠️ **要等 15 秒** |
| **锁超时** | 抛 `ELOCKTIMEOUT` | ✅ 不静默 |
| **杀毒软件占用 rename** | 重试约 840ms 后抛 | ⚠️ **可能失败** |
| **临时文件泄漏** | 失败时 `.tmp` 留下 | ❌ **没清理** |

## 2.7 未覆盖风险汇总

| # | 风险 | 严重度 | 说明 |
|---|---|---|---|
| **W1** | **`writeFileAtomic` 失败时 `.tmp` 残留** | **中** | 每次失败留一个 `.tmp`（含 pid + 时间戳），长期会累积 |
| **W2** | **`appendDiaryEntry` 的读在锁外** | **中** | 并发 append 会"丢失更新"（不是损坏，是少写） |
| **W3** | **进程崩溃后锁要等 15 秒才释放** | 低 | `staleMs` 的设计权衡（太短会误删正在写的锁） |
| **W4** | **rename 重试总时长只有 ~840ms** | 低 | 杀毒软件扫描时间超过这个就失败 |
| **W5** | **失败路径没有测试** | 中 | 现在只测了成功路径 |

### W2 的严重度判断（要准确）

**并发 append 的实际后果**：

```
进程 A: 读到 entries=[]，算出不重复，写入 entries=[e1]
进程 B: 读到 entries=[]，算出不重复，写入 entries=[e1]   ← 覆盖
结果：entries 只有 1 条，不是 2 条
```

**是"少写一条"，不是"数据损坏"或"文件损坏"。**

**但**：`appendDiaryEntry` 声称"幂等" —— **它只保证"同段不重复"，不保证"并发不丢"**。

**要真正做到并发安全**，需要把**读-改-写整个放进锁里**。

**这正好是 `file-lock.js` 注释里写的那句话**：

> 只在写的时候加锁 = 两个进程各读旧值再互相覆盖（D9 原话：原子写 ≠ 并发安全）。

**`appendDiaryEntry` 恰好犯了这个**。
