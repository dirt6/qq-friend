## 五、潜在兼容风险

### 5.1 `g-legacy-1` 的双重身份

它是**唯一的 `g-legacy-1`**，同时是：
- 旧格式迁移的产物
- 误分类的 chat 动作目标

**处理风险**：如果 2.6.6c 要维护它，要先看它是不是"迁移时那条"。

**建议**：维护时按**文本**识别（"问耳机和今晚睡不睡"），不要按 id 假设。

### 5.2 `completion` 字段是死的

`normalizeGoals` 里 `completion: g.completion ?? null`，但 2.6.3 用的是 `proposal`。

**风险**：如果有旧数据手写了 `completion`，读出来是 `completion` 而不是 `proposal`。

**现状**：生产数据 `completion: null`，没风险。

**建议**：2.6.6 时清理这个字段（或明确标 deprecated）。

### 5.3 `decision.goal` 的历史记录

旧 `history[].actions[].goal` 记录的是 **Action Objective**（语义正确）。

**但** 2.4/2.5 时它被写进 Companion Goal。

**风险**：如果 2.6.6c 要追溯"哪些 Goal 是误创建的"，不能只看 `goal` 字段，要看创建时间对应的 Round。

**建议**：按 `since` 时间匹配 `history[].startedAt`。

### 5.4 `pending` 的 `expiresAt`

现在的 `addPending` 默认 30 天过期，**但 `expiredPending()` 没人调用**（只导出）。

**风险**：Pending 会一直累积（上限 20 条）。

**建议**：2.6.6a 时加惰性清理（和 Goal 的 proposal 一样）。

### 5.5 `history` 的扁平化字段

`round` 层有 `action` / `goal` / `why` / `next` / `chat` 等**第一件事的快照**。

**风险**：如果改这些字段的语义，旧数据会被误读。

**建议**：**不动这些字段**，A3 只在 `actions[]` 里操作。

```
id: g-legacy-1
```

## 九、要你确认的

### ① 是否现在加 `pendingId` / `goalId`

这两个关联字段是 A3 要求的，但**没有它们系统也能跑**。

**加的好处**：能追溯"这个 Pending 是从哪个 Action 来的"、"这个 Pending 属于哪个 Goal"。

**加的代价**：数据结构变更 + 兼容处理。

**我建议**：**B1 加 `pendingId`**（Action → Pending 的追溯价值高），
**`goalId` 暂时不加**（现在没有真正的 Goal 需要关联）。

### ② `completion` 死字段怎么处理
