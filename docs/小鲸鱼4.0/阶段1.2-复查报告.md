## 一、预算闸门是否真正统一

### 发现：按「聊天+自主合计」卡 5 元预算，她会永久不醒

第一版实现让 `budgetGate` 用 `readMonth().total.cost`（合计）判断，实测：

```
聊天侧  19 天 $20.35
自主侧  $0.39
合计    $20.74  vs  预算 ¥5   →  超支 4 倍
```

**那 5 元本来是 `plugins/autonomous` 自己的配置**（`settings.monthlyBudgetYuan`），
聊天从来没被这 5 元约束过。合并之后她第一次醒来就会吃一个"超支"、再也不醒。

这是**破坏性改动**，必须回滚语义。

### 修复：三层预算，主限制仍是自主自己

| 层 | 字段 | 默认 | 作用 |
|---|---|---|---|
| 1 | `monthlyBudgetYuan` | **5** | 自主自己的月度预算（行为与 2.x 一致） |
| 2 | `monthlyTokenCap` | **800 万**（只看自主自己的 token） | 成本算不准时的兜底 |
| 3 | `totalBudgetYuan` | **0 = 关** | 开了才是"聊天和自主抢同一笔钱" |

场景验证（真实数据：自主 ¥0.39 / 16.6 万 tokens）：

| 场景 | 判定 |
|---|---|
| 当前状态 | 继续 ✓ |
| 自主花掉 5 元 | 停：自主超预算 |
| 自主 token 超 800 万 | 停：自主 token 兜底 |
| 开总预算 25 元 | 继续 ✓ |
| 开总预算 5 元 | 停：总预算 |

### 逐条回答

| 检查项 | 结论 |
|---|---|
| 聊天费用增加 → 自主额度减少 | **默认不生效**，要开 `totalBudgetYuan` 才生效。默认语义是"自主只管自己"，否则 20 元聊天会让 5 元预算永远爆 |
| 自主费用增加 → 聊天侧统计可见 | ✅ `readMonth()` 合并视图同时给出 chat/autonomous/total，面板可用 |
| 月份切换不重复累计 | ✅ 按 `monthKey` 前缀过滤日文件；`monthKeyOf` 用本地时区 |
| 多进程同时记账不丢 | ✅ **已补跨进程锁**（见下） |

### 跨进程锁（补充实现）

第一版只有进程内 Promise 队列，且**锁的范围是错的**——只锁了写，读在锁外，
等于"两个进程各读旧值再互相覆盖"（D9 原话：原子写 ≠ 并发安全）。

现在：`withFileLock(AUTONOMOUS_FILE, () => { 读 → 改 → 原子写 })`，
独占创建 `.lock`，退避重试，**超过 5 秒视为崩溃残留自动清掉**。

实测（`test/token-ledger-concurrent-test.mjs`）：两个真实子进程各记 50 笔 →
**总数 100，一笔不丢**；残留锁与陈旧锁都验证过。

## 二、成本未知时的预算行为

### 原实现的问题

```js
const spent = Number(m.total.cost) || 0;   // null → 0
```

聊天侧当天只有 `usage-today.json`（**不含成本**），`total.cost` 会是 `null`，
被 `|| 0` 当成零成本 —— 等于"算不出来就当没花钱"，会无限调用。

### 现在的口径

1. **自主成本永远算得准**（自己记账，输入/输出 token × 单价），所以自主预算不受影响；
2. 合计成本不可靠时，`readDay()` 返回 `cost: null` + `costAccurate: false`，
   **不拿单价硬估**（宁可说"未知"也不给假精确）；
3. **Token 兜底独立存在**：`monthlyTokenCap` 只看自主自己的 token，
   成本口径失效时仍然能拦住无限调用。

### 一个踩过的坑：兜底口径不能算总量

第一版 `monthlyTokenCap` 用**聊天+自主总 token**，实测：

```
本月总 token 6054 万（聊天 6000 万 + 自主 16 万） > 兜底 800 万  →  判停
```

聊天一个月 6000 万 tokens 是常态，拿总量兜底等于永久锁死。
**已改成只看自主自己的 token**。

## 三、旧账本迁移

### 现状：没有物理迁移，做的是"统一读 + 单写者"

| 问题 | 结论 |
|---|---|
| 旧 `token-usage.json` 是否完整迁移 | **没有迁移，也不需要迁移**。它仍是自主活动的唯一真源，`src/token-ledger.js` 负责读写它；主账本（`usage-days/`）只做合并读取 |
| 历史数据有没有重复计入 | **没有**。聊天成本只从 `usage-days/` 来，自主成本只从 `token-usage.json` 来，两边的日期维度互斥 |
| 新旧账本切换期间有没有漏记 | **不会**。改造前后写的是同一个文件、同一套格式（`{version,monthKey,budgetYuan,days}`），只是写入入口从 `usage.js` 的 read-modify-write 换成了 `recordAutonomousCall` |
| 旧账本是否只读保留、避免两处继续写 | **不是只读**，但它变成**单写者**：只有 `recordAutonomousCall` 写。`lib/usage.js` 保留纯函数（计算/格式化/闸门工具），不再自己落盘 |

### 一个需要记住的现象：`usage-days` 是按需重算的

```
10-31 之前 usage-days 只到 10-24（7 天没更新）
调用一次 /api/usage/stats?range=30 后，立刻补齐到 10-30
```

原因：日文件只在面板用量页被访问时重算落盘。

**影响**：`readMonth()` 读的是日文件，**长时间不开面板就会少算**。
当前实现已经会如实反映（少算就是少算，不编），但这对"月度预算"是个隐患。

**建议**（未实施，等机主决定）：
- 在 app 启动后 + 每天零点各触发一次 `buildUsageStats({range:'2'})`；
- 或者 `budgetGate` 发现最新日文件落后超过 2 天时，降级为"只用自主账本判断"。
