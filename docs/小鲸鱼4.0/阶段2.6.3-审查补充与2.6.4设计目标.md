## 一、你问的原子性：**通过**

### 1.1 `yes` 的确认和状态转换在同一个锁内

```js
export function answerConfirmation(id, { answer, quote = '' } = {}) {
  const r = updateCompanion((st) => {
    ...
    // ④ 正常记录回答
    g.proposal.answer = ans;
    g.proposal.answerAt = nowIso();
    g.proposal.answerQuote = String(quote || '').slice(0, 100);

    // yes → 执行（**同一个 fn 里**）
    const res = applyEnd(g, kind, { by: 'owner', reason: '老大确认：' + ans });
    ...
  });
}
```

### 1.2 `applyEnd` 不嵌套调用 `updateCompanion`

```js
function applyEnd(g, kind, { by, reason }) {
  // 直接改 g，不调 updateCompanion
  transition(g, target, { by, reason });
  g.proposal = null;
  return { ok: true };
}
```

**验证结果**：`applyEnd` 里**没有** `updateCompanion(` 调用 ✅

**所以**：`yes` 的"写 answer"和"转状态"是**一次写盘**完成的，不会有"先写确认、再调另一个接口"的问题。

## 二、但发现一个边界：`applyEnd` 失败时 `answer` 会残留

### 2.1 复现

```js
const g = cs.createGoal({ text: '边界探针', source: 'user_directed' }).goal;
cs.proposeCompletion(g.id, { kind: 'complete' });
cs.markConfirmationAsked(g.id, { roundId: 'r1' });

// 模拟并发：老大答 yes 之前，goal 被别处 paused 了
st.goals.find(x => x.id === g.id).status = 'paused';
fs.writeFileSync(CS, JSON.stringify(st), 'utf8');

const r = cs.answerConfirmation(g.id, { answer: 'yes', quote: '好' });
```

**结果**：

```
返回: {"ok":false,"error":"不允许从 paused 转到 completed","code":"INVALID_TRANSITION"}

状态: paused（正确，没变）
proposal 还在: true
proposal.answer: "yes"          ← ⚠ 被写进去了
proposal.answerAt: "2026-11-01T11:48:03.171Z"
```

### 2.2 为什么会这样

`answerConfirmation` 的 `fn` 里：

```js
// ④ 先写 answer
g.proposal.answer = ans;
g.proposal.answerAt = nowIso();
g.proposal.answerQuote = ...;

// yes → 执行
const res = applyEnd(g, kind, {...});
if (!res.ok) { err = res; return; }   // ← err 设置了，但 fn 正常返回
```

**关键**：`fn` **没有抛错**（只是设置了 `err` 变量）→ `updateCompanion` 认为成功 → **写盘** → `answer = 'yes'` 被持久化。

### 2.3 影响

**后果**：留下"已确认、但未执行"的中间状态。

**具体风险**：

1. **下次 `completeGoal` 会拿这个 yes 执行** —— 但那时候状态可能已经允许了（比如被 `resumeGoal` 恢复成 active），于是**一个过期的确认会被当作有效**
2. **`answer = 'yes'` 但状态没变** —— 如果老大之后问"我确认过了吗"，记录会说他确认了，但事没做

**严重度**：**中**。需要并发才能触发（`answerConfirmation` 和另一个改状态的操作同时发生），但一旦触发，语义就错了。

### 2.4 最小修复建议（不实施）

**方案 A（推荐）：先执行，成功了再写 answer**

```js
// 不预写 answer
const res = applyEnd(g, kind, { by: 'owner', reason: '老大确认' });
if (!res.ok) { err = res; return; }   // ← 失败时 answer 还没动

// 成功后才把审计信息写进 history
// （applyEnd 已经清了 proposal，所以 answer 写到 reason 里）
```

**但**：`applyEnd` 里 `transition(g, target, { by: 'owner', reason })` 的 `reason` 可以带上原话：

```js
reason: `老大确认过了（${ans}${quote ? '：' + quote.slice(0, 50) : ''}）`
```

**这样**：审计信息在 `history.reason` 里，不在 `proposal` 里。

**方案 B：失败时回滚**

```js
g.proposal.answer = ans;
const res = applyEnd(...);
if (!res.ok) {
  g.proposal.answer = '';        // 回滚
  g.proposal.answerAt = null;
  g.proposal.answerQuote = '';
  err = res; return;
}
```

**方案 A 更干净**（不写预状态就不会有残留）。

## 三、`clearGoal` 的日志去重（你提的第一个细节）

**确认**：

```js
const lastClearGoalFail = new Map();
const MAX_CLEAR_FAIL_KEYS = 50;

function logClearGoalFailure(goalId, code, operation, source) {
  const key = `${goalId}:${code}`;
  if (lastClearGoalFail.has(key)) return;
  if (lastClearGoalFail.size >= MAX_CLEAR_FAIL_KEYS) {
    const first = lastClearGoalFail.keys().next().value;   // Map 保留插入顺序
    if (first) lastClearGoalFail.delete(first);
  }
  lastClearGoalFail.set(key, Date.now());
  ...
}
```

**你问的**："容量淘汰不会影响业务逻辑"

**确认**：**不影响**。

- `Map` 只用于日志去重
- 淘汰只导致"同一个错误可能再记一次"
- **不碰 Goal 状态、不碰 proposal、不碰任何业务数据**

**`Map` 保留插入顺序** ✅（`keys().next().value` 是最早插入的）。

## 四、2.6.4 的设计目标（按你的原则）

### 4.1 你定的原则

| # | 原则 |
|---|---|
| 1 | 同时最多一个 active |
| 2 | 最多三个 paused |
| 3 | **不自动删除有效的 `user_directed` Goal** |
| 4 | **新的 `user_directed` 不能挤掉旧的 `user_directed`**；容量不足时**请求老大决定** |
| 5 | `autonomous` 可以按价值和来源优先级淘汰，但**不能把淘汰伪装成用户确认过的 `superseded`** |
| 6 | **重复 Goal 识别不能仅靠文本完全相等** |

### 4.2 最核心的问题

> **容量满了以后，系统有没有权力替用户决定放弃哪个目标？**

**我的判断：没有。**

**理由**：

- `user_directed` 是**老大的明确承诺**，系统无权替他决定"哪个不重要"
- 容量上限是**系统资源约束**，不是**业务优先级**

### 4.3 三个候选方案

**方案 A：硬拒绝**

```
容量满 + 新的 user_directed → 拒绝创建，返回 CAPACITY_FULL
                            → 告诉老大"已经记了 3 件事，要不要先放下一件？"
```

**优点**：简单、不会误删
**缺点**：老大说"这个也记着"时，她只能回答"记不下了"

**方案 B：软限制（允许超出，但标记）**

```
容量满 → 允许创建，但状态里标 overCapacity: true
       → 不删任何东西
       → 面板/聊天里提醒"当前记了 4 件事"
```

**优点**：不会丢任何承诺
**缺点**：上限形同虚设

**方案 C：硬拒绝 + 提议（我倾向）**

```
容量满 + 新的 user_directed
  → 拒绝创建（CAPACITY_FULL）
  → **同时生成一个"想记这件事"的 proposal**（kind: 'replace'）
  → 下次聊天时问她该放哪个（2.6.7 才接聊天）
  → 老大决定后，才真的创建
```

**优点**：既不误删，也不丢承诺
**缺点**：要引入新的 proposal kind（`replace`），复杂度上升

### 4.4 `autonomous` 的淘汰

**你的原则 5**：可以按价值淘汰，但**不能伪装成 superseded**。

**我的理解**：

- 淘汰 = **从 paused 列表里移除**（不是转 superseded）
- 或者 = 转 `superseded`，但 `reason` 必须写清"因为容量限制被淘汰"，**不能写"被新方向取代"**

**建议**：**淘汰 ≠ superseded**。

淘汰应该是：

```js
{
  status: 'superseded',      // 状态上确实是"不再跟了"
  reason: '因为容量限制被淘汰（不是被新方向取代）',
  history: [{ from: 'paused', to: 'superseded', by: 'capacity', reason: '...' }]
}
```

**`by: 'capacity'`** 和 `by: 'autonomous'` 区分开 → 审计时能看出"这是系统淘汰的，不是她自己判断的"。

### 4.5 重复 Goal 识别

**你的原则 6**：不能仅靠文本完全相等。

**问题**：怎么判断"语义相同"？

**选项**：

| 方案 | 做法 | 风险 |
|---|---|---|
| A | 归一化后比较（去空格、标点、统一大小写） | 只能处理表面差异 |
| B | 关键词提取 + 集合相似度（Jaccard） | 阈值难定，容易误判 |
| C | **让模型判断**（提议时带"是否和已有重复"） | 多一次调用，但准确 |
| D | **不做自动识别**，只在文本高度相似（编辑距离 < N）时提示 | 最保守 |

**我倾向 D + C 的组合**：

- 程序做**编辑距离**检查（成本低，能抓"差几个字"的）
- 相似度高时**不自动合并**，而是**记一个提示**，由模型在下次决策时判断

**但这要等 2.6.7 接聊天才有意义。**

**2.6.4 先做**：
- `findSimilarGoals(text)` 返回相似度高的（编辑距离 / 关键片段包含）
- **不自动做任何事**，只提供这个查询
