## 四、`writeState` 的真实并发语义（关键）

### 4.1 它**不是**简单覆盖

```js
export function writeState(file, state) {
  ...
  const r = withState(file, (cur) => {
    const curV = Number(cur._v) || 0;
    const myV = Number(state._v) || 0;
    if (curV > myV) {                       // 期间有人写过
      const base = state.__base ? JSON.parse(state.__base) : null;
      if (base) {
        for (const k of Object.keys(state)) {
          if (k === '_v' || k === '_updatedAt' || k === '__base') continue;
          const now = JSON.stringify(state[k]);
          const was = JSON.stringify(base[k]);
          if (now === was) continue;        // **本轮没碰这个字段 → 保留锁内别人写的**
          cur[k] = state[k];
        }
      } else {
        Object.assign(cur, state);          // 没有基线 → 整体覆盖
      }
      // 增量字段始终合并（"只增不减"的账）
      cur.seen = mergedSeen;
      cur.history = mergeByKey(cur.history, state.history, 'startedAt');
      cur.shares = mergeByKey(cur.shares, state.shares, 'at');
    } else {
      Object.assign(cur, state);
    }
  }, { fallback: state });
}
```

### 4.2 `__base` 是**一定**有的

```js
export function readState(file, ...) {
  const st = readStateInner(file, ...);
  // 4.0 / 1.5.3 验收修：记一份"读的时候长什么样"，writeState 用它做字段级 diff。
  // 不这样做的话，后写的进程会用自己那份旧快照把别人刚改的标量覆盖掉
  // （2026-11-01 验收实测：面板写的 pendingNextStep 被自主活动覆盖成空）。
  Object.defineProperty(st, '__base', { value: JSON.stringify(st), ... });
  return st;
}
```

**所以**：**只要是从 `readState` 拿的 `st`，写盘就走字段级 diff**。

### 4.3 结论：Judge 的异步写盘**是安全的**

```js
writeState(STORE, st);                                  // finish
judgeGoalCandidate(...).then(() => writeState(STORE, st));   // 异步
```

**Judge 的 `st` 是旧快照，但它只改了**：
- `st.goalJudgeLog`
- `st.goalJudgeCount`

**其余字段 `now === was`** → **不覆盖** → **保留锁内别人写的** ✅

**所以**：
- `st.digests` 不会被 Judge 的旧快照覆盖 ✅
- 下一轮写的 `history` 不会被 Judge 覆盖 ✅（除了 `mergeByKey` 的问题）

## 五、真实缺口（只有两个）

### 缺口 1：`history` 的合并 key 用 `startedAt`（**P1**）

```js
cur.history = mergeByKey(cur.history, state.history, 'startedAt');
```

```js
function mergeByKey(a, b, key) {
  const k = String(item?.[key] ?? '');
  if (k && seen.has(k)) continue;   // 同 key 去重
  if (k) seen.add(k);
  out.push(item);                    // 空 key 全部保留
}
```

**问题**：两轮并发的 `startedAt` **可能是同一毫秒**（`Date.now()` 精度）→ **被当成同一条 → 丢一个**。

**实测**（探针）：

```
history 轮数: 1                     ← 只留下 1 条
调用记录: 4 条
  autonomous.intent  round-0f9fde0d
  autonomous.intent  round-e073c30f   ← 这轮的 history 丢了
  autonomous.decision round-e073c30f
  autonomous.decision round-0f9fde0d
```

**两个 roundId 都真的跑了，但 history 只留了 1 条** → 印证。

**为什么会同毫秒**：`runSession({ nowTs = Date.now() })`，两个并发调用几乎同时进入。

**修复方向**（不实施，只列）：

| 方案 | 做法 | 风险 |
|---|---|---|
| **A** | `mergeByKey(..., 'roundId')` | 旧 history 14 轮没有 `roundId`（39 里 15 有）→ 空 key 会全部保留，可能重复 |
| **B** | 双 key：`roundId \|\| startedAt` | 需要改 `mergeByKey` 支持函数 key |
| **C** | `startedAt` 加微秒/随机后缀 | 改语义，不推荐 |
| **D** | `runSession` 加互斥，根本不并发 | 治标，但简单 |

**我倾向 B**（双 key），配 D 一起做。

### 缺口 2：`runSession` 没有重入锁（**P2**）

**后果**：
- 两个并发 `runSession` **都会跑完**（消耗双倍模型调用）
- **各自持锁写盘**（不覆盖，但有上面的 history 问题）
- `autonomous-run.mjs` 和 `tick` 同时跑时会这样

**不是数据损坏**（有字段级 diff 兜底），**是资源浪费 + history 合并问题**。

**修复方向**：

```js
// 方案：runSession 开头加互斥
if (sessionRunning) return { skipped: 'already-running' };
sessionRunning = true;
try { ... } finally { sessionRunning = false; }
```

**但**：**接口语义变了**（返回 `{ skipped }` 而不是 `rec`）→ **要看两个调用方怎么用**：
- `tick`：`await runSession({})` → **忽略返回值** → 安全
- `autonomous-run.mjs`：`const rec = await runSession(...)` → **用了返回值** → 要处理

**`autonomous-run.mjs` 的处理**：打印"已经在跑了"并退出。

## 六、其他检查项

### 6.1 `tick` 与 `runSession` 的锁关系

```js
async function tick() {
  if (running) return;         // 2160
  ...
  running = true;              // 2209
  await runSession({});        // 2211
  ...
}
```

**但**：`runSession` 的 `finally { running = false; }`（1809）会在**任何情况下**释放。

**如果** `runSession` 抛错 → `finally` 释放 ✅
**如果** `tick` 在 `runSession` 之后还有代码 → `running` 已经 false → **可能重入**？

**看**：2211 之后还有什么。

### 6.2 Judge 与 `runSession` 的写入时序

```
T0: runSession #1 → finish → writeState（history + digests）
T1: runSession #1 返回 → running = false
T2: judgeGoalCandidate 开始（fire-and-forget）
T3: runSession #2 开始（因为 running 已 false）→ 读 st
T4: judge 完成 → writeState（旧 st，但只改 judgeLog）
T5: runSession #2 → finish → writeState
```

**T4 和 T5 交错时**：
- T4 的 `st` 版本老于 T5 → 走合并分支
- T4 只改 `goalJudgeLog` → **T5 的 `digests` 保留** ✅
- **但 T4 的 `history` 会走 `mergeByKey`** → 如果 T5 的 `startedAt` 和 T4 的不同 → 正常 ✅

**所以**：**Judge 的写盘不会覆盖下一轮的数据**（除了 history 的 key 问题）。

### 6.3 预算预留在并发下会不会被绕过

```js
const gate = shouldJudge(...);            // 读 count
st.goalJudgeCount = bumpJudgeCount(...);  // 内存
await call(...);                          // 模型调用
```

**两个并发 Judge**（如果 `runSession` 并发）→ **都读到 count=0** → **都放行** → **一天可能调 6 次**。

**但**：`runSession` 有互斥的话，Judge 也串行 → 不会。

**所以**：**修了 `runSession` 互斥，预算就安全了**。

### 6.4 进程异常退出时会不会留死状态

- `goalJudgeLog`：正常追加 → 异常退出时**没写** → 下次重试 ✅
- `goalJudgeCount`：**调用前加** → 异常退出时**已经加了** → 那次预算被"浪费" ✅（这是**故意的**，避免无限重试）

**结论**：**不会留无限重试状态** ✅

## 八、跨进程 vs 进程内（机主问的）

| 层 | 机制 | 覆盖范围 |
|---|---|---|
| **跨进程** | `withState` → `withFileLock`（文件锁 + EPERM backoff） | ✅ 多进程安全 |
| **进程内** | `tick` 的 `running` | ⚠ **只覆盖定时器** |
| **`runSession`** | **无** | ❌ |

**结论**：
- **文件级并发是安全的**（有 `withFileLock`）
- **缺的是 `runSession` 的进程内互斥**（防止重复跑一轮）
- **`mergeByKey` 的 key 问题是独立的逻辑缺陷**

**不能把进程内锁当成跨进程保护** —— 这一条现有实现**做对了**（用了 `withFileLock`）。
