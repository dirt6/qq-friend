## 三、已发现但不阻塞验收

### 3.1 goal 在 `finish` 轮不更新

**18:32 那轮**：

```
round-e2c59085
intent=finish   goal=先歇一会儿，等老大打完游戏回话
stop=完成：现在没什么想做的
```

**`companion-state.json` 完全没有变化**：

```
updatedAt: 07:29:56（15:29，3 小时前）
goal:      问出老大昨晚真实睡眠情况   ← 还是旧的
```

**原因**：`intent=finish` 时不产生 `decision`，而 `setGoal` 只在决策分支执行：

```js
if (decision.goal) setCompanionGoal(...)
```

**这是从旧代码继承的行为**（原 `st.currentGoal = decision.goal` 也只在有 decision 时写），不是 2.5 引入的。但注入放大了它的影响。

### 3.2 已达成的 goal 不会自动清除

10:49 你答「睡着了呀」之后，这个目标实际上已经达成，但：

- `settleChatPending` 只清**匹配 pending 的** goal（这条没有对应 pending）
- 下一轮 `setGoal` 会覆盖（但 18:32 是 `finish`，没有覆盖）
- `clearGoal` 没人调

**结果**：一个已完成的 goal 可以挂很久。

**两个缺口叠加**：

```
达成后不清（10:49 答了，15:29 又写成 goal）
+ finish 轮不更新（18:32 歇着，goal 还是旧的）
= 一个 goal 可能挂好几天
```

## 七、转入 2.6 的两个子问题

| 子问题 | 核心问题 |
|---|---|
| **Goal 生命周期** | 什么情况下创建、继续、完成、取消、替换、过期？ |
| **唤醒调度** | 固定周期唤醒和单次延迟唤醒如何共存？ |

**机主明确的边界**：

> `finish` 不能简单等于清除 goal。她决定"先歇一会儿"可能只是暂时停止行动，并不意味着长期方向已经完成。
> 反过来，也不能因为没有新 decision，就让旧 goal 永久保留。

**设计候选（不建议现在就加字段）**：

- `active`：当前方向仍然有效
- `completed`：有明确依据认为目标达成
- `cancelled`：主动放弃或被新方向取代
- `paused`：暂时停止，但仍保留

**要先确定这些状态对聊天注入有什么实际影响，再决定要不要加字段。**
