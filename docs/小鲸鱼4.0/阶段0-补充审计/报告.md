## 0.1 延迟基线（真实调用，短 prompt：`只回复两个字：收到`）

| 场景 | spawn | 首事件 | final | 总耗时 | input | cacheRead |
|---|---|---|---|---|---|---|
| 冷启动（新 session） | 22 ms | 5 362 ms | 6 202 ms | **6 273 ms** | 513 | 5 504 |
| 热会话 1 | 17 ms | 5 157 ms | 6 100 ms | **6 168 ms** | 140 | 5 888 |
| 热会话 2 | 8 ms | 5 119 ms | 5 747 ms | **5 810 ms** | 151 | 5 888 |
| 并发新 session A | 18 ms | 5 296 ms | 5 917 ms | **5 995 ms** | 134 | 5 883 |
| 并发新 session B | 9 ms | 5 303 ms | 6 970 ms | **7 033 ms** | 134 | 5 883 |

### 结论

1. **进程启动不是瓶颈**：spawn 8~22 ms，可以忽略。
2. **主要开销是 profile 加载 + 首 token**：每次约 5.1~5.4 s 才出现第一条事件；final 随后 0.5~0.9 s。
3. **冷热差异很小**（6.27 s vs 5.81~6.17 s，差 0.1~0.4 s）：会话恢复不是主要成本，**每次调用都要重新加载 profile/插件**。
4. **单次调用约 5.6~6.3 s**。自主活动每轮 2~6 次调用 → **约 11~38 s**，低于 D1 的 60 s 可接受线。
5. 注意：本次 prompt 极短（input 513/140 tokens）。真实 intent/decision 的输入 2~5 k tokens，首 token 会更慢；按经验每多 1 k input 约 +0.2~0.5 s，6 次调用仍在 60 s 内，但接近上限。**阶段 3 需要用真实 prompt 再测一次**。
6. 缓存命中很高（cacheRead 5.5~5.9 k），说明 system prompt 前缀稳定，成本可控。

### 对 D1 的影响

- 60/120 s 阈值可用，当前短 prompt 下余量充足。
- 若真实 prompt 让单轮接近 60 s，优先做"同一轮复用进程"（把 intent/decision/reflection 放进一次 DSH 调用），而不是提高阈值。

## 0.2 多 Session 并发预检

| 场景 | 结果 |
|---|---|
| 两个**新 session** 并发 | 两个都成功（5.99 s / 7.03 s），各自拿到独立 sessionId，文本都正确 |
| 同一 session 并发两次 | A 成功（6.35 s）；B 退出码 1，stderr：`dsh: session "..." is already owned by an active write handle` |

### 结论

- **不同 session 可以并发**，未见 projcache/文件锁冲突（本次各 1 轮；长时间并发需阶段 3 复测）。
- **同一 session 双开被明确拒绝**，错误信息清晰，不会静默损坏——这是好消息，说明 DSH 的单写者锁有效。
- 仍需在阶段 3 复测：并发 10+ 轮、并发下的 token 账本归属、attachments/projcache 竞争、异常退出后的锁释放。

### 对 D2/D4 的影响

- D2 的"每个逻辑会话一个 session"可行；但**状态文件（Companion State）必须自己实现单写者**，因为 DSH 的锁只保护 session 目录，不保护 QQ-agent 的 JSON。
- D4 的 Session 轮换可以安全地"新建而不动旧会话"：并发新建已验证。

## 0.3 文件写入风险清单（静态）

统计范围：`src/`、`plugins/`、`scripts/`、`dsh-plugins/` 下含 `writeFileSync|appendFileSync|renameSync|fs.write` 的文件。

| 文件 | 写次数 | 目标 | 写方式 | 跨进程保护 | 风险 |
|---|---|---|---|---|---|
| `src/sessions.js` | 10 | `data/sessions/*.json`、`session-index-cache.json`、`usage-today.json` | 会话单文件 **直接 writeFileSync**；缓存/usage 用 tmp+rename | 无 | **中高**：会话文件非原子写，崩溃可能半截；面板与主进程可能同时写 |
| `src/store.js` | 3 | `data/messages/<chat>.json` | tmp+rename | 无 | 中：整文件重写，1.4 MB 且增长 |
| `src/config.js` | 3 | `data/config.json` | tmp+rename + 损坏备份 | 无 | 中：面板/CLI/插件都可能写 |
| `src/learned.js` | 2 | `data/learned.json` | tmp+rename | 无 | 中：面板 `learned.save` 与插件写入并发 |
| `src/memory.js` | 3 | `data/memory/**` | tmp+rename | 无 | 低（目前 300 B） |
| `src/dsh-gateway.js` | 6 | `dsh-sessions.json`、`dsh-injected.json`、`dsh-persona.patch.yml`、`dsh-gateway.log` | tmp+rename / append | 无 | 中：每轮重写 persona patch；sessions 映射被并发更新 |
| `plugins/autonomous/lib/state.js` | 3 | `data/autonomous.json` | tmp+rename | 无 | **高**：185 KB，面板/`trim-autonomous.mjs` 也可能写 |
| `plugins/autonomous/index.js` | 5 | 日记、活动日志、状态 | append / 重写 | 无 | 高：与 diary 技能、orchestrator 代写并发 |
| `plugins/silence-ping/index.js` | 6 | 自己的状态 + 日记 | 混合 | 无 | 中 |
| `scripts/web-panel-server.mjs` | 6 | learned/stickers/drawings/日志 | 混合 | 无 | 中：面板写与主进程并发 |
| `scripts/trim-autonomous.mjs` | 4 | `autonomous.json` | 读改写 | 无 | **高**：外部脚本与插件同时写会丢更新 |
| `src/app.js` | 4 | `usage-days/*.json`、`token-usage.json` | tmp+rename | 无 | 中：并发调用时 last-writer-wins |
| `src/image-cache.js` | 3 | `data/image-cache/**` | 直接写 | 无 | 低（文件级） |

### 共性结论

1. **tmp+rename 只保证单进程原子，不是跨进程锁**——两个进程同时读改写仍会丢更新。
2. **没有一把锁覆盖 `autonomous.json`**，而它同时被插件、面板、`trim-autonomous.mjs` 写。
3. **日记有三条写入路径**，且都是 append，天然并发安全但会重复。
4. `sessions.js` 的会话文件是**直接覆盖写**，最脆弱。
5. 面板是"事实上的写入口"：`learned.save/delete/archive`、`stickers.note`、`drawings.delete`。

### 修复建议（对应阶段）

| 风险 | 修复 | 阶段 |
|---|---|---|
| 会话文件非原子 | 改为 tmp+rename；或合并进统一 writer | 1.5 |
| `autonomous.json` 多写者 | 单 writer 进程 / 文件锁；`trim-autonomous.mjs` 改为调用 API | 1.5.4 |
| 日记三入口 | Diary Writer + lock.js | 1.5.1 |
| 面板记忆写入 | 收回，走 Memory Hub 管理接口 | 1.5.5 / 2.6 |
| usage 账本并发 | 统一账本 writer | 1.3 |
| 事件日志 | 追加写 + `eventId` 幂等 + 单写者 | 1.1 / 1.2 |
| 存储删除 | 回收站 + 索引一致 + 审计 | 2.6 |

## 0.4 对既有决策的影响

| 决策 | 影响 |
|---|---|
| D1 自主活动全部走 DSH | 延迟可用（短 prompt 6 s/次，6 次约 38 s）；真实 prompt 需阶段 3 复测；进程复用优先级下调 |
| D2 状态迁移 | Companion State 必须自带单写者；DSH 的 session 锁不能复用 |
| D3 日记 Writer | 三入口 + 面板并发已确认，Writer 必须带 lock.js |
| D4 Session 轮换 | 并发新建安全；轮换不删旧会话可行 |
| D5 事件归档 | 事件日志同样需要单写者 + 幂等；否则归档统计不可信 |
| D6 面板写收回 | 面板 6 处写中至少 4 处属于记忆类，收回到 Memory Hub 管理接口 |
| D7 旧 API | 失败时的静默回落仍存在（`#askDsh` 返回 null → `#runAgent` 回落），阶段 3 必须显式化 |
| D8 存储治理 | `sessions.js` 直接覆盖写是存储治理的第一个修复点；`data/sessions` 141 MB 需保留策略 |
