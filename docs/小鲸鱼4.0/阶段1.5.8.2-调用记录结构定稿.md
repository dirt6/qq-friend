### 字段说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | `call-<8位十六进制>`，**每次实际调用唯一** |
| `roundId` | string | `round-<8位十六进制>`，一轮处理共用一个 |
| `at` | ISO 8601 | 带时区（本机 `+08:00`） |
| `purpose` | enum | 见第四节 |
| `backend` | `dsh` \| `api` | **实际**使用的，不是计划的 |
| `status` | `success` \| `failed` | 不含 `fallback`（fallback 是标记，不是状态） |
| `durationMs` | number | 从发起到返回/抛错的总耗时 |
| `fallback` | boolean | 这次调用是不是回落后的 |
| `fallbackFrom` | `dsh` \| null | 从哪个入口回落来的 |
| `failureCode` | enum \| null | 见第五节 |
| `failureDetail` | string \| null | 人能看懂的一句话，**截断到 200 字** |
| `model` | string \| null | 实际模型名 |
| `tokens` | object \| null | **失败且没拿到用量时是 `null`，不填 0** |

## 三、ID 与生命周期

### 生成

```js
// 8 位十六进制，够用且短
const callId = `call-${crypto.randomBytes(4).toString('hex')}`;
const roundId = `round-${crypto.randomBytes(4).toString('hex')}`;
```

### 生命周期

```
一轮开始
  └─ beginRound({ kind: 'chat', chatKey })
       ↓ 返回 roundId（存进 AsyncLocalStorage）
     ┌──────────────────────────────┐
     │  model call #1 → recordCall  │  ← 自动带上 roundId
     │  model call #2 → recordCall  │
     │  工具执行      → （另一套）   │
     └──────────────────────────────┘
       ↓
  └─ endRound(roundId, { outcome: 'done' | 'error' })
```

### 为什么用 AsyncLocalStorage（以及它的边界）

`chatCompletion` 有 7 个调用点、`ask()` 还有 spawn 子进程。**改一遍签名要动 7 处调用链**，而且 `orchestrator.js` 有 2300+ 行，漏一个就断链。

**机主 2026-11-01 修正了一个我写错的说法**：ALS 能跨 `await`、跨同进程异步任务传播，**但不能跨 `spawn` 传到另一个 Node 进程**。

**结论：调用记录全部由父进程写。**

```
父进程
  ├─ ALS 创建 roundId
  ├─ chatCompletion        ← 父进程内，ALS 能拿到
  ├─ DSH Gateway
  │    └─ spawn dsh 子进程  ← 子进程不写日志
  │         （父进程等结果，成功/失败/耗时都是它观测到的）
  └─ recordCall            ← 父进程写，roundId 从 ALS 取
```

**禁止**：让 DSH 子进程和主进程同时写同一份调用日志（会出现两套 roundId、两套口径）。

`AsyncLocalStorage` 在本进程内能**自动跨 await / 跨异步**传播：

```js
import { AsyncLocalStorage } from 'node:async_hooks';
const ctx = new AsyncLocalStorage();

export function withRound(meta, fn) { return ctx.run({ ...meta, roundId: newRoundId() }, fn); }
export function currentRound() { return ctx.getStore() || null; }
```

**`purpose` 不走 ALS**，由调用点显式传 —— 只有它自己知道自己在干什么（意图？决策？回复？）。

## 五、failureCode 枚举

| 码 | 含义 | 来自 |
|---|---|---|
| `DSH_SPAWN_FAILED` | 起不来（找不到 dsh / 临时目录建不了） | gateway |
| `DSH_TIMEOUT` | 超时 | gateway |
| `DSH_NONZERO_EXIT` | 非零退出 | gateway |
| `DSH_EMPTY_REPLY` | 空回复 | gateway |
| `DSH_BAD_JSON` | 返回的不是合法 JSON | gateway |
| `API_HTTP_4XX` | 除 429 的 HTTP 错误 | llm |
| `API_429` | 限频 | llm |
| `API_TIMEOUT` | 超时 | llm |
| `API_EMPTY` | 空回复 | llm |
| `API_BAD_TOOLCALL` | 工具调用格式错 | llm |
| `ABORTED` | 用户中止 | llm |
| `UNKNOWN` | 兜底（**附带 failureDetail**） | 任何 |

**规则**：
- 失败**必须有** failureCode
- `UNKNOWN` 必须带 `failureDetail`（一句人话）
- 成功时 `failureCode` 和 `failureDetail` 都是 `null`

### 文件

```
data/model-calls.ndjson      ← 当前
data/model-calls.ndjson.1    ← 上一代（只留一份）
```

### 写入

```js
fs.appendFileSync(file, JSON.stringify(rec) + '\n', 'utf8');
```

**不包锁？** 需要。参照 1.3 事件的做法：进程内串行 + 跨进程 `.lock`。

但这里是**高频**写入（每轮几次），锁开销要考虑。**参照 events.js 的模式**（拿不到锁就降级直写）。

### 轮转

```js
if (size > MAX) fs.renameSync(file, `${file}.1`);   // 覆盖上一代
```

**只留一代**（你定的）。

### 容量估算（实测基数）

```
最近 24 小时：106 轮会话，约 106 次模型调用
单条记录：约 303 字节
一天：约 31 KB
```

加上自主活动（一轮 2~3 次）和辅助调用，**按 45 KB/天估**。

**机主 2026-11-01 定稿：B 方案。**

| 项 | 值 |
|---|---|
| 单条记录 | 303 B |
| 每日预计 | 45 KB |
| 主文件上限 | **2 MB** |
| 历史文件上限 | 2 MB |
| 最大占用 | **4 MB** |
| 预计追溯 | **约 45 天** |

附加两条要求：

- **轮转失败不能删除旧文件**（rename 失败就保持原样，不 unlink）
- **磁盘达到上限时不影响模型调用**，只记告警

## 七、fallback 的记录流程（最重要的一条）

### DSH 失败 → API 成功的完整时序

```
orchestrator 决定走 DSH
  ├─ recordCall({ backend:'dsh', status:'failed', failureCode:'DSH_TIMEOUT', durationMs:180000 })
  │     ↑ 这条在 catch 里记，**不因为后面成功了就丢弃**
  ↓
回落 API
  ├─ recordCall({ backend:'api', status:'success', fallback:true, fallbackFrom:'dsh' })
  ↓
本轮结束
```

**禁止的行为**（你特别强调的）：

```js
// ❌ 错的：第二次成功就把第一次抹了
if (dshResult === null) {
  apiResult = await chatCompletion(...);
  recordCall({ status: 'success' });   // 只记一条
}
```

### 面板怎么读

```
round-9d2e4f11
  call-3f8a1c2b  dsh  failed   DSH_TIMEOUT     180s
  call-7b2c5e90  api  success  fallback←dsh      3.4s

→ 这一轮：DSH 超时，靠 API 兜住了，用户无感
```

## 八、和 actions 的关系

**两套记录，用 roundId 关联，不合并。**

| | 谁写 | 回答什么问题 |
|---|---|---|
| `model-calls.ndjson` | 记录器（gateway/llm 层） | 模型调用成没成、走哪条路 |
| `autonomous.json` 的 `history[].actions` | 自主活动 | 她想做什么、做成没成 |

**关联示例**：

```
round-a1b2c3d4（自主活动一轮）
  ├─ model-calls: call-1  intent     success
  ├─ model-calls: call-2  decision   success
  ├─ actions:     [ { action:'draw', result:'failed', error:'绘图程序启动失败' } ]
  └─ model-calls: call-3  decision   success

→ 面板能说：模型三轮都成功，但她想画画失败了，所以这轮没有产出
```

**关键**：`actions` 里要**存 roundId**（新增字段），才能对上。

## 九、故障隔离（你要求的安全底线）

> 记录器故障不能反过来导致正常聊天失败。

三条：

1. **`recordCall` 永不抛错** —— 内部全 try/catch，失败只 `console.warn`
2. **写失败不影响返回值** —— 记录是旁路，不是调用链的一环
3. **锁拿不到就降级直写**（参照 events.js）—— 宁可多一条，不丢记录
