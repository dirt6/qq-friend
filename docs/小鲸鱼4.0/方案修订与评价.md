# 小鲸鱼 4.0 · 方案修订与评价

> 基于 [阶段 0 架构审计报告](阶段0-架构审计报告.md) 对原方案的逐条修订。
> 结论：**方向保留，顺序调整，三处假设必须改写，工作量上调。**

---

## 一、总体评价

### 保留

1. **统一认知入口**：聊天与自主活动共享人格、记忆、状态——这是 4.0 的核心价值，方向正确。
2. **独立 Session**：两个上下文分开，避免把后台思考塞进聊天记录，符合当前"注意力稀释"的经验。
3. **事件同步而不是全量复制**：正确。当前 `hotNote` 每轮补丁已经证明"全量复制"会膨胀。
4. **分阶段 + 旧系统保持可用 + 回退机制**：正确，且比一次性切换务实。
5. **保留现有文件**：正确。`data/` 下的日记、经验、印象、活动都是可读的 Markdown/JSON，强行入库收益低。

### 需要调整

| # | 原方案 | 问题 | 修订 |
|---|---|---|---|
| 1 | 两个 Session 都是 DSH Session | 自主活动当前**没有 Session**，直连 `llm.chatCompletion`；阶段 1/2 若按"已有两个 Session"设计，会做出没有消费者的接口 | 阶段 3 先建 autonomous session；阶段 1/2 明确"自主活动仍是旧 API，只接状态与事件" |
| 2 | 全部模型调用统一经过 DSH | 自主活动每轮 2~6 次调用；DSH 每轮 spawn 子进程约 3~5 s，统一后单轮自主活动可能 15~30 s | 阶段 3.1 先测 DSH 常驻/批量能力；若不可行，接受延迟并调低自主频率，或保留"高频小调用走 API、重大决策走 DSH"的混合模式（需机主拍板） |
| 3 | 阶段 1 建 Companion State | 状态没有输入：聊天事件还不存在 | 阶段 1 的第一件事是**在 orchestrator 发布 chat 事件**，再加状态消费 |
| 4 | 阶段 2 建 Memory Hub | 日记有三处写入口、经验/印象各写各的；先建 Hub 只是给三个写者套壳 | 增加**阶段 1.5：写入口归一**（一个 writer），再做 Hub 的读接口与检索 |
| 5 | Companion State 是新增 | `autonomous.json` 已有 currentGoal/pendingNextStep/selfWake，会形成双真源 | 二选一：迁移字段（旧文件只读镜像）或把 companion-state 设计成 `autonomous.json` 的受控投影。**不要双写。** |
| 6 | 影子测试"只记录不执行" | DSH 工具会真实执行（`qq_tool` 可能发消息/评论/发帖） | 阶段 3.2 必须先加 dry-run 开关，让 DSH 侧工具只写 outbox、不执行 |
| 7 | Token 账本阶段 5 整合 | 现在主账本 + 自主账本分裂，预算已经失真 | **阶段 1 就并账**（统一账本接口），成本最低 |
| 8 | 工作量 11.5~22 天 | 未计入：DSH 并发实测、dry-run 改造、三处日记归一、事件幂等、面板改造 | 建议上调到 **18~32 天**，其中阶段 3 占比最大 |
| 9 | "不调用真实模型"完成阶段 0 | 多 session 并发必须实测 | 阶段 0 只做静态审计 + 待实测清单；并发验证放阶段 3.1（专用测试 profile） |

## 二、逐节修订

### 1. 目标架构

原图把 Memory Hub 与 Companion State 并列。修订为：

```
Core（人格/身份/权限/生命周期）
   │
   ├─ Companion State（话题、计划、待办、状态）── 事件日志（唯一写入口）
   │        ▲                         │
   │        └──── 聊天事件 ───────────┘
   │
   ├─ Memory Hub（读接口 + 一个 writer）
   │        │ 日记 / 经验 / 印象 / 活动 / 聊天索引
   │        └─ 原始文件保持 Markdown/JSON
   │
   ├─ DSH 统一模型网关
   │    ├─ chat session（现有）
   │    └─ autonomous session（阶段 3 新建）
   │
   └─ 工具层（QQ-agent 执行端 + DSH qq-tools outbox）
```

关键：**Companion State 不存长期记忆，只存"当前正在发生的事"**；长期记忆仍归 Memory Hub 的原始文件。

### 2. 模块处置

审计后修订三处：

- `src/dsh-gateway.js`：不是"可直接复用"，而是"复用 + 改造"（新增 autonomous 模式、dry-run、usage 出口）。
- `plugins/autonomous`：不是"只换模型适配器"，还要把状态读写接到 Companion State，并消费事件。
- 日记：三处写入必须归一；`skills/diary`、`plugins/autonomous`、`dsh-plugins/qq-tools` 谁是 writer 需要在阶段 1.5 决定（建议 `memory-hub/diary.js` 作为唯一 writer，其余改为调用）。

### 3. 数据设计

- `companion-state.json` 与 `companion-events.ndjson` 的设计可行，但必须补：
  - **单一写者**：面板、插件、脚本都不得直接改 JSON；只允许通过 writer 进程/文件锁。
  - **事件幂等**：`eventId` + 消费位点 + 失败不推进位点。
  - **归档**：已处理事件定期滚动到 `companion-events.<月>.ndjson`，主文件保留最近 N 天。
  - **来源**：每个状态变更记录 `source`（chat/autonomous/panel）与 `reason`。
- 现有 `autonomous.json` 185 KB，建议迁移时只迁 `currentGoal`/`pendingNextStep`/`selfWake` 三类字段，`history`/`shares`/`seen` 保持原位（活动历史仍归 autonomous）。

### 4. DSH 统一调用

- 新增 `companion.run({ mode, sessionKey, task, context, permissions })` 是合理的抽象，但要在阶段 3 用真实 DSH 参数验证：
  - `--session-id` 是否支持"同一个 autonomous session 跨轮复用"；
  - 多 session 并发是否稳定（阶段 3.1）；
  - `--json` 事件流的 usage 是否够统一账本使用。
- **不要**让自主活动每轮 spawn 2~6 次；建议一次 `runSession` 只起一个 DSH 进程，把 intent/decision/reflection 作为同一进程内的多轮对话（DSH 支持多轮 prompt）。
- 旧 API 回退：保留，但默认关闭静默回退；失败时显式记录 `backend=api`，并在面板可见。

### 5. 迁移顺序

修订为（2026-10-31 机主拍板后的最终顺序，详见 [决策记录](决策记录.md)）：

| 阶段 | 内容 | 与原文差异 |
|---|---|---|
| 0 | 架构审计（已完成）+ 补充审计：延迟基线、并发预检、写风险清单 | 增加待实测项 |
| 1 | 基础设施：聊天事件发布、Token 账本统一、Session 生命周期管理、单写者基线 | 原阶段 1 拆细 |
| 1.5 | 写入口归一：Diary Writer、经验库收口、autonomous.json 并发修复 | 新增，先于 Memory Hub |
| 2 | Companion State：唯一真源，迁移 currentGoal/pendingNextStep，事件同步 | 原阶段 1 后移 |
| 2.5 | Memory Hub：统一读取接口、按需检索（不复制记忆） | 原阶段 2 后移 |
| 2.6 | 存储治理与删除：分级、回收站、容量保护、审计、关联保护 | 新增（D8） |
| 3 | DSH Autonomous Session：并发 Go/No-Go、延迟测量、dry-run、迁 intent/decision/reflection、并账、旧入口退役 | 原阶段 3 细化 |
| 4 | 工具适配：清单、模式白名单、权限 | 保留 |
| 5 | 整合验收：状态页、事件审计、故障恢复、7 天长跑 | 保留 |

四项拍板摘要（完整内容见 [决策记录](决策记录.md)）：

- **D1** 自主活动全部走 DSH；先测延迟（P50/P95/整轮），再研究同进程复用；30 分钟窗口不变；单轮 P95 > 120 s 时暂停全面迁移。
- **D2** 跨模式状态迁 Companion State；调度/历史/预算留 Autonomous；同一字段唯一写入者，旧字段只读兼容。
- **D3** 日记统一 Writer（`diary/{diary,writer,reader,lock}.js`），保留 Markdown/目录/分级/心情/历史；并发保护、重试、去重、确认。
- **D4** 自动 Session 轮换（70% 准备、80% 优先新会话、质量下降提前、损坏从记忆恢复）；旧会话保留，摘要不替代原始记录。
- **D5** 事件：未处理永久保留、已处理 90 天、按月 gzip 归档不自动删；按 `processedAt` 归档；启动只读未处理；归档 500 MB 提醒、1 GB 暂停扩张（可配置）。
- **D6** 面板保留 bot/panel 与表情库；记忆类写操作收归 Memory Hub；面板只读展示记忆，修改走授权接口。
- **D7** DSH 唯一正式入口；禁止静默回退；保留人工开关并记录操作者/时间/原因；回退期间禁止双入口重复执行；DSH 故障时自主活动暂停。
- **D8** 存储分级 L1~L4、回收站 30 天、未处理事件不可批量删、删除前展示影响与释放空间、关联保护、容量预警 500 MB~5 GB、审计不含正文。

### 6. 安全与回退

补三条：

1. **单写者**：任何状态文件只允许一个进程写；其他进程通过 IPC/HTTP 请求写。
2. **迁移双读**：迁移期新代码读新格式、旧代码读旧格式；回退时不丢新数据（新格式只增字段，不删旧字段）。
3. **预算熔断**：统一账本后，自主活动与聊天共享月度预算；超预算先停自主活动，不静默降级聊天。

### 7. 验收标准

原文 19 项保留，补充 5 项：

- 事件日志可重放，重复消费不产生第二条状态变更；
- 任一时刻只有一个进程持有状态写锁（有测试）；
- DSH 故障时，自主活动"暂停"而不是"重复执行上一轮动作"；
- 三处日记写入归一后，同一天同一条不会重复；
- 回退到旧版后，新版写入的状态字段不导致旧版崩溃。

## 四、最终建议

1. **先做阶段 1 的"聊天事件发布"**，这是整个 4.0 的第一个真实收益点：她以后不会重复问已回答的问题。
2. **不要同时动 Memory Hub 与 autonomous**；先归一日记写入口，再谈检索。
3. **阶段 3.1 的并发实测是 Go/No-Go 门**：如果两个 DSH session 不能稳定并发，就退回"自主活动继续直连 API、只共享状态与记忆"的方案（L2 重合），不要硬推。
4. **保留旧的 API 路径至少一个大版本**，但默认关闭静默回退。
5. 面板先加"状态与事件审计"，再做写操作归一。
