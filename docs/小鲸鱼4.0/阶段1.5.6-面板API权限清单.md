## 五、收回方式（建议）

不是删接口，是**改成"明确的拒绝"**：

```
POST /api/learned.save
→ 403 { ok:false, error:'记忆写入已收回到统一入口（阶段 2 Memory Hub）',
         code:'MEMORY_WRITE_RETIRED',
         hint:'用聊天里的「记住/忘了」工具，或等记忆管理面板上线' }
```

配套三件事：

1. **后端拒绝**：四个路由直接返回 403，不碰文件
2. **前端降级**：按钮置灰 + 悬浮提示"该功能已收回到统一入口"，点击弹同样的提示（不是崩，也不是静默无反应）
3. **拒绝日志**：`data/logs/` 记一条 `[acl] 面板试图写记忆：learned.save from 127.0.0.1`，方便排查"为什么按钮点不动"

### 为什么后端必须拒绝

只藏按钮不够——旧页面、书签、`curl`、以后某个脚本都可能直接打这个接口。**权限必须在后端判**。

## 六、画作删除的处理（按你的意见）

**查了一下现状：`deleteDrawing` 是 `fs.rmSync(abs, { force: true })` —— 直接删，没有备份，也没有回收站。**
现有 5 张画（250~310 KB 一张），删了就真没了。

补两个机制：

1. **备份**：删除前移到 `data/drawings/.trash/`，记一条删除日志（谁、什么时候、哪个文件）
2. **确认**：前端二次确认（"确定删除？会移到回收站，7 天内可恢复"）

顺手把**恢复**也做了（`drawings.restore` + 7 天自动清理），成本很小：
`.trash/` 目录 + 一个 `restore` 路由 + 启动时清理过期项。你要是不需要，我就只做备份。

## 七、阶段 2 要提前定的事（你提的）

你列的五项能力（查看/修改/分级/归档/删除 + 使用情况）属于**阶段 4 的记忆管理面板**。
但 **API 的权限模型要在阶段 2 定**，所以这里先把三层写下来：

| 层 | 谁 | 能做什么 |
|---|---|---|
| 1 | **她** | 写日记、提新经验（pending）、检索记忆、形成候选 |
| 2 | **机主** | 确认经验、改文本、调等级、归档、删除（带回收站） |
| 3 | **系统** | 去重、索引、同步、备份、权限检查、一致性 |

**关键**：机主的"修改/删除"也要走**统一入口**（Memory Hub 的 API），不是直接改 JSON。这样阶段 4 的面板只是这个 API 的 UI。

"使用情况"（被检索几次、哪轮自主活动用过、多久没调用、为什么想起、谁写的）——
`learned.json` 现在已经有 `hits` / `lastUsedAt` / `corrections`，缺的是**"哪一轮用过"**的关联。
建议在阶段 2 加一个 `usedBy: [{ roundId, at }]`（保留最近 N 条），1.5.4 的增量合并已经能正确处理它。
