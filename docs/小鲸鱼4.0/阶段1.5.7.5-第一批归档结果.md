## 三项抽查结果

### ① 聊天可读性 ✅

**一个重要的发现**：`session.messages` **不是聊天记录**，是**模型交互轨迹**：

```
第 1 条: { role: 'assistant', content: '', tool_calls: [{ name: 'get_message_images', … }], raw: {…} }
第 2 条: { toolCall: { name: 'get_message_images', args: {…}, result: '消息 … 的内容：1 张图片。' } }
```

**真正的聊天内容在**：
- `trigger`（1 条）：`[dirrrt] [图片]`
- `sent`（2 条）：她发出的消息

**这两个字段归档后原样保留**，所以对话可读性没问题。时间戳也单调递增。

### ② 面板兼容性 ✅（且是"不适用"）

**查下来：面板根本没有 Session 展示页面。**

`web-panel/index.html` 的 13 个板块：
状态 / NapCat / 机器人 / 面板自身 / 机器人日志 / 面板日志 / 人设 / 日记 / 她自己写的功能 / 表情包 / 她的画 / 经验 / 她一个人时

**没有会话列表，也没有会话详情。**

所以"打开已归档 Session 会不会因缺 Prompt 报错"这个问题**不存在** —— 面板不读这个数据。

（如果以后做 Session 管理页，要注意 `messages` 是模型轨迹，展示聊天得读 `trigger` + `sent`。）

### ③ 后续检索 ✅

真实请求 3210 的 API：

```
GET /api/sessions
  → ok | 1304 条 | 归档的还在列表里，status=done

GET /api/sessions/mvb4skf9-e4480367
  → ok
    messages: 8 条 / sent: 2 条 / trigger: 1 条
    有 systemPrompt: 无（已剥离）
    有 archive: v1
```

**恢复路径检查**（代码验证）：

| 路径 | 条件 | 归档的会话满足吗 |

| `retry()` | `status === 'error'` | ❌ 不满足（是 done） |
| 等待会话恢复 | `status === 'waiting'` | ❌ 不满足 |

→ **不会被当成可恢复的活动会话** ✅

## 为什么还剩 73 MB

634 个归档了，但还有 **650 个未满 7 天**的会话带着完整 prompt（每份约 107 KB）。

```
634 个已归档  ≈  5 MB
650 个未到期  ≈  67 MB   ← 还带着完整 prompt
其他 20 个    ≈  1 MB
合计          ≈ 73 MB
```

**等那 650 个陆续满 7 天，每次跑一次 `--apply`，最终会降到约 9 MB。**

这是设计上的"分批自然释放"，不是没生效。
