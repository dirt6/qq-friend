## 一、当前实现与设计目标的差异

### 1.1 现状实测

| 场景 | 当前行为 | 设计目标 | 差异 |
|---|---|---|---|
| 3 paused + 1 active，再 `createGoal` | **成功**，paused 变 4 | **`CAPACITY_FULL`** | ❌ 超限 |
| `resumeGoal`（有别的 active） | paused 数量不变（1 active / 3 paused → 3 paused） | 不变 | ✅ **已符合** |
| `MAX_PAUSED_GOALS` | **定义了从未使用** | 实际检查 | ❌ 死代码 |
| 相同文本 active | 返回已有 | 一样 | ✅ |
| 相同文本 paused | 恢复原 ID | 一样 | ✅ |
| 文本规范化 | **只做 `trim()`** | 还要「统一连续空白」 | ❌ 缺一步 |

**实测证据**：

```
创建前: active=1 paused=3
创建后: active=1 paused=4     ← 超限
创建返回: ok=true created=true
```

### 1.2 关键发现：`resumeGoal` 天然不会超限

**实测**：

```
恢复前: active=1 paused=3
恢复后: active=1 paused=3     ← 不变
```

**原因**：

```
恢复 X（paused 之一）→ X 变 active，原 active 变 paused
净变化：paused -1（X 转出）+1（原 active 转入）= 0
```

**所以**：`resumeGoal` **理论上不需要容量检查**。

**但机主明确要求检查**（第四节第 3 条）。

**建议**：**仍加检查**（防御性，成本几行），因为：

1. 如果将来 `resumeGoal` 的语义变了（比如允许多个 active），这里会漏
2. 显式检查比"靠推理保证"更可靠
3. 失败时行为明确（整个操作失败，两个 Goal 都不变）

## 二、容量规则的完整状态转换表

### 2.1 容量定义

```
capacity.active = 1        （同时最多一个 active）
capacity.paused = 3        （最多三个 paused）
capacity.total  = 4        （active + paused）
不占容量：completed / cancelled / superseded
```

### 2.2 每个操作对容量的影响

| 操作 | active 变化 | paused 变化 | 什么时候可能超限 | 要不要检查 |
|---|---|---|---|---|
| `createGoal`（新建） | +1（新的）<br>-1（旧 active 转 paused） | **+1** | **paused 已经是 3** | ✅ **要** |
| `createGoal`（相同 active） | 0 | 0 | — | ❌ 不用 |
| `createGoal`（相同 paused → 恢复） | 0（净：+1 -1） | 0（-1 转出 +1 转入） | — | ⚠ **边界**（见下） |
| `updateGoal` | 0 | 0 | — | ❌ 不用 |
| `pauseGoal` | **-1** | **+1** | **paused 已经是 3** | ✅ **要** |
| `resumeGoal` | 0（净：+1 -1） | 0 | 理论上不会 | ⚠ **防御性检查** |
| `completeGoal` / `cancelGoal` / `supersedeGoal` | 可能 -1 | 0 | 只会减少 | ❌ 不用 |
| `clearGoal` | 可能 -1 | 0 | 只会减少 | ❌ 不用 |

### 2.3 `createGoal` 恢复分支的边界

**场景**：

```
现状：active=A, paused=[X, Y, Z]（3 个满了）
操作：createGoal("X 的文本") → 走"相同 paused → 恢复"
```

**净变化**：

```
X: paused → active       （paused -1）
A: active → paused       （paused +1）
净：paused 不变 = 3
```

**结论**：**不会超限** ✅

**但**：如果 `A` 不存在（没有 active）呢？

```
现状：paused=[X, Y, Z]，无 active
操作：createGoal("X 的文本") → 恢复 X
```

```
X: paused → active       （paused -1 → 2）
没有别的 active          （不用让位）
净：paused = 2
```

**也不会超限** ✅

**所以**：`createGoal` 的恢复分支**天然不会超限**。

### 2.4 `pauseGoal` 的容量检查

**这是最容易忽略的**：

```
现状：active=A, paused=[X, Y, Z]（3 个满了）
操作：pauseGoal(A)
```

```
A: active → paused       （paused +1 → 4）
```

**超限** ❌

**所以 `pauseGoal` 必须检查**！

**但**：`pauseGoal` 是**用户的合法操作**（"这件事先放一放"），拒绝它合理吗？

**设计选择**：

| 方案 | 行为 | 评价 |
|---|---|---|
| A | `pauseGoal` 也拒绝（`CAPACITY_FULL`） | 一致，但用户可能困惑 |
| **B** | **`pauseGoal` 不检查**（暂停是"收起来"，不是"新增"） | 但会导致 paused > 3 |
| C | 允许暂停，但**标记超限**（`overCapacity`） | 复杂 |

**我倾向 A**（拒绝）：如果 paused 已经满了，说明有 3 件事在搁置，第 4 件也该先处理而不是继续囤。

**但这需要机主确认**。

## 三、重复识别规则

### 3.1 文本规范化（保守方案）

```js
function normalizeGoalText(text) {
  return String(text ?? '')
    .trim()                    // 去首尾空白
    .replace(/\s+/g, ' ')      // 连续空白 → 一个空格
    .slice(0, 200);            // 上限
}
```

**不做**：

- ❌ 不删标点（"准备 CSP。"和"准备CSP"是不同文本）
- ❌ 不改大小写（中文没大小写，英文保留原样）
- ❌ 不语义改写
- ❌ 不相似度合并

### 3.2 四种情况

| 情况 | 预期行为 | 当前实现 |
|---|---|---|
| 相同文本，已有 **active** | 返回已有 Goal，不重复创建（`created: false`） | ✅ 已实现 |
| 相同文本，已有 **paused** | 恢复原 Goal，沿用原 ID | ✅ 已实现 |
| 相同文本，只有**终态**记录 | **允许创建新 Goal** | ✅ 已实现 |
| **文本不同，但明显同一方向** | **只提示，不自动合并** | ❌ **未实现** |

### 3.3 第四种情况的实现建议

```js
/**
 * 找"看起来像同一个方向"的 goal（只用于提示，**不自动合并**）。
 * 本阶段只做保守的包含关系判断，不做语义相似度。
 */
export function findSimilarGoals(text, { limit = 3 } = {}) {
  const t = normalizeGoalText(text);
  if (!t) return [];
  const st = readCompanion();
  const live = st.goals.filter((g) => g.status === 'active' || g.status === 'paused');
  return live.filter((g) => {
    const g2 = normalizeGoalText(g.text);
    if (g2 === t) return false;                 // 完全相同的走正常去重
    // 保守：一个包含另一个，且长度差不大（避免"想了解老大"命中"想了解老大的学习状态和作息"）
    if (!g2.includes(t) && !t.includes(g2)) return false;
    const ratio = Math.min(g2.length, t.length) / Math.max(g2.length, t.length);
    return ratio >= 0.6;
  }).slice(0, limit);
}
```

**关键**：

- **只返回，不做任何修改** —— 调用方（2.6.7 的聊天）决定怎么说
- **不自动合并**
- **阈值 0.6 是保守猜测**，要观察

### 3.4 需要你确认的四个细节

**① 相同文本但 `source` 不同**

**场景**：

```
现状：active = "准备 CSP"（source: autonomous）
操作：老大说"这个你记着，我要准备 CSP" → createGoal(..., source: 'user_directed')
```

**当前行为**：返回已有的 autonomous Goal（`source` **不变**）。

**问题**：老大的明确交代**没有被记录成 user_directed** → 以后她可以自主 cancel 这个方向（因为它是 autonomous）。

**三个选项**：

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 保持现状（source 不变） | 简单，但**违背"老大交代的事不能擅自取消"** |
| **B（我倾向）** | **保留原 Goal，但把 source 升级成 `user_directed`** | 保护老大的承诺 |
| C | 拒绝创建，返回 `SOURCE_CONFLICT` | 让调用方处理 |

**我倾向 B**，但**2.6.2 明确说过"updateGoal 不允许修改 source"** —— 这是**另一个场景**（createGoal 的去重路径，不是 updateGoal）。

**需要你确认**。

**② 是否保留原 Goal 的 source**

同上。

**③ 多条相同文本的 paused 如何选择**

**当前**：恢复 `statusSince` 最新的（2.6.2 已实现，测试④验证）。

**保持不变**。

**④ 终态记录是否参与重复识别**

**当前**：不参与（终态不阻止新建）。

**保持不变** ✅

**但**：`findSimilarGoals` 要不要包含终态的？

**建议**：**不包含**（终态是"过去的事"，不该提示"你好像记过这个"）。

## 四、并发与原子性方案

### 4.1 现有机制

```
createGoal / pauseGoal / resumeGoal
  └─ updateCompanion(fn)
       └─ withState → withFileLock（跨进程锁）
            └─ 锁内：读 → fn(cur) → 原子写
```

**所有容量检查必须在 `fn(cur)` 里**（读的是锁内的最新状态）。

### 4.2 五个并发问题逐项

| # | 问题 | 现在会不会发生 | 加了容量检查后 |
|---|---|---|---|
| 1 | 两个不同 Goal 并发创建 → 两个 active？ | **不会**（第二个会把第一个转 paused） | 不变 |
| 2 | 两个相同 Goal 并发创建 → 重复创建？ | **不会**（第二个走 `sameActive` 分支） | 不变 |
| 3 | 并发 pause / resume / create 突破容量？ | **会**（现在没检查） | **不会**（检查在锁内） |
| 4 | 容量检查与实际写入同一锁内？ | — | ✅ **必须在 `fn(cur)` 里** |
| 5 | 失败保证不写盘？ | ✅（`fn` 抛错或设置 `err` 且**不改 `cur`**） | ⚠ **要小心**（见下） |

### 4.3 关键：失败时不能改 `cur`

**现在的模式**：

```js
let err = null;
const r = updateCompanion((st) => {
  ...
  if (容量不足) { err = { code: 'CAPACITY_FULL' }; return; }   // ← 提前返回，**没改 st**
  ...
});
```

**问题**：如果容量检查在**改状态之后**，就晚了。

**所以顺序必须是**：

```js
// ① 先算出"这个操作会不会超限"（纯读，不改 st）
const willBePaused = st.goals.filter((g) => g.status === 'paused').length
  + (curActive ? 1 : 0)    // 旧 active 会转成 paused
  - (restoring ? 1 : 0);   // 被恢复的会从 paused 转出

// ② 超限就返回，**什么都不改**
if (willBePaused > MAX_PAUSED_GOALS) {
  err = { error: `已经记了 ${MAX_PAUSED_GOALS} 件搁置的事...`, code: 'CAPACITY_FULL' };
  return;
}

// ③ 通过了才动 st
```

### 4.4 `updateCompanion` 的一个细节

**看代码**：

```js
const r = updateCompanion((cur) => {
  ...
  fn(cur);
  cur.pending = tidyPending(cur.pending);
  cur.updatedAt = nowIso();
  cur.version = 2;
});
```

**注意**：即使 `fn` 只是 `return`（没抛错），`updateCompanion` **仍然会写盘**（因为 `fn` 正常返回）。

**所以**：**容量检查失败时，`fn` 里不能改 `cur` 的任何字段**。

**但**：`updateCompanion` 会改 `cur.updatedAt` 和 `cur.version`（在 `fn` 之后）→ **还是会写盘**（虽然内容几乎一样）。

**影响**：多一次无意义的写盘，但**状态没变** ✅

**要不要避免？**

**方案**：让 `fn` **抛一个特殊错误** → `withStateOnce` 的 catch → `ok: false` → **不写盘**。

**但**：抛错会让 `updateCompanion` 返回 `{ ok: false }`，和"业务失败"混在一起。

**折中**：接受"多一次写盘"（`updatedAt` 变、`_v` +1，但 `goals` 完全没变）。

**判断**：可接受。**测试要验**："容量不足时所有 Goal 的状态、history、proposal、时间字段都不变"（允许 `updatedAt` 和 `_v` 变）。

## 十、一个需要说明的实现细节

`updateCompanion` 在 `fn` 正常返回后**一定会写盘**（改 `updatedAt` / `_v`）。

**所以**：容量检查失败时，**文件会被写一次**（内容几乎一样，`goals` 完全没变）。

**要不要避免？**

**方案 A**：接受（测试验"goals 不变"，不验"文件不变"）

**方案 B**：让 `fn` 抛错 → `updateCompanion` 返回 `ok: false` → 不写盘

**但 B 会把"业务失败"和"写入失败"混在一起**，调用方分不清。

**我建议 A**，并在测试里明确写：**"容量不足时不修改任何 Goal 数据，允许 `updatedAt` / `_v` 变化"**。
