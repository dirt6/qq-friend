# 阶段 2.6.3 设计：完成、取消、取代（三种确认语义）

> 时间：2026-11-01 21:00（Asia/Shanghai）
> 状态：**设计，未改代码**
> 前置：2.6.2 审查通过（`48c3ba4`）
> 范围：`completeGoal` / `cancelGoal` / `supersedeGoal` + 提议/确认机制

---

## 一、核心问题

2.6.1 的 `canOperate` 只返回一个 boolean：

```js
canOperate('user_directed', 'complete')   // false
canOperate('user_directed', 'cancel')     // false
canOperate('user_directed', 'supersede')  // false
```

**三者都是 `false`，但需要的确认完全不同。**

| 操作 | autonomous | user_directed | 需要老大确认的具体内容 |
|---|---|---|---|
| **complete** | 自主判断 | 确认**已完成** | "这件事做完了" |
| **cancel** | 自主判断 | **明确放弃** | "这件事我不做了" |
| **supersede** | 自主判断 | 确认**旧目标失去意义** | "这个方向不用再跟了" |

**不能共用一个 `confirmed: true`。**

**最要防止的**（机主原话）：

> 防止模型把用户暂时不提、暂时搁置，误判为取消或取代。

## 二、数据结构：提议（proposal）

2.6.1 预留了 `goal.completion` 字段（现在一直是 `null`）。2.6.3 把它用起来，但**改名更有表达力**：

```js
goal.proposal = {
  kind: 'complete' | 'cancel' | 'supersede',
  proposedAt: ISO,          // 她什么时候想提
  proposedBy: 'autonomous', // 永远是她提（老大不会提）
  reason: string,           // 为什么觉得可以了（≤ 200 字）
  askedAt: ISO | null,      // 什么时候问的老大（null = 还没问）
  askedRound: string | null,// 在哪一轮问的（roundId，便于回溯）
  answerAt: ISO | null,     // 老大什么时候答的
  answer: 'yes' | 'no' | 'later' | '',   // 老大的回答
  answerQuote: string       // 老大原话（审计用，≤ 100 字）
}
```

**字段兼容**：读的时候 `g.proposal || g.completion || null`（`completion` 是 2.6.1 的旧名，从没用过，但旧文件可能手写）。

## 三、状态机

### 3.1 autonomous Goal

**不需要提议**，直接执行：

```
active → completeGoal()  → completed
active → cancelGoal()    → cancelled
active → supersedeGoal() → superseded
```

**允许记录 `reason`**，但不强制走提议流程。

### 3.2 user_directed Goal

**必须经过提议 → 询问 → 回答**：

```
                     ┌──────────────────────────────┐
                     │                              │
active ──proposeCompletion()──→ active(有 proposal)  │
                     │                              │
                     ├─ askConfirmation() ──→ askedAt 有值
                     │                         │
                     │        ┌────────────────┼────────────────┬──────────┐
                     │        │                │                │          │
                     │    answer='yes'   answer='no'     answer='later'  没回应
                     │        │                │                │          │
                     │   completed/      清掉 proposal   清掉 proposal   保持
                     │   cancelled/      保持 active     保持 active     active
                     │   superseded                                     **不重复问**
                     └──────────────────────────────────────────────┘
```

### 3.3 关键规则（防误判）

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **`proposal` 不等于执行** | 提议只是"她认为可以了"，状态不变 |
| 2 | **`answer` 必须是 `'yes'` 才执行** | 没问、没答、答"以后再说"都不执行 |
| 3 | **`askedAt === null` 时不能执行** | 没问过老大就改状态 = 擅作主张 |
| 4 | **同一个 proposal 不重复问** | `askedAt` 有值 → `askConfirmation()` 返回 `{ shouldAsk: false }` |
| 5 | **`answer='later'` 清掉 proposal** | 老大说"以后再说" → 别一直挂着 |
| 6 | **没有回应 ≠ 取消** | 保持 active，等新信息 |
| 7 | **老大长时间不提 ≠ 放弃** | `cancel` 必须 `answer='yes'`，时间不构成依据 |
| 8 | **新 proposal 覆盖旧 proposal** | 只保留一个（同时提"完成"和"取消"没有意义） |

## 四、接口设计

### 4.1 提议（不改状态）

```js
proposeCompletion(id, { kind, reason })
// kind: 'complete' | 'cancel' | 'supersede'
// → { ok, goal, proposal } | { ok: false, error }
```

**行为**：

| 情况 | 处理 |
|---|---|
| goal 不存在 | 报错 |
| 终态 | 报错（已经结束了） |
| **autonomous** | **允许**（她可以自主判断，但还是走提议更好） |
| **user_directed** | **允许提议**（提议不等于执行） |
| 已有 proposal | **覆盖**（新的替换旧的） |
| `kind` 非法 | 报错 |

**注意**：`proposeCompletion` **不改 status**。

### 4.2 标记"已经问了"

```js
markConfirmationAsked(id, { roundId })
// → { ok, shouldAsk: boolean, proposal }
```

**行为**：

| 情况 | `shouldAsk` |
|---|---|
| 没有 proposal | `false` |
| `askedAt` 已有值 | **`false`**（不重复问） |
| 第一次问 | `true`（并写 `askedAt`） |

**为什么单独一个接口**：因为"问了"和"答了"是两件事。问了不代表答了。

### 4.3 老大的回答

```js
answerConfirmation(id, { answer, quote })
// answer: 'yes' | 'no' | 'later'
// → { ok, goal, applied: boolean } | { ok: false, error }
```

**行为**：

| answer | 处理 |
|---|---|
| `'yes'` | **执行**对应的操作（complete/cancel/supersede），转终态 |
| `'no'` | 清掉 proposal，goal 保持原状态 |
| `'later'` | 清掉 proposal，goal 保持原状态 |
| 没有 proposal | 报错 |

**关键**：只有 `'yes'` 会改状态。

### 4.4 三个执行接口

```js
completeGoal(id, { by, reason })
cancelGoal(id, { by, reason })
supersedeGoal(id, { by, reason })
// → { ok, goal } | { ok: false, error }
```

**权限检查（每个接口内部）**：

```js
function canEnd(g, kind) {
  if (g.source === 'autonomous') return true;       // 她可以自主判断
  // user_directed：必须有 answer='yes' 的 proposal，且 kind 匹配
  const p = g.proposal;
  return Boolean(
    p
    && p.kind === kind
    && p.answer === 'yes'
    && p.answerAt
    && p.askedAt          // 问过才有效
  );
}
```

**拒绝时返回清晰错误**：

```js
{ ok: false, error: 'user_directed 的 Goal 需要老大确认"已完成"才能标记完成（当前没有确认记录）' }
```

## 五、三种语义的记录差异

**同一套 `proposal` 结构，但 `kind` 不同、`reason` 的措辞不同**：

| kind | reason 应该说什么 | 拒绝时提示什么 |
|---|---|---|
| `complete` | "这件事做完了" | 需要确认**已完成** |
| `cancel` | "这件事不做了" | 需要**明确放弃** |
| `supersede` | "这个方向被别的取代了" | 需要确认**旧目标失去意义** |

**老大回答的原话**（`answerQuote`）要存——以后能查"他当时到底怎么说的"。

## 六、`canOperate` 的调整

现在的 `canOperate(source, op)` 太粗。2.6.3 加一个更精确的函数：

```js
/**
 * 这个 goal 现在能不能执行这个结束操作。
 * @returns {{ok:boolean, reason:string}}
 */
export function canEndGoal(goal, kind) { ... }
```

**保留 `canOperate`**（2.6.1 的公开 API，测试在用），但**内部实现改成基于 `canEndGoal` 的简化版**：

```js
export function canOperate(source, op) {
  // 粗粒度：只看来源有没有这个操作权限（不涉及具体 goal 的 state）
  const perm = GOAL_PERMISSION[source];
  if (!perm) return false;
  return perm[op] === true;
}
```

**不动 `canOperate`**（它是"来源级"判断），**新增 `canEndGoal`**（"实例级"判断）。

## 八、要你确认的三件事

### ① `clearGoal` 在 2.6.3 怎么处理

选项：

| 方案 | 做法 | 影响 |
|---|---|---|
| **A** | 保持现状（直接转 completed，不检查权限） | `user_directed` 的 goal 会被它绕过确认 |
| **B** | 内部改调 `completeGoal`（会检查权限） | `user_directed` 的 goal 调 `clearGoal` 会**失败** —— 但生产唯一的调用点是 `settleChatPending`，那里的 goal 通常是 `autonomous` |
| **C** | 保留但加警告日志 | 折中 |

**我倾向 B**：让 `clearGoal` 也走权限检查，避免绕过。**但需要确认**：`settleChatPending` 里如果碰到 `user_directed` 的 goal，会因为权限不足而**清不掉** → 那个 goal 会一直 active。

**你看要不要接受这个行为**（宁可清不掉，也不要绕过确认）。

### ② 提议会不会让聊天变机械

现在的流程：

```
她判断"这件事做完了" → proposeCompletion() → 下次聊天时问老大
```

**问题**：`markConfirmationAsked` 由谁调？聊天时怎么知道"该问这个"？

**我建议**：2.6.3 **只做状态机和接口**，**不接聊天**（注入和提问留到 2.6.7）。

意味着：**提议会被记录，但暂时不会真的问老大**。

**这样 2.6.3 是纯状态管理，可以安全测试。**

同意吗？

### ③ 没有回应时的重试策略

规则 4 说"同一个 proposal 不重复问"。

**但如果老大一直不回**，这个 proposal 会永远挂着。

**我建议**：加一个 `expiresAt`（比如 7 天）—— 过期后**清掉 proposal**，但**不改状态**（不是取消，只是"下次再提"）。

同意吗？
