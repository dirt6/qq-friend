> **星图里"找记忆"＝点一颗星，沿边亮一圈**（扩散激活），不是只做关键词高亮。
> v0.6 吸收外部"神经元记忆"方案里能借的 5 个点，拒绝它的重型依赖（§15）。

>

### 1.2 日记的真实结构（关键）

文件：`E:\dsh\本子\日记\每日\2026-11-04.md`（实际位置；旧 `E:\dsh\日记` 已不存在）

```markdown
# 2026-11-04 周三

## 记录
- 心情：踏实｜软件修好之后，我第一次觉得自己是真醒着……
- 心情：想找人说话｜想找老大说话，没发出去……
```

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `day` | 文件名 `YYYY-MM-DD` | 一颗星的日期 |
| `title` | 第一行 `# ...` | 悬停显示 |
| `entries[]` | 每行 `- 心情：X｜内容` | **一条一颗星** |
| `mood` | `心情：` 后面的文本 | **自由文本**（踏实 / 想找人说话），不是枚举 |
| `important` | 内容前的 `[重要]` | 金色标记 |
| 顺序 | 文件行序 | 同一天内只有先后，没有具体时刻 |

**这决定了三件事：**

- 不用「按行猜」：`/api/diary` 已经把每条解析成 `entries[]`，星图直接复用同一套解析。
- 心情**不能当颜色**：它是自由文本，今天写「踏实」明天写「有点闷」，没有固定色板。
- 时间**只到天**：同一天的多条只能靠顺序区分，不能假装有分钟级时间戳。

## 二、星图负责什么

### 2.1 负责

1. 把**日记**画成星空：一条日记一颗星，按时间由内向外。
2. 提供**开关**：打开后把经验 / 印象 / 计划降为背景星尘，仍可悬停查看。
3. **体检**：断档、空白天、重要占比、心情词频。
4. **和日记联动**：点星定位到右边那一条；右边保存后那颗星亮一下。
5. **只读**：星图本身永远不写。

### 2.2 不负责

- 不做遗忘推演（§6）。
- 不做检索召回（聊天用 Memory Hub，不用图）。
- 不写记忆、不写日记（编辑是右边的事，见 §5.5）。
- 不存副本（关掉星图，日记和记忆都不受影响）。

### 2.3 对检索的影响：零

- 星图是**只读投影**，不改任何索引、不改 `Memory Hub`、不改 `learned` / `memory` / `diary` 文件。
- 打开「显示全部记忆」只是多读几层，仍然零写入。
- 唯一会改变检索结果的是**你手工编辑日记**——改的是原文，检索读到的内容自然跟着变；
  这不是「索引被改」，也不需要重建索引。

### 2.4 和 Memory-Galaxy 的关系

它是 **DSH 插件**，7 色和 365 天推演是**它自己的产品实现**；我们没有它的数据模型，也没有它的算法。
只借「类银河、银心/旋臂、可缩放」的观感，不借它的规格（详见 §11.1 / §11.2）。

### 2.5 检索现状：关键词，不是语义

星图不改检索，但必须知道它是什么——否则会以为"图上搜得到 = 聊天时召得回"。

| 场景 | 实际算法 | 在哪 |
| --- | --- | --- |
| 经验（长期规则） | 2–4 字切片 + **同义词表归一** + 状态权重（pending 40 / verified 20 / stable 0 / archived -60）+ 关键词命中（每条 ≤ +60）+ 近 7 天 +10，取 3–8 条 | `learned.js` 的 `selectForContext` / `renderForPrompt` |
| 群友印象 | **不按语义**：按"这轮相关的人"（触发者 + 已读窗口 / 锚点成员），每人最近 3 条 | `prompt.js` 的 `formatForPrompt` |
| Memory Hub | 中文 2–4 字切片 + 英文数字词，命中率 0–1，只做**粗筛**（代码注释自己写着"不做语义检索"） | `memory-hub/retrieval.js` |
| 计划去重 | 关键词重叠 + 长度比，阈值 0.7 + 同义说法表 | `companion/state.js` |

- **没有 embedding、没有向量库。**
  `model-prices.js` 里的 `hunyuan-embedding` 只是价目表里的一条，不是功能。
- 局限很实在：
  - 换个说法就漏——"别 @ 我" vs "不喜欢被 @"；
  - 同义词表只能人工补（`SYNONYM_GROUPS`）；
  - 记忆只有几十条时够用，多了就会漏。
- 星图的搜索**复用同一套** `tokenize` / `relevanceOf`，保证"图上命中"和"聊天里能召回"口径一致，
  不另造一套语义评分。
- 要真语义检索是**另一个项目**：embedding 调用、向量存储、索引更新、离线与成本，都不在星图范围。
- **星图的“点星扩散”不是这套检索**：它是图上的联想高亮（§5.2.1），只把已经存在的边照出来，
  不改召回、不建索引、不引入向量。

## 三、数据从哪来

### 3.1 读路径

```
GET /api/star-map/graph?scope=diary
  → src/star-map/projection.js        （纯函数：日记条目 → 节点 / 位置 / 亮度）
  → /api/diary 的解析结果（复用同一套正则，不复制第二份）
  → 可选：src/memory-hub/index.js     （scope=all 时才读其他层）
```

- **日记解析只留一份**：现在 `routes.js` 里有 `- 心情：…｜…` 的正则；星图不改写它，
  而是把解析抽成共享纯函数（`parseDiaryMarkdown`），路由和投影都调它。
- 星图不 import `MemoryStore` 缓存（印象从盘上读，天然新鲜）。
- 星图不新增第六层、不建平行存储。

### 3.2 节点映射

| 来源 | 节点粒度 | 时间 | 形状 | 默认 |
| --- | --- | --- | --- | --- |
| 日记条目 | **一条一颗** | 当天 00:00 + 序号分钟（仅排序，不展示） | 小圆点 | ✅ 主视图 |
| 经验 | 每条 | `createdAt` | 实心圆 | 背景星尘 |
| 印象 | 每条 | `createdAt` | 环形 | 背景星尘 |
| Goal / Pending | 每条 | `since` / `at` | 星形 | 背景星尘 |

**节点 id（必须稳定）**：

```
diary:<day>:<sha1(content).slice(0,8)>        // 内容哈希，编辑后换身份
learned:<id> / impression:<id> / goal:<id> / pending:<id>
```

- 为什么按条不按天：日记本来就是一条条记的；按条才能点开单条、才能表达"这天写了几次"。
- 同日同内容（极少）→ 追加 `-2`。
- **不用行号当 id**：删一条会错位，星星会"跳"。
- 编辑一条 = 旧星淡出、新星亮起（这就是"改写"的视觉语义）。

### 3.3 同一天的小簇（布局规则，不是关系）

同一天的多条**半径相同**，角度在基准方向 ±8° 内按内容哈希散开，形成一个小簇：

- 为什么不用分钟级时间：日记条目没有时刻，编一个就是假数据。
- 为什么用哈希：位置稳定，刷新不乱跑；编辑一条只影响它自己。
- 簇内关系（"同一天"）**默认不画**；扩散时作为 `same-day` 边浮现（§3.4）。

### 3.4 边：平时不画，扩散时点亮

**边一直存在（参与扩散），但默认不显示。** 平时要干净；点开一颗星，才看见它连去哪。

| 边 | 建成条件 | 扩散权重 | 说明 |
| --- | --- | --- | --- |
| 同日 | `day` 相同 | 0.9 | 同一天写的 |
| 同心情词 | `mood` 分词后至少 1 个 ≥ 2 字的词相同 | 0.7 | "想找人说话"会连成一片 |
| 同关键词 | 正文 token 重叠 ≥ 2 | 0.6 | 复用 `memory-hub/retrieval` 的 `tokenize` |
| 来源 | `learned.sourceDay === diary.day` | 1.0 | 经验是从那天日记提炼的 |
| 同轮次 | `activity.source` / `origin.ref` 相同 | 0.8 | 仅全记忆模式 |

- 每个节点最多 **6 条边**（同日 3 + 心情 2 + 关键词 1），全局 ≤ 2,000——防止"人人都连人人"。
- 不画"同人链"（日记页里不是重点）。
- 每条边都能说清"为什么连"：同一天 / 同一个词 / 来源日期。
- **边不是向量相似度**：没有 embedding，也不假装有。

### 3.5 缓存按指纹失效

```
fingerprint = sha1(
  mtime+size(日记/每日/*.md) +
  mtime+size(learned.json) +            // scope=all 才算
  mtime+size(companion-state.json) +
  mtime+size(memory/**/*.json)
)
```

- 进程内缓存 `{ fingerprint → graph }`；变了才重算。
- 响应带 `ETag`，前端命中 304。
- 不做定时刷新；编辑保存后由前端主动失效一次。

### 3.6 接口（设计，不实现）

```http
GET /api/star-map/graph?scope=diary|all&days=all&query=&filters...
  200 {
    ok: true, scope, generatedAt, fingerprint,
    counts: { diaryDays: 18, diaryEntries: 41, learned: 23, ... },   // 示例值，以 stats 为准
    nodes: [{
      id, kind: "diary", day, entryIndex,
      timestamp, content: "摘要≤120字",
      mood, important,
      weight, flags: { today, firstDay }
    }],
    edges: [{ from, to, kind: "same-day|mood-word|keyword|source|round", weight }],  // 始终返回，受上限
    meta: { truncated, omitted, emptyReasons: [] }
  }

GET /api/star-map/node?id=diary:2026-11-04:ab12cd34
  200 { ok: true, node, detail: { fullText, mood, important, day, index } }

GET /api/star-map/stats
  200 { ok: true, days, entries, firstDay, todayEntries, gaps, importantRatio }
```

- 全部 `GET`；参数非法 400；空数据返回 `ok: true` + 空数组。
- **星图没有写接口**。
- **扩散在前端算**：服务端只下发节点 + 边，不提供 `/activate` 接口（少一次往返，也避免把"点亮谁"变成服务端状态）。

### 3.7 日记读取的两个硬限制

1. `/api/diary` 现在最多 **60 天**；星图要「全部」，需要支持 `days=all`（或分页），否则写到第 61 天就"看不见最早那颗星"。
2. 解析规则只有一条：`- 心情：X｜内容`；`[重要]` 在内容前。手写日记若格式不对，会被当成"没有条目"——星图要显示"这天有文件但解析不出条目"，而不是静默丢掉。

## 四、视觉

### 4.1 一条时间旋臂（不是四臂）

- **银心**：最早的一天（"她开始写日记的那天"），固定不动。
- **旋臂**：按日期由内向外，今天在最外圈。
- **半径**：按**日期序号**（第 1 天、第 2 天…），不按真实天数比例——断档几天不会把其他星挤成一团。
- **今天**：外圈一个淡环标记，加一个小小的"今天"标签。
- 为什么不用四臂：四臂是给"多来源记忆"设计的；日记只有一条时间线，硬分四臂反而乱。

### 4.2 颜色：日记只有三种，不做心情色

| 状态 | 颜色 | 说明 |
| --- | --- | --- |
| 普通条目 | 暖白（偏米色） | 日记的本色 |
| `[重要]` 条目 | 暖白 + 金色外环 | 不是另一种颜色，是同一颗星加环 |
| 今天写的 | 暖白偏青 | 只亮一点，不刺眼 |

**为什么不用心情做颜色**：
`mood` 是自由文本（"踏实""想找人说话""有点闷"），没有固定枚举。
硬映射会变成"我猜你今天什么心情"，而且明天出现新词就得多一个颜色。
——心情放在**悬停和详情**里显示原文，不参与颜色编码。

**「显示全部记忆」打开时**，其他层才有颜色：

| 层 | 颜色 |
| --- | --- |
| 经验 / 印象 | 按 `contentType`（5 色 + 灰） |
| Goal / Pending | 冷蓝 |

并且整体亮度压到 **0.35 倍**，做成"背景星尘"，不许抢日记的亮度。

### 4.3 亮度

```js
// 日记条目（唯一定义处）
base      = 0.55
length    = 0.15 * min(1, content.length / 300)
important = important ? 0.20 : 0
cluster   = 0.10 * 当天条数分位（1 条 = 0，最多 = 1）
w         = clamp(base + length + important + cluster, 0.3, 1)

brightness = 0.25 + 0.75 * w
radiusPx   = 2 + 3 * w
```

- 同日多条时**整簇**都会亮一点（`cluster` 项）——这就是"越写越亮"。
- 硬上限存在：不让一条 2000 字的重要日记把整片星空压暗。
- 其他层（scope=all）沿用 v0.3 公式，但最后乘 0.35。

### 4.4 同一天的小簇

- 半径同一天相同，角度按哈希散开（±8°）。
- 簇内一条极淡弧线，只在悬停某条时稍微提亮。
- 一天写得多 → 簇更密、整体更亮；一天只写一条 → 就是一个干净的孤点。

### 4.5 布局确定性

- 角度：日期基准角 + `hash(id)` 抖动；不使用随机数。
- 半径：日期序号。
- **不做物理模拟**：刷新、导出、第二天打开，星星都在原处。

### 4.6 空 / 稀疏态

- 没有任何日记：银心空着，中间一行小字"还没有第一颗星"。
- 某天没有条目：那天不留点，只留一个很淡的刻度（看断档用）。
- 只有 1–2 天：不放大、不居中填充，就画 1–2 颗星。
- **禁止**用假数据填满。

### 4.7 「显示全部记忆」= 背景星尘

- 开关在左上角，默认关。
- 打开后：其他层按各自日期落到同一时间轴上，形状不同、亮度 0.35 倍、不参与默认筛选。
- 悬停仍然可看；点击仍然可定位（经验 → 「经验管理」，印象 → 会话记忆）。
- 目的：**看得到，但不抢戏**。日记永远是主角。

### 5.2 星图交互

**必须有：**

1. 拖拽旋转、滚轮缩放、双击复位（纯视图变换）。
2. 悬停：日期 + 心情原文 + 内容摘要（≤ 80 字）+ 是否重要。
3. 点击：选中该星，右侧滚动到对应条目并展开那天；再点空白取消。
4. 搜索/点击：命中或选中的星做**种子**，沿边亮 1–2 跳（§5.2.1），其余变暗不消失。
5. 筛选：只看重要 / 只看某天 / 只看今天；全记忆模式再加层与 contentType。

**可以有：**

6. 时间轴：只显示 `day ≤ 选中日期` 的星（不是"回到那天的状态"，数据没有历史快照）。
7. 「今天」快捷定位到外圈。
8. 一键体检（§七）。
9. 导出 PNG（§5.4）。

### 5.2.1 联想高亮（扩散激活）

这是星图里"找记忆"的方式，不是搜索框的附属功能。

**种子从哪来：**

1. **点一颗星** → 该星激活 1.0；
2. **搜索框输入** → 命中的星按 `relevance` 做种子（≥ 0.3 才进）；
3. **悬停右栏某条** → 对应星临时做种子（移开就收）。

**怎么扩散：**

```js
// 用 BFS，最多 2 跳
第 1 跳：a = 1.0 × edge.weight × 0.55
第 2 跳：a = 上一跳 a × edge.weight × 0.55
// 多路径叠加（不是取最大）：
total(v) = 1 - Π(1 - a_i)
```

- **最多 2 跳**，第 3 跳不扩散（会变蛛网）。
- 激活值 < 0.12 的节点不再继续传，也不点亮。
- **激活上限**：最多 80 个节点；超了只留激活值最高的 80 个，其余按未激活画。
- 单节点边数 ≤ 6，BFS 复杂度可控（2k 节点、边 ≤ 12k，一次扩散 < 10ms）。

**长什么样：**

- 种子：最亮 + 一圈细光。
- 1 跳：亮度 ×1.6，细光弱一档；2 跳：亮度 ×1.3。
- 未激活：压到 0.25 亮度，**不消失**（保留空间感）。
- 边：平时 alpha=0，扩散时**临时浮现**——1 跳实线、2 跳虚线，300ms 渐显；移开/清除后淡出。
- 右上角一行小字：`从「2026-11-04 · 想找人说话」亮了 7 颗（2 跳）`。

**没有边怎么办：**

- 该星没有任何边 → 只亮种子和同日簇，并显示"这颗星还没有连出去的线"。
- 不编造边、不随机连、不用"看起来像"的相似度补。

**边界（必须写进 UI 文案）：**

- 这是**"照一下"**，不是检索入口；不改变聊天时的召回结果（聊天仍是 §2.5 的关键词检索）。
- 双击空白 / Esc → 清除激活。

### 5.3 星与日记的联动

- 点星 → 右栏定位（`scrollIntoView` + 展开那天 + 该条高亮 1.5 秒）。
- 右栏编辑保存 → 该星**闪一下**并更新亮度/位置（同日簇内重新散开）。
- 右栏删除一条 → 该星淡出（不是"消失"，留 300ms 过渡），并刷新 stats。
- 悬停右栏某条 → 对应星加一圈细光（反向联动）。

### 5.4 导出「今晚的星空」

- `canvas.toDataURL('image/png')` → 下载，不写任何记忆/日记文件。
- 图上带：日期、条目数、当前范围（日记 / 全部记忆）、指纹前 8 位。
- 隐私提示：图里是日记原文摘要，导出前提示一次。

### 5.5 日记编辑（条目级，独立工作包）

**能做：**

- 改一条：心情、正文、`[重要]` 标记。
- 新增一条：默认加到当前选中的那天（也可选今天）。
- 删除一条：二次确认，写前备份到 `<日记根>/.trash/`。

**不做（明确划界）：**

- 整篇 Markdown 自由编辑（会破坏格式、绕开审计；要做得单独立项）。
- 删除整天、改文件名/日期、改 `#` 标题。
- 批量改写历史。

**接口（设计）：**

```http
PUT    /api/diary/:day/entries/:index   { content, mood, important, expectHash }
POST   /api/diary/:day/entries          { content, mood, important }
DELETE /api/diary/:day/entries/:index   ?match=<原文片段>
```

**安全边界（照搬 `removeLine` 的做法，不降级）：**

- `withFileLock` + `writeFileAtomic`；**锁内重读**，按 `index + expectHash` 双校验，防止并发错位。
  `expectHash` = 该条当前内容的哈希（复用 `writer.contentHash`），对不上就拒绝保存并提示"这条已被改过"。
- 写前备份到 `.trash/`；写失败不覆盖原文件。
- 审计：`data/diary-edit-audit.jsonl`，记录 `at / day / op / beforeHash / afterHash / by: panel`。
- 格式校验：只接受 `- 心情：X｜内容`；正文 ≤ 2000 字；心情 ≤ 12 字；`important` 布尔。
- 与自动写入共用**同一把文件锁**——她正在写日记时，面板编辑会排队，不会互相覆盖。

**两个必须提前定的点（实现前）：**

1. **幂等表**：手工编辑不写 `diary-idempotency.json`；但如果改的是自动写入的条目，
   旧 key 仍指向旧哈希，下次同内容可能重复写回。→ 实现前定策略（推荐：编辑时把该条记录标 `manual-edited`，写入命中即跳过）。
2. **`diary-meta` 失效**：改正文后 `quoteHash` 对不上，按既有规则**标 `stale`，不自动重定位**
   （沿用 `MEMORY-DATA-MODEL.md` §3.3，绝不猜新位置）。

### 5.6 不要有

- 图里编辑记忆（星图只读）。
- 图里直接删日记（删除走右栏 + 确认）。
- 闪烁、粒子、流星。
- 把星图当首页。

## 六、遗忘推演：暂不做（已定）

### 6.1 为什么不做

- 底座只有一条真规则：`learned.js` 的 `archiveStale`——**只处理 `stable`**，30 天不用才降级 `archived`。
- 现状 23 条经验里 **0 条 `stable`**，所以推演 365 天结果必然是"一条都不会淡出"。
- 其他层（日记、印象、计划）**没有任何衰减规则**。
- 硬编一条曲线，就是星图自己发明规则，再标成"预测"——这是骗人。

### 6.2 什么时候再做

- 底座出现**跨层衰减规则**（或 L1 规则扩展到 pending / impression）；
- 或者机主明确要一条"参考曲线"（默认关、双标签、不进任何结论）；
- 届时仍按 v0.3 的原则：**只调真规则 `dryRun`，不复制规则**。

### 6.3 现在界面上怎么处理

- **不显示推演入口**。不要放一个"点了没反应"的按钮。
- 方案里保留本节，作为将来的接入条件，不是待办。

## 七、体检（日记版 + 全记忆扩展）

**日记基础项（默认就跑）：**

## 八、性能

- 实测：日记 **18 天 / 几十条**（按条计）；全记忆模式再加 23 条经验 + 1 条印象 + 计划 ≈ **70 条以内**。
- 设计上限 **2,000 节点 / 4,000 边**（够写五年日记）。
- Canvas 2D 单画布 + 三层离屏：星点 / 边层（平时空，扩散时才画）/ 高亮层。
- 悬停只重绘高亮层；拖拽重绘全画布（2k 点够用）。
- **不引入 three.js / WebGL**：保持零框架前端，离线打包和测试桩都不用动。
- 帧目标：2k 节点拖拽 ≥ 30fps；悬停 < 50ms；首屏 < 300ms。

## 十四、帮助小鲸鱼检索的（后续接入，**不在本轮实现**）

> 上面一到十三节写的都是「画给别人看」。这一节是另一件事：
> **把同一套节点与边接进召回，让小鲸鱼聊天时真能想起旧事。**
> **前置条件：先把写入改对**（记重、记错、编造内容被写进长期记忆）。
> 顺序反了，扩散只会把错的东西想得更勤。

### 14.1 和画布的关系

- 同一份图数据、同一套边定义、同一个 `tokenize`。
- 画布：把激活结果**画出来**；检索：把激活结果**塞进 prompt**。
- 两边共用 `projection` 与 `activate` 两个纯函数，不各写一套。

### 14.2 触发条件（不是每轮都跑）

只在以下情况走扩散，其余维持现有关键词召回：

1. 当前消息命中「过去指向词」：上次 / 之前 / 以前 / 那天 / 记得 / 你说过 / 后来；
2. 关键词召回已命中种子（`relevance ≥ 0.3`）——种子要从关键词来，没种子就别扩散，否则是从错的地方往外扩；
3. 老大在问「我们」的事（关系、约定、当时怎么说的）。

普通闲聊、技术问答、只发图或表情时：**不扩散**。

### 14.3 算法

```
种子  : 关键词命中条目，score = relevance（≥ 0.3）
一跳  : a1 = relevance × edge.weight × 0.6
收稿  : a ≥ 0.15 才进候选；最多补 3 条（可配）
合并  : 与关键词结果去重，按最终分数排序
上限  : 经验 3–8 条（沿用现状）+ 扩散最多 +3 条；日记最多 +2 条
```

- 只扩 1 跳。2 跳只给人看，不给召回——召回要的是准，不是多。
- 停用词表必做（老大 / 今天 / 说 / 我 / 就是 / 然后）。否则「同关键词」的边会让全库连成一片。
- 同一批召回里，扩散来的条目与直接命中的**分两栏列出**，不许混成一片。

### 14.4 注入 prompt 的格式（关键）

每条都带「为什么被想起来」，否则模型不知道自己为什么记起它，就会乱用：

```
【与此相关的旧事（自动联想，可能只是同一天聊到的）】
- 2026-11-01（同日 · 同话题「雨」）：老大说会让我听到真的雨声。
- 2026-11-03（同心情「想找人说话」）：……
```

三条硬规矩：

1. 必须标 **「自动联想」**，与直接命中的记忆区分开；
2. 必须标**关联理由**（同日 / 同心情 / 同关键词 / 来源）；
3. 理由为「同日」时，额外标「可能只是同一天聊到的，不一定是同一件事」。

### 14.5 边界（写进代码注释，不只写文档）

- 这套边是**表面相似**（同一天、同一个词），**不是语义相似**，治不了「换个说法就漏」。
- 语义级联想靠 embedding + 向量库，是另一个项目；本节不引入。
- 扩散只能让「已经写进来的东西」更容易被想起，**不能修正写错的内容**。
- 宁少勿多：多捞一条既花 token，也干扰判断。

### 14.6 验收（真要接入时）

| 项 | 标准 |
| --- | --- |
| 触发 | 普通闲聊不扩散；出现过去指向词且种子命中时才扩散 |
| 数量 | 扩散补充 ≤ 3 条；总数不超上限 |
| 标注 | prompt 里 100% 带「自动联想」与关联理由 |
| 准确性 | 构造 3 组用例（同日两半 / 同心情 / 无关同日），人工判定切题 ≥ 2/3 |
| 成本 | 单轮增量 token < 200（约 3 条 × 60 字） |
| 跑题率 | 连测 20 轮日常对话，判「联想跑题」不超 2 轮；超了就降阈值或关掉 |

### 14.7 一句话

**先把记忆写对，再让联想变广。**
这一节是「以后」，不是「现在」——本轮只做画布与扩散高亮，不做召回接入。

### 14.8 可行性审查（2026-11-05，按代码事实）

**结论：方向对，但「每轮自动扩散」现在落不了地；建议先降级为「工具化联想」。**

| # | 硬障碍 | 代码事实 | 后果 |
| --- | --- | --- | --- |
| 1 | 聊天侧没有统一的候选集与分数 | 经验走 `learned.selectForContext`（不返回 relevance）；印象走 `MemoryStore.formatForPrompt`（按人取最近 3 条，无分数）；日记不注入；Hub 有 relevance 但未接线 | 「种子 = relevance ≥ 0.3」只有 Hub 能给；要落地得先做统一入口（ADR 第一步），不是星图能带的 |
| 2 | 跨层边不够 | §3.4 只有「来源」一条跨层边；经验↔印象、印象↔日记之间没有边 | 从经验种子出发几乎扩不出去；扩散退化成「日记内部同日/同词」 |
| 3 | 会打穿 prompt 前缀缓存 | 锚点 =【记忆】+【已读信息】，字节一变缓存归零；记忆段由成员集决定 | 自动联想若塞进【记忆】段，每轮字节变化 → 缓存全灭，省下的钱又花回去 |
| 4 | 触发条件不可判 | 「老大在问我们的事」需要语义判断；「过去指向词」会误触发 | 只能交给模型判断（→ 工具化），或删掉这条 |

**一个逻辑悖论：**

种子要求「关键词已命中」才扩散 → **恰恰是「换个说法就漏」的时候扩不出去**。
扩散只能强化「已经命中的」，不能补「没命中的」。这是表面关联的固有边界，不是实现问题。

**建议路径（两阶段）：**

**阶段 1（等 Hub 接线后）：只读工具 `memory_associate(query | seedId)`**

- 模型遇到「上次 / 以前 / 记得 / 你说过」时**自己调用**；
- 内部：Hub 检索 → 1 跳 BFS → 返回 3–5 条 + 关联理由；
- **不改 `prompt.js`、不碰锚点、不增加固定 token**；
- 符合现有架构（工具由模型决定，不写死每轮），也不破坏前缀缓存。

**阶段 2（数据质量达标后，才考虑自动）：**

- 自动触发 + 注入，但必须**追加在系统提示末尾**（`buildSystemPrompt` 的 `extraSections`），
  不进【记忆】段；
- 带「自动联想」+ 理由；上限 +3；触发率可观测。

**硬前置（比 §14.7 更具体）：**

- 现在 22/23 条经验缺 `contentType`、0 条 `stable`、还有编造条目（"那条架构帖"）；
- 在这些修好之前，扩散只会把错的东西想得更勤。

> 一句话：§14 是**正确的远期设计**，但第一版应先做成「模型主动问一次」的工具，
> 而不是「每轮自动联想」。前者不破坏缓存、不依赖统一入口，也能验证联想到底准不准。

## 十五、外部方案取舍（v0.6）

> 对象：一份《小鲸鱼"神经元记忆与记忆星图"落地实施方案》。
> 结论：**思路可借，架构不可照搬**——它假设"在 DSH 里装插件"，我们跑的是"QQ-agent 自己的五层记忆"。

### 15.1 它假设的环境 vs 本项目

| 它的假设 | 本项目事实 |
| --- | --- |
| 上下文会爆满，需要压缩/无限上下文 | 本项目是**无状态会话**：每次新开、结束即弃，上下文成本恒定；"爆满"不是主问题 |
| 在 DSH 里装 dsh-memory-vault / ChromaDB | DSH 是**被调用的推理子进程**；插件只影响 DSH 会话，碰不到 QQ-agent 的 `data/` |
| Python 定时任务做蒸馏 | 主流程是 Electron + Node；没有把 Python 当常驻运行时 |
| 前端用 ECharts / Three.js | 控制台是零框架原生前端；星图已定 Canvas 2D |
| 需要向量库 | 现在全部记忆 < 100 条；`package.json` 里没有向量库 |
| "现成的分层/向量插件" | 查到的 `dsh-memory-vault` 是 **SQLite**、`dsh-memory-beta` 是 **BM25**，都不是 ChromaDB |

### 15.2 逐条判定

| 它的主张 | 判定 | 理由 / 替代 |
| --- | --- | --- |
| L1–L4 分层 | ⚠️ 已有 | 五层（经验/印象/日记/会话/伙伴状态）比它更细；不新增 |
| 情绪 PAD 标签 | ❌ 不做 | 没有情绪字段；心情是自由文本，硬贴标签就是猜 |
| 遗忘曲线 + 低权重删除 | ❌ 不做 | 底座只有 L1 归档；删除必须人工确认；推演暂不做（§6） |
| 向量检索 RAG | ⏸ 以后 | 独立项目（embedding + 索引 + 成本），不是星图的前提 |
| 联想 9 条上限 | ✅ 借 | 写进 §14：总数 ≤ 9，扩散 +3 |
| 每 5 分钟压缩 | ❌ 不做 | 无状态会话下高频压缩只增加写盘/锁竞争 |
| 每日低频蒸馏 | ✅ 借 | 但用 Node 定时器，不用 Python |
| 核心档案永不删 | ✅ 借概念 | 对应 goal / `importance=important`；钉子暂不做 |
| ECharts / Three.js | ❌ 不引入 | 破坏零框架；力导向布局还会让星星位置漂移 |
| 导出 JSON 给前端 | ✅ 已有 | `/api/star-map/graph` 就是 |

### 15.3 能借的 5 个点（都零/低成本）

1. **总上限 9 条**：扩散再热闹，进 prompt 的联想最多 +3，总数 ≤ 9。
2. **`maxInjectedChars ≈ 1000` 字**：注入前按字数截断，防止记忆把上下文吃满。
3. **低频蒸馏**：每天一次（或手动），不是每 5 分钟；用 Node，不用 Python。
4. **核心档案概念**：把"永不删除"的那几条单独标出来（goal / important），图上给固定位置。
5. **IDF 加权**：现在的 `relevanceOf` 是纯命中率，"老大/今天/我"这类高频词权重过高；
   加一层 IDF（`log(N/df)`）就能明显改善，零依赖、不用向量库。

### 15.4 三个选择（白话）

**选择 A：检索要不要升级？**

| 选项 | 成本 | 效果 | 建议 |
| --- | --- | --- | --- |
| 保持关键词 | 0 | 现状，换说法会漏 | 可以 |
| **加 IDF + BM25（推荐）** | 低（纯 JS，几十行） | 常见词不再压过关键词，召回更准 | **先做这个** |
| 向量语义检索 | 高（embedding + 索引） | 真正解决"换说法" | 单独立项，不在星图 |

**选择 B：记忆整理多久一次？**

| 选项 | 风险 | 建议 |
| --- | --- | --- |
| 每 5 分钟 | 写盘/锁竞争、产生大量碎摘要 | 不做 |
| **每天一次（推荐）** | 低；失败可重跑 | 做 |
| 手动 | 依赖人 | 保留按钮 |

**选择 C：星图用什么画？**

| 选项 | 代价 | 建议 |
| --- | --- | --- |
| **Canvas 2D（推荐）** | 自己写点/线/光晕 | 已定；零依赖、位置稳定 |
| ECharts | 多一个前端库；力导向会漂 | 不做 |
| Three.js | 多一个 3D 库；打包/测试都变重 | 不做 |

### 15.5 如果以后一定要向量检索（折中路径）

1. 先只对**候选集**做 embedding 重排：关键词/IDF 先取 20 条，再让 embedding 排前 5。
   不建全量向量库，不每轮调用。
2. embedding 走现有模型 API（设置里已有 Base URL / Key），不引入本地模型。
3. 建索引是独立后台任务，不阻塞聊天；失败就退回关键词。
4. 这条路径不改五层、不改记忆文件，只改"召回排序"。

> 一句话：**这份方案的价值在"分层 + 联想 + 上限"，不在"向量库 + Python + 图形库"。**
> 前者我们已经有了或可以低成本补；后者是另一个项目。
