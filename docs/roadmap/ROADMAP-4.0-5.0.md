## 一、4.0：统一伙伴架构

### 1.1 目标

> **把「各模块能跑」变成「一个人格、多个 Session、共享记忆、统一权限」。**
>
> 统一伙伴决策（2026-11-03）补充：**共享记忆 = 同一伙伴内所有行为共用一个记忆与状态核心**；不同 PROFILE 是运行隔离，不是伙伴身份，不共享记忆。

### 1.2 范围（R6 + R7）

| 批次 | 内容 |
|---|---|
| **R6** | DSH Session 迁移（自主活动从"每轮 spawn"变成"独立长活 Session"） |
| **R7** | 工具注册、权限统一、**记忆管理入口** |

### 1.3 R6：DSH Session 迁移

#### 现状（实测）

```
调用方式：spawn('cmd', ['/c', dsh.cmd, '--profile', 'headless', '--patch', ..., '--json', '--session-id', sid, '-'])
gateway 接口：ask / hasSession / resetSession / listSessions / buildBody / recordDshCall
Session 存储：data/dsh-home/sessions/（2 个子目录）
```

**每次自主活动都是一个新的 headless 调用**（`--json` 流式返回）。

#### 目标

**建一个独立的 `companion-autonomous` session**，自主活动在里面跑，**而不是每轮新 spawn**。

#### 四个内部批次

| 批次 | 内容 | 产出 |
|---|---|---|
| **R6-A** | **盘点本地 rc.2 的真实 Session API** | 接口清单（不假设 rc.5） |
| **R6-B** | 建 Session Adapter，隔离 DSH API 与业务逻辑 | `src/session-adapter.js` |
| **R6-C** | 双路径验证、恢复测试、并发隔离测试 | 测试报告 |
| **R6-D** | Go/No-Go 通过后迁移，保留原 API 回退 | 生产切换 |

#### 五项硬门槛（不通过就回退）

| # | 条件 | 怎么验 |
|---|---|---|
| 1 | Session 能可靠恢复 | 进程重启后 session 还在，能继续 |
| 2 | 两个 Session 不污染 | 聊天 + 自主同时跑，上下文互不串 |
| 3 | 工具不重复执行 | 同一动作不会执行两次 |
| 4 | P95 延迟满足预算 | 短 ≤ 60s / 长 ≤ 120s（沿用 0.1 基线） |
| 5 | Token 可统计 | `model-calls.ndjson` 有记录 |

**任一不过 → No-Go → 回退原 `ask()` 路径。**

#### Session 生命周期所有权（必须唯一）

**现在**：QQ-agent 管理 `data/dsh-sessions.json`（chatKey → sessionId 映射），DSH 管理 `data/dsh-home/sessions/`（实际会话文件）。

**这是两个系统各管一半。**

**R6 必须定清楚**：

| 操作 | 谁负责 |
|---|---|
| 创建 | **DSH 创建，QQ-agent 只记映射** |
| 恢复 | **DSH 恢复，QQ-agent 传 sessionId** |
| 结束 | **QQ-agent 决定何时结束，DSH 执行** |
| 清理 | **DSH 自己按 TTL 清理，QQ-agent 不删** |

**原则**：**会话文件是 DSH 的，映射是 QQ-agent 的，两边不交叉管理。**

### 1.4 R7：工具注册、权限统一、记忆管理入口

#### 现状（实测）

```
工具：QQ-agent 原生 + 16 个 qq_* 前缀
权限：面板有 ACL（RETIRED_MEMORY_WRITES 退役了 4 个记忆写入口）
记忆管理入口：**不存在**（面板四个按钮全部 403）
```

#### 三个子目标

##### ① 工具注册表

统一描述协议：

```js
{
  name: 'chat.send',
  domain: 'messaging',
  modes: ['chat', 'autonomous'],   // 白名单
  permission: 'external_action',
  description: '发消息给指定会话'
}
```

##### ② 权限模型

**四级权限**（机主 2026-11-02 定的）：

| 级别 | 含义 | 默认策略 |
|---|---|---|
| `read` | 读取信息 | 允许 |
| `write` | 修改内部数据 | 按配置 |
| `external_action` | 对外发布、发送消息 | **用户确认** |
| `destructive` | 删除、覆盖、不可逆 | **明确确认** |

**关键**：**每次工具调用都必须重新检查权限**（不能因为 Session 启动时有权限就整会话放行）。

##### ③ **记忆管理入口**（P0 遗留的功能空缺）

**这是 R7 必须交付的**，因为：

- R7 的 `RETIRED_MEMORY_WRITES` 把面板 4 个记忆写入口全退了
- **但替代的"记忆管理面板"一直没做**
- 用户现在**没有任何方式删除/归档经验**

**R7 要做的**：

| 操作 | 后端 | 权限 | 审计 |
|---|---|---|---|
| 改经验状态 | `learned.setStatus` | `write` | 记 `acl.jsonl` |
| 归档经验 | `learned.archiveStale` | `write` | 同上 |
| 改经验内容 | `learned.saveItem` | `write` | 同上 |
| **删除经验** | `learned.removeItem` | **`destructive`** | **必须用户确认 + 记审计** |

**同时**：**Memory Hub 的读取入口**（R4 已做）要接到面板上。

### 1.5 4.0 阶段验收

| # | 标准 |
|---|---|
| 1 | R6 Go/No-Go 通过，或 No-Go 且已回退 |
| 2 | Session 生命周期所有权唯一 |
| 3 | 工具按 `read` / `write` / `external_action` / `destructive` 分级 |
| 4 | **记忆管理入口可用**（改状态 / 归档 / 改内容 / 删除） |
| 5 | 删除操作有用户确认 + 审计 |
| 6 | 失败不伪装成功 |

## 二、5.0：长期自主伙伴

### 2.1 目标

> **从「能自主活动」到「长期可靠地自主」，并且不靠频繁调用模型或频繁打扰来证明存在感。**

### 2.2 范围（R8 + R9 + R10）

| 批次 | 内容 |
|---|---|
| **R8** | 自主规划与执行（从"每轮决定做什么"到"有节奏的长期规划"） |
| **R9** | 长期记忆治理（让记忆从"不断积累"变成"持续准确"） |
| **R10** | 主动交流与长期运行 |

### 2.3 R8：自主规划

> 统一伙伴决策（2026-11-03）：R8 的规划能力属于**同一个伙伴**的自主行为，不是第二个 AI。Goal/Pending/Round/Action 与聊天共享同一套伙伴状态，不新建第二套记忆；**R8-C（记忆治理）保留**。见 `ARCHITECTURE-UNIFIED-COMPANION.md`。

#### 硬约束（机主明确）

> **沿用现有 Goal / Pending / Action / Round 生命周期，不重新定义平行对象。**

| 对象 | 定义 | 时间尺度 |
|---|---|---|
| Goal | 长期方向 | 周/月 |
| Pending | 未完成事项 | 天 |
| Round | 一次活动 | 单次 |
| Action | 一次执行 | 即时 |

**R8 不能创造第五种对象。**

#### 四个内部批次

| 批次 | 内容 |
|---|---|
| R8-A | 规划数据模型与生命周期（**复用** Goal/Pending） |
| R8-B | Goal、Pending、Action 与规划关联 |
| R8-C | 计划拆解、执行、结果评估 |
| R8-D | 中断恢复、计划调整、长期观察 |

#### 必须有明确的停止条件

> 连续几轮没有进展 → **降低优先级或暂停**，不是无限循环。

### 2.4 R9：长期记忆治理

#### 六条核心原则（机主明确）

1. **用户明确说过的内容与模型推断必须区分**
2. **不能因为重复出现就自动认定为事实**
3. **不能自动覆盖用户明确纠正过的内容**
4. **重要记忆不能仅因为长期未被检索就删除**
5. **需要保留来源、修改历史和可追溯性**
6. **重要或存在歧义的修改，交给用户确认**

#### ⚠️ R5 日记元数据写入的启用前提

**R5-D 的 `QQ_DIARY_META_WRITE` 当前默认关闭。**

**机主明确**：

> 在 R9 正式使用长期记忆维护之前，**单独评估是否启用日记元数据生产写入**。
> 启用前先做小范围验证、备份和回退演练。

**所以 R9 必须有一个独立的 Go/No-Go**：

| 前提 | 检查 |
|---|---|
| R5 写入链路已在观察期验证 | 至少 N 轮真实数据 |
| W1 / W2 / 陈旧锁已修 | 已完成（R5-A/B/C） |
| 备份和回退演练 | 隔离目录演练通过 |
| 生产影响可控 | 小范围启用 → 观察 → 扩大 |

**不通过就不启用。**

### 2.5 R10：主动交流与长期运行

#### 核心区分（机主明确）

| 不等于 | |
|---|---|
| 发现了内容 | **不等于**一定要分享 |
| 有了想法 | **不等于**一定要调用模型 |
| 可以执行 | **不等于**一定有权限执行 |
| 完成一次自主活动 | **不等于**一定要给用户发消息 |

#### 必须评估的指标

| 指标 | 说明 |
|---|---|
| **主动询问频率** | 每天主动问了几次 |
| **重复询问率** | 同一件事问了几次（P0 已修，R10 要看效果） |
| **静默等待** | 静默后是否真的不再问 |
| **用户打断/纠正频率** | 用户主动打断或纠正的次数 |
| **成本** | 每日 token / 费用 |

#### 长期运行验收指标（不等于"活跃度"）

| 指标 | 说明 |
|---|---|
| 有效行动比例 | 产生了实际结果的 Action 占比 |
| 无意义调用比例 | 没有产出的模型调用占比 |
| 记忆错误率 | 需要纠正的记忆占比 |
| 重复执行率 | 同一件事做了两次的比例 |
| 异常恢复成功率 | 崩溃/超时后恢复正常 |
| **每日 Token 和运行成本** | 不超预算 |

## 四、依赖关系

```
R4 Memory Hub（只读）✅
R5 写入安全 + 日记接入（开关关闭）✅
  ↓
R6 DSH Session 迁移 ──┐
                      ├─→ 4.0 验收
R7 工具权限 + 记忆管理 ─┘
  ↓
R8 自主规划
  ↓
R9 长期记忆治理（含日记写入启用 Go/No-Go）
  ↓
R10 主动交流 + 长期运行
  ↓
5.0 验收
```

**可并行的**：
- R8 的数据模型设计可以提前（不依赖 R6/R7 完成）
- R9 的指标准备可以提前

**不能并行的**：
- R10 必须在 R8/R9 之后（要先有规划能力和干净记忆）
- R7 的权限必须在 R6 的 Session 迁移**之前或同时**（不能让未稳定的权限被自主规划绕开）
