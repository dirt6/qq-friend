# 事故报告：QQ Agent 无法启动（2026-11-04）

## 一、现象

- 双击桌面「QQ Agent」无窗口、无托盘图标、无错误弹窗；
- 任务管理器里没有新的 `electron.exe`；
- 重启电脑后仍无法启动；
- 之前还有“关掉后仍在后台运行、托盘却没有图标”的情况。

## 二、环境

- Windows 11（LAPTOP-HANXC102），Node 24.21.0（开发），Electron 33.4.11（运行时）
- 应用：`E:\dsh\QQ-agent`，快捷方式 → `node_modules\electron\dist\electron.exe "E:\dsh\QQ-agent\." --no-sandbox`
- 数据：`E:\dsh\QQ-agent\data`；日记正文 `E:\dsh\日记`

## 三、关键证据

### 1. Windows 事件日志（Application Error，2026/11/4 1:25:53）

```
出错应用程序名称: electron.exe, 版本: 33.4.11.0
出错模块名称: electron.exe
异常代码: 0x80000003
错误偏移: 0x00000000068cf3db
```

`0x80000003` = `STATUS_BREAKPOINT`（`__debugbreak`）。项目 bat 的历史注释已记录过同一个异常：

> 2026-10-11: this machine needs --no-sandbox. Without it Chromium dies with exception 0x80000003 (__debugbreak in the Electron main module) BEFORE any JS runs.

但本次**已经带了 `--no-sandbox`**，仍然崩在同一个位置。

### 2. 启动日志（data/boot-diag.log）

- 2026-11-03T11:48:45Z（本地 19:48）正常：`核心已启动 port=3210`、`窗口与托盘就绪`；
- 2026-11-03T17:25:53Z（本地 01:25）：`main.js 已加载` → `src/app.js 已导入`，之后无 `核心已启动`，进程消失；
- 2026-11-04 重启后：**没有任何新的 boot-diag 记录**（崩在 main.js 之前）。

### 3. 复现方式

| 启动方式 | 结果 |
|---|---|
| 从 DSH 会话直接运行 electron.exe | 0x80000003，main.js 前崩 |
| `cmd start`（ShellExecute） | 同上，偶尔能到 app.js 导入后崩 |
| **计划任务（独立于 DSH 会话）** | 同样崩溃，无新日志 |
| 用户双击快捷方式 | 无进程、无日志 |

计划任务已排除“DSH 沙箱 job 限制”这一因素，说明是**系统级启动崩溃**。

## 五、根因判断

**Electron 33.4.11 在这台机器重启后的系统环境下启动即崩（0x80000003）**，且 `--no-sandbox` 已不能绕过。参数组合 `--disable-gpu`、`--disable-gpu-sandbox`、`--disable-features=RendererCodeIntegrity`、`--in-process-gpu`、`--disable-breakpad` 均无效。

最可能的方向：
1. Windows 更新在重启后生效，Electron 33.4.11 与当前系统/驱动不兼容（同一 exe 在 19:48 还能启动）；
2. 某个安全软件/系统策略在启动阶段对 electron.exe 做了拦截（无 WER/Defender 记录，无法直接证明）。

**这不是数据问题，也不是今晚的代码问题**；`data` 与日记正文没有被动过。

## 六、修复建议（按优先级）

1. **升级 Electron**（推荐）：`electron@33.4.11 → 35.x/36.x`，改 `package.json` + `npm install`，再验证启动。这是对 0x80000003 最直接的修复路径；
2. 若升级后仍崩：抓取 WER 的 `.dmp`（`C:\ProgramData\Microsoft\Windows\WER\ReportArchive\AppCrash_electron...`）分析崩溃模块；
3. 长期：把 Chromium userData 从 `data/electron-user-data` 挪到 `%LOCALAPPDATA%`，避免与工作区 ACL/备份策略互相影响（与本崩溃无关，是另一件事）。

## 七、托盘图标问题（附带记录）

“关掉后仍在后台运行、却没有托盘图标”是另一个独立问题：

- 主窗口 `close` 时按配置 `hide()` 到托盘，进程继续运行；
- `Tray` 只在启动时创建一次；Windows 资源管理器重启后 Electron 的托盘图标可能丢失，且 `main.js` 没有重建逻辑；
- 窗口隐藏 + 托盘图标丢失 = 用户无法唤出，看起来像“打不开”。

修复方向（未实施）：监听 `second-instance`（已有）之外，增加托盘图标健康检查/重建，或在 `close` 时同时给出“已最小化到托盘”的通知。

## 九、关键结论（2026-11-04 15:13，管理员会话）

以**管理员身份**启动同一份 `electron.exe 33.4.11` + 同一份代码：

```
boot-diag: 核心已启动 port=3210
boot-diag: [tray] 托盘已创建        ← P3 新增日志
boot-diag: 窗口与托盘就绪
进程: electron 26524 MainWindowTitle=QQ Agent，3210 监听
```

**启动成功，没有 0x80000003。**

对照之前所有失败记录（普通权限/受限 token）：33.4.11、35.7.5、44.7.0 全部在 `main.js` 之前以 `0x80000003` 崩溃。

因此**根因方向修正**：

- 不是 Electron 版本（管理员下 33.4.11 正常，DSH 用 44.7.0 也正常）；
- 不是数据/ACL/userData（这些已分别排除）；
- **与启动进程的权限/完整性级别有关**：普通 token 下 Chromium 初始化触发 `__debugbreak`，管理员 token 下正常。

这与 bat 注释“这台机器需要 `--no-sandbox`”属于同一类环境限制，但 `--no-sandbox` 已不能覆盖普通 token 下的崩溃。

**当前处置**：

- 桌面快捷方式 `QQ Agent.lnk` 已设为“以管理员身份运行”（`SLDF_RUNAS_USER`，flags 0x60F7）；
- 以后双击会弹一次 UAC，确认后启动；
- 若想免 UAC，可改用“计划任务（使用最高权限运行）”触发启动；
- 进一步定位普通 token 崩溃需要：受限 token 下复现 + dmp（WerSvc 已可启动，待用受限 token 触发）。
