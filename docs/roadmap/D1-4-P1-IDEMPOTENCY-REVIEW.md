## 一、判定方法（不靠“正文相似/时间接近”）

对每条告警：

1. 读取幂等记录：`key/day/hash/at/source/merged/line`；
2. 用 writer 的 `contentHash(mood|importance|text)[:16]` 对 `line` 反算，校验与记录 `hash` 一致；
3. 在对应日期正文中查找：**完全相等行**、**任意行内容 hash 与记录 hash 相等**、**前 14 字规范化前缀相同的行**；
4. 查 `diary.written` 事件（按 hash）：证明该次写入是否真的发生；
5. 对前缀相同的行，反算其 hash，若等于某条**更晚**的幂等记录 hash，则建立「合并/改写链」；
6. 查 `.trash` 历史备份，确认某行在历史时点是否存在；
7. 分类：
   - `confirmed_consistent`：能证明内容以合并/改写形式存在，或能证明是测试/重复键残留（非生产内容丢失）；
   - `confirmed_anomaly`：有证据表明生产内容被错误丢失/损坏；
   - `historical_unverifiable`：证据不足（写入发生过，但后续变化无记录）。

## 四、审计工具本身的问题（P1 要求）

1. **过度依赖精确文本匹配**：`done` 判定用 `line` 完全包含或前 20 字；合并改写会改变措辞/长度，导致误报；
2. **未利用 hash ↔ 正文行的对应**：记录 `hash` 是内容 hash，正文行可反算 hash；当前工具只看文本；
3. **无法识别合法合并改写**：没有“后继键 + 正文行 hash”的链条分析；
4. **会把测试残留误报为生产异常**：`source=test` 与测试时段写入未区分；
5. **重复键形态未区分**：同 day+hash 的 `auto:` / `auto:autonomous:` 两种键被当作独立异常；
6. **对“前 20 字”启发式敏感**：`36d951…` 因前 20 字命中而不告警，实际仍是改写（漏报/规则不一致）。
