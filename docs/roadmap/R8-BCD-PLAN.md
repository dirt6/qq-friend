### ① `pending: 22` 与 R4/R5 的 `pending: 12` 不一致

**我的实测**（2026-11-03 17:33 的文件快照）：


**文件元数据**：

**创建日期分布**：

```
2026-10-31:  5 条
2026-11-01:  3 条
```

**结论：无法直接验证 R4/R5 的 `pending: 12`。**

**原因**：
· `data/` 被 `.gitignore` 排除，**没有历史快照**
· R4/R5 的统计没有落盘
· 我只有当前状态

**三个可能的解释**（按可能性排序）：

| # | 解释 | 证据 |
|---|---|---|
| **1** | **不同时间点的快照** | `_v: 219` 说明文件持续在写。10-31 到 11-03 新增了 10 条（5+3+1+1），**正好对上 12 → 22 的差额** |
| **2** | **统计口径不同** | R4/R5 可能只统计 `status === 'pending' && contentType === 'fact'` 之类 |
| **3** | **生产数据变化** | 她在这几天确实写入了新经验 |

**我倾向解释 1**：
```
10-31: 5 条
11-01: 3 条
11-02: 1 条
11-03: 1 条
合计: 10 条   ← **正好是 12 → 22 的差额**
```

**但这是推测，不是证据。** 要确认需要 R4/R5 当时的原始输出。

**对设计的影响**：**零**。
不管历史是 12 还是 22，**当前基线是 22**，**设计按 22 来**。

### ② `corrections` vs `history` vs `correction` —— 三个字段完全不同

**实测分布**：

```
corrections = 1:          23 条（**全部！**）
有 history:                0 条
有 correction 对象:         1 条
historicalUnresolved=true:  1 条
```

**这三个字段的真实语义**：

| 字段 | 真实含义 | 实测 |
|---|---|---|
| **`corrections: 1`** | **`addExperience` 创建时的初始值**，**不是"被纠正过 1 次"** | 23/23 都是 1（**默认值，无信息量**） |
| **`history: []`** | **相似文本合并时的旧版本快照** | 0 条 = **没发生过合并** |
| **`correction: {...}`** | **真正的纠正事件**（含 `count`、`events[]`、`historicalUnresolved`） | **只有 1 条** |

**证据**（`src/learned.js` 的 `addExperience`）：
```js
store.items.push({
  ...
  corrections: 1     // ← 创建时就写 1，不是计数
});
```

**所以机主的担心是对的**：

> 不能把"没有历史记录"误解为"没有发生过纠正"

**准确的说法是**：
· **`history` 为空** = 没有发生过**相似文本合并**
· **`correction` 对象存在** = 发生过**真正的纠正**
· **`corrections: 1`** = **无信息量的默认值**

**🔴 这是一个需要修正的字段语义问题**：

`corrections` 这个字段名叫"纠正次数"，但**实际存的是初始值 1**，
只有合并时才 +1（`merged.corrections`）。

**建议**：
· **保留 `corrections` 字段**（向后兼容），但**文档里标注它不可靠**
· **判断"是否被纠正"只看 `correction` 对象**
· **R8 不依赖 `corrections` 字段**

## 二、R8-B：状态机与晋升候选（**不自动晋升**）

### 2.1 设计原则（机主原文）

> 如果错误记忆被频繁注入，它反而可能因为频繁使用而晋升，形成自我强化。
>
> 使用频率、重要性、来源和可信度不能相互替代。

**所以**：**`hits` 和 `lastUsedAt` 绝对不能作为晋升依据。**

### 2.2 状态定义（按机主的表格）

| 状态 | 含义 | 晋升依据 |
|---|---|---|
| `pending` | 新写入，尚未充分核实 | 创建时默认 |
| `verified` | **有明确来源或得到用户确认** | 用户确认，或满足严格的可追溯证据规则 |
| `stable` | **已确认且适合长期保留** | 明确确认其长期有效性，**不能仅凭命中次数** |

### 2.3 晋升候选机制（替代自动晋升）

**核心**：**系统只产出候选，不自己改状态。**

```
addExperience / 定期扫描
  ↓
suggestPromotion()  ← **新增**
  ↓
产出候选列表：{ id, from, to, reasons[], evidence }
  ↓
面板展示（经验管理页）
  ↓
用户点「确认晋升」
  ↓
setStatus(id, to, { source: 'owner' })   ← **现有入口，不变**
```

**关键**：**`setStatus` 的 `source === 'owner'` 检查不用改** ——
**候选机制只是"帮他做筛选"，最终拍板还是人。**

### 2.4 候选的判定规则（**可解释，可追溯**）

**`pending → verified` 的候选条件**（满足任一）：

| # | 条件 | 可解释理由 |
|---|---|---|
| **1** | **`origin.kind === 'owner'`**（机主明确说的） | 来源本身是"用户直接陈述" |
| **2** | **`epistemicType === 'direct'` 且 `correction.count === 0`** | 直接观察到的事实 + 从未被纠正 |
| **3** | **`correction.historicalUnresolved === false` 且有 `correction.events[]`** | 纠正过且已解决 |

**`verified → stable` 的候选条件**（**更严格**）：

| # | 条件 |
|---|---|
| **1** | 已经是 `verified` |
| **2** | `correction.count === 0` 或 `historicalUnresolved === false` |
| **3** | **`epistemicType === 'direct'`**（不能是推断） |
| **4** | **创建时间 > 14 天**（给足够时间验证） |

**⚠️ 明确排除的**：
· ❌ `hits >= N`
· ❌ `lastUsedAt` 距今多久
· ❌ 任何"使用频率"指标

### 2.5 数据结构

**新增字段**（不改现有字段）：

```json
{
  "id": "...",
  "status": "pending",
  "promotionSuggested": {
    "to": "verified",
    "at": "2026-11-03T...",
    "reasons": ["来源是机主本人的直接陈述", "从未被纠正"],
    "ruleId": "R1-owner-direct"
  }
}
```

**`promotionSuggested` 只是标记，不改变 `status`。**

### 2.6 测试矩阵

| # | 场景 | 期望 |
|---|---|---|
| 1 | `hits: 999` 的 pending | **不产生候选**（使用频率不是依据） |
| 2 | `origin.kind === 'owner'` 的 pending | 产生 `pending → verified` 候选 |
| 3 | `historicalUnresolved: true` 的 pending | **不产生候选**（未解决纠正要保护） |
| 4 | `epistemicType === 'inferred'` 的 verified | **不产生 `stable` 候选**（推断不能进 stable） |
| 5 | 创建 3 天的 verified | 不产生候选（不满 14 天） |
| 6 | 候选被接受后 | `status` 变了，`promotionSuggested` 清空 |
| 7 | 候选被拒绝后 | 记 `promotionRejectedAt`，**同一规则不再重复建议** |

## 三、R8-C：可信度评分（**与 relevance 正交**）

### 3.1 设计原则（机主原文）

> relevance 是检索相关度，不是可信度，必须保持正交。
> 不得让模型任意生成不可追溯的分数。

### 3.2 四个维度（**可解释，不调模型**）

**所有分数都由确定性规则算出，不调用任何模型。**

| 维度 | 取值 | 依据 |
|---|---|---|
| **来源可信度** `sourceScore` | 0.0 ~ 1.0 | `origin.kind`：`owner`=1.0 / `observed`=0.8 / `inferred`=0.5 / `unknown`=0.3 |
| **证据类型** `evidenceScore` | 0.0 ~ 1.0 | `epistemicType`：`direct`=1.0 / `inferred`=0.5 / `unknown`=0.2 |
| **纠正历史** `correctionScore` | 0.0 ~ 1.0 | 无纠正=1.0 / 已解决=0.7 / 未解决=0.3 |
| **冲突情况** `conflictScore` | 0.0 ~ 1.0 | 无冲突=1.0 / 有冲突但已标注=0.5 / 有未解决冲突=0.2 |

### 3.3 综合分

**加权平均**（权重写死在代码里，可审计）：

```js
credibility = 0.35 * sourceScore
            + 0.30 * evidenceScore
            + 0.20 * correctionScore
            + 0.15 * conflictScore
```

**为什么这三个权重**：
· **来源**最重要（0.35）—— 谁说的决定上限
· **证据类型**次之（0.30）—— 直接看到 vs 推断
· **纠正历史**（0.20）—— 被纠正过说明曾经错过
· **冲突**（0.15）—— 冲突不是错，是要标注

### 3.4 与 relevance 正交

**关键**：**两个分不开混。**

| 场景 | credibility | relevance | 会用吗 |
|---|---|---|---|
| 高可信 + 高相关 | 0.9 | 0.9 | ✅ **首选** |
| 高可信 + 低相关 | 0.9 | 0.1 | ❌ 不用（不相关） |
| 低可信 + 高相关 | 0.3 | 0.9 | ⚠️ **用，但标注"不确定"** |
| 低可信 + 低相关 | 0.3 | 0.1 | ❌ 不用 |

**实现**：**`selectForContext` 只按 relevance 排序**，**credibility 作为附加信息一起注入**。

**这样模型能看见**：「这条相关，但可信度只有 0.3」。

### 3.5 测试矩阵

| # | 场景 | 期望 |
|---|---|---|
| 1 | `origin.kind='owner'` + `direct` + 无纠正 | credibility ≈ 1.0 |
| 2 | `origin.kind='inferred'` + `inferred` | credibility ≤ 0.5 |
| 3 | `historicalUnresolved=true` | correctionScore = 0.3，总分明显降低 |
| 4 | 两个条目 relevance 相同、credibility 不同 | **排序不变**（正交） |
| 5 | 分数计算 | **纯函数，同输入同输出**（不调模型） |
| 6 | 未知的 `origin.kind` | 落到 `unknown`=0.3，**不崩** |

## 四、R8-D：重要日记结构化 + 分层加载

### 4.1 `[重要]` 结构化（机主给的字段建议）

**目标结构**（**不新建平行存储，挂到现有 R3 日记元数据接口上**）：

```json
{
  "importance": "important",
  "retention": "protected",
  "source": "diary",
  "paragraphIndex": 12,
  "quoteHash": "sha256:...",
  "migratedFrom": "text-prefix"
}
```

**机主明确**：字段只是建议，**最终要根据现有 R3 日记元数据接口确定**。

**所以第一步是查 R3 的接口**（下面 4.2）。

### 4.2 迁移策略（机主给的五条）

| # | 策略 | 实现 |
|---|---|---|
| **1** | **旧日记正文保持原样** | 只读不写 |
| **2** | **识别 `[重要]` 前缀，生成元数据** | 解析器 |
| **3** | **先做 dry-run 报告** | 列出每条的 `day` + `paragraphIndex` + 原文前 50 字 |
| **4** | **无法可靠匹配的保留待人工确认** | `importance: "unknown"`，不擅自标记 |
| **5** | **新日记写入时直接产生结构化元数据** | 改 `diary.write` |

**dry-run 的输出格式**：

```
2026-11-01.md  第 3 条  [重要] 别再提「那条架构帖」...
2026-11-02.md  第 1 条  [重要] 老大说要我听见真的雨声...
...
共 28 条 → 与人工核对数量一致
```

### 4.3 一个重要边界（机主原文）

> `important` 不应自动等同于"永远进入每轮提示词"。
> 它代表保留优先级和保护策略，**是否注入仍由当前话题相关性决定**。

**所以**：
· `importance: "important"` → **只影响"要不要被衰减"和"检索时的优先级"**
· **不改变"每轮注入什么"** —— 那是 `selectForContext` 的事

### 4.4 分层加载（按机主的修正版）

| 时间范围 | 默认处理 | 能否被召回 |
|---|---|---|
| **最近 7 天** | 允许加载摘要 + 相关条目 | ✅ |
| **8–30 天** | 优先加载**重要**和**与当前话题相关**的 | ✅ |
| **30 天以上** | **默认不批量注入** | ✅ **允许按话题检索** |

**关键差别**（和报告初稿比）：

| | 报告初稿 | 机主修正 |
|---|---|---|
| 30 天以上 | **不注入**（像是硬截断） | **默认不批量注入，但可检索** |

**实现**：
```js
async function loadDiaryForContext({ topic = '', now = Date.now() }) {
  const days = readDiaryDays(90);   // 最多读 90 天
  const out = [];
  for (const d of days) {
    const ageDays = (now - Date.parse(d.day)) / 86400000;
    for (const e of d.entries) {
      const isImportant = e.importance === 'important';
      const isRecent = ageDays <= 7;
      const isMid = ageDays > 7 && ageDays <= 30;
      const matchesTopic = topic && e.text.includes(topic);

      if (isRecent) { out.push(e); continue; }           // 7 天内默认加载
      if (isMid && (isImportant || matchesTopic)) { out.push(e); continue; }
      if (ageDays > 30 && (isImportant || matchesTopic)) { out.push(e); }  // 30 天以上仍可召回
    }
  }
  return out;
}
```

**注意**：**这只是"注入策略"，不删任何数据。**

### 4.5 测试矩阵

| # | 场景 | 期望 |
|---|---|---|
| 1 | 7 天内的普通条目 | 默认加载 |
| 2 | 20 天前的普通条目 | **不加载**（除非话题命中） |
| 3 | 20 天前的重要条目 | **加载** |
| 4 | **60 天前的重要条目** | **话题命中时加载**（不因年龄失去资格） |
| 5 | 只有 `[重要]` 前缀的旧日记 | dry-run 能识别出来 |
| 6 | 无法解析的条目 | 标 `importance: "unknown"`，不猜 |
| 7 | 新写的日记 | **直接带元数据**，不依赖正文前缀 |

## 五、Token 替换语义（独立工作包，**不依赖 R8**）

### 5.1 三种情况（机主的表格）

| 情况 | 处理 |
|---|---|
| **相同键、相同 usage** | **幂等跳过** |
| **相同键、不同 usage** | **替换旧值，并记录冲突** |
| **不同键** | 独立记录 |

### 5.2 冲突记录的结构（机主要求）

> 冲突记录至少应保留旧值、新值、替换时间和来源，避免只留下一个无法解释的最终数字。

```json
{
  "key": "turn:1|step:2",
  "oldUsage": { "input": 100, "output": 20, "cacheRead": 0, "cacheWrite": 0, "total": 120 },
  "newUsage": { "input": 150, "output": 30, "cacheRead": 0, "cacheWrite": 0, "total": 180 },
  "replacedAt": "2026-11-03T...",
  "source": "step_end",
  "seq": 42
}
```

### 5.3 实现位置

**`src/dsh-gateway.js` 的 `applyEvent`（`status` 分支）**

当前：
```js
if (seen.has(key)) {
  if (!sameUsage(seen.get(key), u)) conflicts.push(...);
  continue;   // 忽略
}
```

改成：
```js
if (seen.has(key)) {
  const prev = seen.get(key);
  if (sameUsage(prev, u)) continue;          // 情况 1：幂等跳过
  conflicts.push({ key, oldUsage: prev, newUsage: u, replacedAt: now, source: 'step_end', seq });
  seen.set(key, u);                          // 情况 2：替换
  continue;
}
```

### 5.4 测试矩阵

| # | 场景 | 期望 |
|---|---|---|
| 1 | 同键同 usage 两次 | 只算一次，`conflicts` 为空 |
| 2 | 同键不同 usage 两次 | 用**后者**，`conflicts` 有 1 条 |
| 3 | 同键不同 usage 三次 | 用**最后一个**，`conflicts` 有 2 条 |
| 4 | 不同键 | 各算各的 |
| 5 | 乱序到达（先 step2 后 step1） | 都记录，不因顺序丢失 |
| 6 | 异常中断（只收到 half） | 已收到的保留，不崩 |
| 7 | **和 DSH 的 `addReplacing` 对比** | 同输入同输出 |

### 5.5 R9-B 准入条件（机主定的）

> 替换语义实现完成，重复事件、乱序事件、异常中断和多次不同 usage 更新测试通过；
> retry 轴暂不作为当前硬门槛。

**所以**：
· ✅ 必须做：替换语义 + 四种测试
· ⏸ 可以不做：retry 轴

### 5.6 不改生产账本

**`data/model-calls.ndjson` 的历史记录不动。**
**新记录用新语义。**

## 七、兼容与迁移

### 7.1 旧数据兼容

| 对象 | 兼容策略 |
|---|---|
| **`learned.json` 的 `items`** | **只加 `promotionSuggested` 字段**，不改现有字段 |

### 7.2 异常恢复

| 场景 | 处理 |
|---|---|
| `promotionSuggested` 写了一半 | 字段不存在 = 无候选，**不崩** |

### 7.3 不删任何东西

**R8 全程不删除任何记忆**：
· 衰减 = 改 `status`（`archived`），**数据还在**
· 重要日记 = **加元数据**，正文不动
