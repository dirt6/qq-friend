## 二、3.0：记忆可信化

### 2.1 版本目标

> **让每一条记忆都能回答三个问题：这是什么性质（事实/推测）？从哪来的？被纠正过什么？**

**不是为了存更多，而是为了能判断可信度。**

### 2.2 完整功能范围

| # | 功能 | 现状 | 目标 |
|---|---|---|---|
| 3.0.1 | **统一元数据规范** | 五层各有一套字段 | 统一 `epistemicType` / `origin` / `correction` |
| 3.0.2 | **经验记忆纠正结构化** | `corrections: 1`（只有计数） | 记录 `correctedFrom` / `correctedTo` / `at` |
| 3.0.3 | **聊天记忆来源与性质分类** | `impressions` 无明确标注 | 标注 `fact` / `inference` |
| 3.0.4 | **日记结构化与原文保留** | 纯 markdown | 加元数据，**原文不动** |
| 3.0.5 | **记忆检索质量验证** | 无验证 | 建评测集，测准确率/召回率 |
| 3.0.6 | **五层数据兼容与迁移** | 无 | 只加字段，不重写存储 |

### 2.3 数据模型（核心）

```js
{
  // ── 性质分类（机主明确定义）──
  contentType: 'fact' | 'preference' | 'event' | 'plan' | 'other',
  epistemicType: 'direct' | 'inferred' | 'unknown',

  // ── 来源 ──
  origin: {
    kind: 'chat' | 'autonomous' | 'diary' | 'user_stated' | 'inferred' | 'unknown',
    ref: 'chatKey / roundId / dateKey',
    at: ISO,
    quote: '原话片段（可选，≤ 200 字）'
  },

  // ── 纠正事件（**与 epistemicType 分开**）──
  correction: {
    count: 1,
    events: [
      {
        at: ISO,
        correctedFrom: '原来的说法',
        correctedTo: '纠正后的说法',
        by: 'user_directed' | 'autonomous',
        quote: '机主原话（可选）'
      }
    ],
    // ⚠️ 历史纠正无法还原时用这个标记
    historicalUnresolved: false
  }
}
```

**机主强调的两点**：

1. **`correction` 不能和 `epistemicType` 混为一谈**
   - `epistemicType` 回答「这条记忆是什么性质」
   - `correction` 回答「它被改过几次、改成什么」

2. **历史 `corrections` 计数怎么恢复**

| 情况 | 处理 |
|---|---|
| 能从 `text` 里读出纠正内容 | 恢复真实 `correctedFrom` / `correctedTo` |
| 读不出 | 标 `historicalUnresolved: true`，**保留 count** |
| ❌ **禁止** | **推测 `correctedFrom` / `correctedTo`** |

**生产上现在有 1 条真实数据**：

```json
{
  "id": "l-mvq5ul9z-fla",
  "text": "老大纠正我说话的主语：“老大我让你学一下梗”改为「老大，我学一下梗」，别把事说到他头上；",
  "corrections": 1
}
```

**这一条能读出纠正内容**（"…改为…"）→ **可以结构化**（但是启发式提取，要人工确认）。

### 2.4 模块依赖

```
3.0.1 元数据规范
  ├─→ 3.0.2 经验纠正结构化（learned.js）
  ├─→ 3.0.3 聊天记忆分类（memory.js）
  └─→ 3.0.4 日记结构化（diary/writer.js）
        ↓
3.0.5 检索质量验证（依赖前四项）
3.0.6 五层兼容（贯穿）
```

### 2.5 验收标准

| # | 标准 |
|---|---|
| 1 | 五层数据都能读出 `epistemicType`（旧数据默认 `unknown`） |
| 2 | `correction.events` 能记录纠正前后；无法恢复的标 `historicalUnresolved` |
| 3 | **不推测任何 `correctedFrom` / `correctedTo`** |
| 4 | 日记**原文一个字节不改**，元数据单独存 |
| 5 | 检索评测集 ≥ 30 条，准确率/召回率有基线数字 |
| 6 | 旧数据读取不产生写入 |

### 3.3 三条硬约束（机主明确）

#### ① Memory Hub 必须是统一访问与管理层，**不得合并五层底层存储**

**已有的规划就是这个定位**：

> 约束：只做统一入口，不复制第三套记忆；原始文件仍是唯一存储。
> —— `待办-清单.md` §阶段 2.5

**具体接口**（历史上已定）：

```js
// src/memory-hub/{index,retrieval,writer,diary,learned,impressions,activities,chat-history}.js

// 统一检索结果
{ type, id, source, content, timestamp, relevance }
// relevance 只表示检索评分，不是可信度
```

#### ② DSH 会话继续保留原始会话语义

**机主明确**：

> DSH 会话继续保留原始会话语义，不要求每条消息都变成 fact/inference 记忆。

**所以**：DSH session **不是**第 6 层记忆，**它就是会话轨迹**。3.0 的元数据**不要求**应用到 DSH 消息上。

#### ③ Autonomous Session 迁移必须有 Go/No-Go 测试

**机主明确**：

> 不通过时保留原 API。

**对应内部阶段 3.1**：

| Go 条件 | 不满足时 |
|---|---|
| 独立 Session 可恢复 | ❌ No-Go → 保留 `askDsh` 原路径 |
| 双 Session 不污染 | ❌ No-Go |
| 工具不重复执行 | ❌ No-Go |
| 延迟在阈值内（P95 60/120s） | ❌ No-Go |
| Token 可统计 | ❌ No-Go |

**DSH 版本约束**：`0.2.1-rc.5`，**不得默认任何第三方插件兼容**（包括 `dsh-mnemon`，它只能是后续技术候选）。

## 四、5.0：长期自主伙伴

### 4.1 版本目标

> **从「能自主活动」到「长期可靠地自主」，并且不靠频繁调用模型或频繁打扰来证明存在感。**

### 4.2 完整功能范围

| # | 功能 | 说明 |
|---|---|---|
| 5.0.1 | **长期方向管理** | Goal 的跨月维护、回顾、自然退役 |
| 5.0.2 | **自主活动规划** | 从「每轮决定做什么」到「有节奏的周计划」 |
| 5.0.3 | **长期记忆维护** | 记忆的衰减、强化、合并（**不自动删**） |
| 5.0.4 | **主动交流** | 有边界的主动发起（**不刷存在感**） |
| 5.0.5 | **任务连续性** | 跨轮任务不丢、可恢复 |
| 5.0.6 | **管理面板** | 长期趋势、异常、预算 |
| 5.0.7 | **长期运行可靠性与预算控制** | 7 天 / 30 天长跑 |

### 4.3 一条硬约束（机主明确）

> **不得以频繁调用模型或频繁打扰用户作为自主性指标。**

**这意味着**：

| ❌ 不作为指标 | ✅ 作为指标 |
|---|---|
| 每天调用多少次模型 | **有意义的长期方向是否被推进** |
| 主动发了多少条消息 | **该说话的时候有没有说，不该说的时候有没有忍住** |
| Goal 创建数量 | **创建的方向后来是否真的持续关注** |
| 活动轮次 | **活动是否产生了可复用的成果** |

### 4.4 验收标准（初稿，需细化）

| # | 标准 |
|---|---|
| 1 | 30 天长跑无数据损坏 |
| 2 | 预算不超（月 5 元 / 800 万 token 口径） |
| 3 | 无「重复追问已答问题」 |
| 4 | 长期方向的生命周期可追溯（创建→推进→完成/取消） |
| 5 | **活跃度不作为成功指标**（写入验收文档） |
